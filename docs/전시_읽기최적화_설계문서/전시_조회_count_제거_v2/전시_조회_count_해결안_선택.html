01 — 갈림길을 정한 것

count는 한 종류가 아니었습니다

지금은 이 둘을 요청 하나가 같이 처리합니다. 그래서 양쪽 다 손해를 봅니다.

A와 B 모두 “count는 목록과 다른 리소스”라고 말합니다. A는 목록 없이 숫자만 원하고, B는 숫자를 목록보다 늦게 받아도 됩니다. 이건 성능 우회가 아니라 원래 두 개였어야 할 것이 하나로 붙어 있던 것입니다 — 그래서 해결 3(엔드포인트 분리)이 구조상 맞습니다.

동시에 A가 해결 3만으로는 안 빨라진다는 것도 여기서 보입니다. 요청을 쪼갠 것뿐이고 count 쿼리 자체는 여전히 5.4초입니다. 그래서 마지막 갈림길이 생깁니다(05장).

02 — 해결 1의 판단 과정

왜 해결 1은 “선택”이 아니었나

나머지 5개는 전부 무엇을 내주고 속도를 살 것인가의 문제입니다. 해결 1만 내줄 게 없습니다. 그래서 비교 대상에 올리지 않고 세 가지만 확인했습니다.

Q1

이 count를 누가 쓰는가?

아무도 안 씁니다. 만들자마자 버려집니다.

// infra/exhibition/catalog/ExhibitionQueryRepositoryImpl.java
return jpaRepository.findAll(ExhibitionSpecifications.slice(query),
        PageRequest.of(0, limitPlusOne, sortFor(query.sort()))).getContent();
//                                                              ~~~~~~~~~~~~
//   Page를 받아 content만 꺼내고, 함께 실행된 총 건수는 버린다

그래서 — 사용처가 0인 비용은 트레이드오프가 아니라 결함입니다. “속도를 위해 무엇을 포기할까”라는 질문 자체가 성립하지 않습니다.

Q2

없애면 무엇이 바뀌는가?

응답은 한 바이트도 안 바뀝니다. 바뀌는 건 SQL 하나가 안 나가는 것뿐입니다.

확인 항목beforeafter판정
응답 JSON동일동일변화 0

정렬 결정성sortFor(정렬컬럼, id)sortFor(정렬컬럼, id)그대로 전달
커서 경계Specification 내부Specification 내부건드리지 않음

그래서 — 되돌리기가 git revert 한 줄입니다. 리스크 평가에 시간을 더 쓸 이유가 없었습니다.

Q3

그럼 왜 지금까지 안 보였나?

Spring Data가 count를 생략할 수 있으면 생략하는데, 그 조건이 개발 환경에서만 참이었습니다. 

// SimpleJpaRepository → PageableExecutionUtils.getPage(...)
if (첫 페이지다 && 요청한 페이지 크기 > 실제로 받은 건수) {
    return new PageImpl<>(content, pageable, content.size());  // count 안 나감
}
return new PageImpl<>(content, pageable, countSupplier.getAsLong()); // count 나감
상황pageSize받은 건수판정count
로컬 — 데이터 몇 건21821 > 8 참생략
운영 — 페이지가 꽉 참212121 > 21 거짓실행

그래서 — 로컬에선 정상으로 보이고 목록이 한 페이지를 채우는 순간(= 정상 운영 상태) 두 배가 됩니다. 코드 리뷰로도 재현으로도 안 잡히는 종류입니다. 운영은 진행 중 전시 246건에 size=20이라 거의 모든 요청이 해당합니다.

그래서 회귀 테스트에 조건이 하나 붙습니다. ExhibitionSliceCountTest는 대상을 페이지 크기보다 많이 만들어 페이지를 반드시 채워야 합니다. 안 그러면 Q3의 생략 분기가 타서 옛 구현도 통과합니다 — 테스트가 있는데 아무것도 못 잡는 상태가 됩니다.

마지막 확인 — 뒤 단계가 이 이득을 흡수하지 않는가? 해결 3으로 totalCount를 목록 밖으로 빼도 해결 1의 가치는 남습니다. 둘은 다른 count입니다: 해결 1은 searchSlice 내부의 버려지는 count를 없애고, 해결 3은 ListPage의 응답용 count를 옮깁니다. 슬라이스 조회는 어느 루트에서도 목록 경로에 남으므로 해결 1은 뒤 결정과 무관하게 항상 참입니다.

기대 · 요청당 JDBC 문 5 → 4 · S1(최신순) 100만 p50 8,890ms → ~7,100ms

판정과 근거

04 — 해결 2 탈락의 두 번째 이유

공통 봉투를 건드리면 측정도 안 한 도메인이 깨집니다

설계 문서는 CursorResponse에서 필드를 빼라고 했지만, 그 봉투는 전시 전용이 아닙니다.

public record CursorResponse<T>(List<T> content, String nextCursor, boolean hasNext, long totalCount) { }

interfaces/bookmark/BookmarkV1Controller.java:67       ← 관심 전시   (이번 실험 미측정)
interfaces/notification/dto/NotificationDto.java:39    ← 알림       (이번 실험 미측정)

봉투에서 빼면 두 도메인의 응답 계약이 같이 바뀝니다. 관심 전시·알림은 전시 볼륨이 아니라 유저당 데이터 수에 반응하므로 이번 실험이 측정하지 않았습니다 — 안전하다고 쓸 근거가 없습니다.

빼더라도 봉투는 그대로 두고 전시 응답에서만 채우지 않는 쪽이어야 합니다. 관심 전시는 이미 countActiveByIds로 id 목록 안에서만 세고 있어 성격도 다릅니다.

05 — 마지막 갈림길

루트 두 개 — 각각 무엇을 얻고 무엇을 잃는가 B 채택

해결 1과 해결 3은 두 루트의 공통 구간입니다. 갈리는 건 그다음 한 가지 — count 자체를 상수 시간으로 만들 것인가, 정확성을 지킬 것인가.

루트 A · “괜찮다”  미채택

상한을 허용한다 — 해결 3 + 해결 4

정확한 숫자 대신 상한까지만 센다. 스캔이 상한에서 멈춘다.

GET /api/v1/exhibitions/count
  → countUpTo(query, 1000)
  ← { count: 126, exact: true }
목록 응답에서 totalCount 제거

얻는 것

  • 볼륨과 무관한 상수 시간. 데이터가 4배 늘어도 count 비용이 그대로 — 곡선의 기울기가 바뀐다
  • A 화면이 즉답. 칩을 눌러도 숫자가 바로 갱신됨
  • 목록에서 count가 완전히 사라짐 → S3(인기순)이 배너처럼 평평해질 것
  • 지금 데이터(246건)에선 숫자가 여전히 정확하다 — 1,000+는 부하실험에서만 뜬다
  • 해결 5(캐시)가 불필요해진다 — 조합 폭발 문제를 아예 안 만난다

잃는 것

  • 정확성의 상한. 진행 중 전시가 1,000을 넘으면 버튼이 1,000+개 전시 보기가 된다
  • 응답에 exact 플래그 추가 → 프론트가 문구를 분기해야 한다(두 화면)
  • 상한값이 매직넘버가 된다 — 어디에 두고 누가 언제 바꾸는지 정해야 함
  • “정확한 총 건수”라는 성질을 영구히 포기하는 결정이다(되돌리려면 다시 UI 작업)

남는 위험

  • 상한은 결과 행 기준이지 읽은 행 기준이 아니다. 선택도가 낮은 필터 (section=free 등)는 조건에 맞는 1,000행을 채우려 훨씬 더 읽는다 — 해결 6이 여전히 필요하다
  • 설계 문서의 구현안(project("id").limit(n).all().size())은 매 요청 1,000개 스칼라를 만든다. QueryDSL로 상한을 거는 편이 낫다
루트 B · “항상 정확해야 한다”  채택

정확성을 지킨다 — 해결 3 + 해결 6

count는 정확한 값 그대로 두고, 인덱스로 상수배만 줄인다.

GET /api/v1/exhibitions/count
  → count(query) — 그대로
  ← { count: 126 }
+ idx (type,start_date) (type,end_date)
  + place(region) + detail(price)

얻는 것

  • 숫자가 100% 정확. UI 문구 변경 없음, exact 플래그 불필요
  • B 화면(목록)은 루트 A와 체감이 같다 — count가 목록 밖으로 나가는 건 공통 구간이므로
  • 프론트 작업이 더 적다 — 엔드포인트 하나만 붙이면 끝
  • 인덱스는 목록 filesort도 같이 없앤다(정렬 몫 3~4초)
  • 제품 결정을 지금 안 내려도 된다 — 나중에 루트 A로 갈 수 있다

잃는 것

  • A 화면이 근본적으로는 안 빨라진다. count는 여전히 O(N), 인덱스는 상수배만 줄인다 — 칩을 누를 때마다 그 비용을 낸다
  • 곡선의 기울기가 그대로다. 66만 행을 세는 사실이 안 변한다 — 데이터가 늘면 다시 느려진다(구조적 해결을 미룬 것)
  • 프론트에 디바운스가 사실상 필수가 된다(칩 연타 → count 폭주)
  • 인덱스 4개 = 쓰기 비용 + 저장. ingestion 대량 적재 경로가 그만큼 느려진다

남는 위험

  • 언젠가 루트 A로 갈아타야 할 수 있다 — 그때 UI 문구 변경 비용을 그때 낸다. 지금 내는 것보다 비싸진다(화면이 늘어나 있을 것)
  • “인덱스로 해결했다”가 다음 볼륨에서 무효화되는 종류의 개선이다

차이는 화면 하나에서만 납니다

루트 B — 성능이 아니라 팀 상황이 정했습니다.

정확성을 포기하고 속도를 챙기는 것 자체는 문제가 없고, 사용자에게 1,000+개로 보여주는 것도 괜찮습니다. 다만 프론트가 1명이고 본업 야근이 많아 작업이 추가되는 구조라, exact 문구 분기 같은 사소한 것도 부담이 됩니다. 그래서 루트 B로 갑니다.

이 결정으로 얻는 것

  • 프론트 작업이 엔드포인트 연결 하나로 끝난다 — 문구 분기도, 플래그 처리도 없다 (이게 실제 이유)
  • 숫자가 항상 정확하다. 126개 전시 보기가 영원히 정확한 값
  • 목록(B 화면)은 루트 A와 똑같이 빨라진다 — 여기서 잃는 게 없다
  • 제품 결정을 지금 안 내려도 된다

이 결정으로 잃는 것

  • 필터 시트(A 화면)의 count가 O(N)으로 남는다. 인덱스가 줄인 만큼만 빨라진다
  • 곡선의 기울기가 안 바뀐다 — 데이터가 늘면 같은 문제가 다시 온다
  • 해결 5(캐시)가 보류에서 후보로 승격된다 — 루트 A에선 필요 없던 작업이다
  • 백엔드 후속 작업이 5건 생긴다(07장) — 루트 A였다면 상한 하나로 끝났을 일

그래서 이 거래의 정체는 “정확성 ↔ 속도”가 아닙니다. “프론트 1명의 작은 작업 1건 ↔ 백엔드 후속 작업 5건”으로 바뀐 것입니다. 프론트가 낼 비용을 백엔드가 인수한 거래이고, 그 인수분이 다음 장의 내용입니다. 이 교환이 유리한지는 백엔드에 그만한 여유가 있는지에 달렸습니다 — 없다면 지금 다시 말해야 합니다.

06 — 그런데

사실 두 루트가 아니라 다이얼 하나입니다

루트 B는 “상한 없음”이고, 루트 A는 “상한 1,000”입니다. 같은 축의 양 끝이지 다른 설계가 아닙니다.

1,000루트 A · 상수 시간
10,000사실상 정확 · 10배 스캔
∞  ← 여기루트 B · 정확 · O(N)
← 빠름 · 덜 정확정확 · 느림 →

그래서 포트 시그니처 하나가 두 루트를 다 표현합니다. 상한을 설정값으로 두면 지금 결정을 못 내려도 코드가 바뀌지 않습니다 — 나중에 다이얼만 돌리면 됩니다. 

/** 최대 {@code limit}까지만 센다. limit <= 0 이면 상한 없이 정확히 센다. */
long countUpTo(ExhibitionQuery query, int limit);

// limit = 1000  → 루트 A
// limit = 0     → 루트 B (기존 count(*)로 위임)

우리는 지금 ∞에 섭니다. 그래도 exact 필드는 지금 넣고 항상 true를 줍니다 — 프론트는 모르는 필드를 안 읽으면 그만이라 지금 드는 프론트 작업이 0이고, 나중에 다이얼을 돌릴 때 백엔드 한 줄로 끝납니다. 프론트가 1명인 상황에서 가장 싼 보험입니다(07장 작업 5).

07 — 인수한 몫

08 — 필터 축 설계

지역·장르를 인덱스가 타게 만들 수 있는가

가능합니다. 다만 숫자로 바꾸는 것은 그 이유가 아닙니다 — 먼저 이것부터 털고 갑니다.

가설 — “VARCHAR라서 인덱스를 못 타니 1, 2 같은 숫자로 바꾸면 되지 않을까?”

사실 — VARCHAR도 인덱스를 그대로 탑니다.

region IN ('SEOUL','GYEONGGI')는 인덱스만 있으면 정상적으로 범위 스캔이 됩니다. 지금 못 타는 이유는 타입이 아니라 두 가지입니다 — ① exhibition_place.region에 인덱스가 아예 없고, ② 다른 테이블 서브쿼리라서입니다. 숫자화는 이 둘 중 어느 것도 풀지 않습니다.

숫자화가 실제로 주는 건 상수배입니다 — 인덱스 엔트리 크기(utf8mb4 VARCHAR(20)는 최대 80바이트대, TINYINT는 1바이트)와 비교 비용(collation 비교 → 정수 비교). 페이지당 엔트리가 늘어 I/O가 주는 이득은 진짜지만, 없는 인덱스를 만들어주지는 않습니다.

그래서 순서는 — 인덱스를 만들고(작업 2) · 같은 테이블로 내리고(작업 3) · 그다음에 타입을 줄인다.

그럼 진짜 설계 여지는 — 세 가지

설계 1 · 작업 3에 이미 포함

복합 인덱스 — 등치 먼저, 범위 마지막

작업 3으로 region이 exhibitions에 내려와야 비로소 지역과 장르를 한 인덱스에 담을 수 있습니다. 

create index idx_ex_filter on exhibitions(region, category, end_date, id);
                                          └ 등치(IN) ─────┘  └ 범위 ─┘  └ 타이브레이커

-- 서울·경기 × 회화·사진 = 등치 조합 4개 → 각각 end_date 범위 스캔 4회

그래서 작업 3은 단순한 서브쿼리 제거가 아닙니다. 두 필터 축을 한 인덱스에 넣기 위한 전제조건입니다 — 이게 작업 3의 진짜 가치입니다.

주의 1 — 한 축만 걸 때를 위해 컬럼 순서가 중요합니다. (region, category, …)는 지역만 걸어도 선행 prefix라 잘 탑니다. 장르만 걸면 못 탑니다(skip scan은 약합니다). 둘 다 흔하면 인덱스를 두 벌 두거나, 더 자주 단독으로 쓰이는 축을 앞에 둡니다.

주의 2 — 다중 선택 + 정렬은 한 인덱스로 동시에 만족되지 않습니다. region IN (a,b)면 범위가 둘로 갈라져 행이 전역 정렬 순서로 나오지 않습니다 → 목록 쿼리엔 filesort가 남습니다. 다행히 count는 ORDER BY가 없어 이 제약을 받지 않습니다 — 우리가 지금 푸는 게 count라 맞아떨어집니다. 대신 목록 쪽 이득은 다중 선택 시 반감된다고 적어둡니다.

설계 2 · 가장 강력 ★

요약 테이블 — (지역 × 장르) 칸의 합

결정적 성질이 하나 있습니다. 전시 하나는 지역 1개·장르 1개만 갖습니다 (exhibitions.category, exhibition_place.region 모두 단일 컬럼). 따라서 (지역, 장르) 쌍이 데이터를 겹치지 않게 분할합니다.

가로 = 장르 9 · 세로 = 지역 18  →  162칸 · 서울·경기 × 회화·사진 = 4칸의 단순 합 (겹침 보정 불필요)

그래서 다중 선택 count가 선택된 칸들의 덧셈이 됩니다. 필터 시트의 126개 전시 보기는 162행짜리 작은 테이블에서 몇십 행을 더하는 일이 되고, 전시가 100만 건이든 상관없이 상수 시간입니다. 인덱스 스캔조차 필요 없습니다.

갱신은 “진행 중” 판정이 날짜에 의존하므로 하루 1회 + 수집 직후 재계산이면 충분합니다 (전시 데이터는 12시간 폴링으로만 바뀝니다). 무료 축까지 넣으면 324칸입니다.

정직하게 — 이것도 근사의 일종입니다. 갱신 시점 기준이라 그 사이 변경분이 빠집니다. 루트 B의 전제(“항상 정확”)와 긴장 관계에 있다는 걸 알고 써야 합니다.

다만 상한 근사와는 성격이 다릅니다 — 표시되는 숫자의 형태는 정확하고 (1,000+ 같은 표기가 없어 프론트 작업 0이 유지됩니다), 오차 원인이 볼륨이 아니라 시간 지연이며, 전시는 하루 단위로만 바뀌므로 실질 오차가 0에 가깝습니다.

못 쓰는 경우 — 검색어가 같이 걸리면 무효입니다. 그때만 실시간 count로 폴백합니다. 홈 3섹션은 조합이 고정이라 같은 테이블에 행 몇 개로 흡수됩니다.

설계 3 · 마지막 · 선택

숫자화 (TINYINT) — 질문의 직접 답

해도 됩니다. 다만 1순위가 아닙니다. 얻는 것은 인덱스 크기와 비교 비용의 상수배 감소입니다.

잃는 것은 가독성(콘솔에서 3이 뭔지 모릅니다), 그리고 더 중요한 것 — JPA ORDINAL은 위험합니다. enum 상수 순서만 바꿔도 기존 데이터의 의미가 통째로 어긋납니다. 지금은 @Enumerated(STRING)이라 그 위험이 없습니다.

굳이 한다면 ORDINAL이 아니라 명시적 코드 컬럼 (region_code TINYINT)을 두고 enum에 코드를 박아 순서와 분리해야 합니다.

그리고 설계 2를 하면 이 축은 거의 의미가 없어집니다 — 162행짜리 테이블에서 컬럼이 VARCHAR인지 TINYINT인지는 차이를 만들지 않습니다.

07장 작업 목록에 미치는 영향 — 작업 4가 바뀝니다. 캐시(해결 5)는 조합 폭발과 무효화 정책이 골칫거리였는데, 요약 테이블은 조합이 162개로 유한하고 무효화가 “재계산” 하나로 단순합니다. 같은 문제에 대해 캐시보다 낫습니다 — 작업 4의 1안을 요약 테이블로 바꾸고, 캐시는 검색어 폴백 경로에만 남겨두는 편이 맞습니다.

단, 순서는 그대로입니다 — 요약 테이블도 작업 1~3 뒤에. 먼저 오면 느린 쿼리를 감춥니다.
