## 🧭 1. 설계 원칙 — 두 축을 섞지 않습니다

| 축 | 답하는 질문 | 도구 | 병목이 나타나는 곳 |
| --- | --- | --- | --- |
| **동시성** | 동시 N명에서 버티는가 | k6 부하 | CPU · 커넥션풀 · 스레드 |
| **데이터 볼륨** | 데이터 N건에서 쿼리가 어떻게 되는가 | `EXPLAIN` · 단일요청 | 인덱스 · IO · 정렬 |

이번 목적(조회속도 개선)은 **볼륨 축**입니다. 그런데 k6는 동시성 축 도구입니다.

`k6/README.md`의 기존 측정이 이 함정을 보여줍니다.

> 병목은 CPU(backend 피크 **728%**, mysql **539%**)

**수백 건 규모에서 이미 CPU-bound입니다.** 부하를 세게 걸면 CPU 포화가 쿼리 비용을 덮어써서, p95가 올라가도 그것이 인덱스 탓인지 CPU 경합 탓인지 구분할 수 없습니다.

> 🧠 **부하를 세게 걸수록 볼륨 효과는 오히려 안 보입니다.** 볼륨을 재려면 동시성을 **낮게 고정**해야 합니다.

## 📋 2. 매트릭스별 분석

### 🧠 D. 반복 조회 볼륨 스윕 (VU 1, 경로당 500회) ⭐ **본체**

| 항목 | 내용 |
| --- | --- |
| **목적** | 쿼리 자체의 비용이 볼륨에 따라 어떻게 변하는가 |
| **알 수 있는 것** | 순수 쿼리 시간, 어느 경로가 **볼륨에 선형인지**, 인덱스 추가 전후의 차이 |
| **못 알아내는 것** | 커넥션풀 포화, 조회수 UPDATE 락 경합 — **원리상 못 봅니다** |
| **한계** | 실사용 재현이 아님. 반복 시 버퍼풀이 웜이라 낙관적 → **파라미터 랜덤화로 완화**(4장) |
| **비용** | 매우 낮음 (볼륨당 수 분) |

`EXPLAIN`과 1:1로 대응돼 **Stage 2 작업에 그대로 쓰입니다.** 인덱스를 하나 걸 때마다 5분이면 재측정됩니다.

- ✅ **장점:** 재현성이 가장 높고 가장 쌉니다. 노이즈(CPU 경합·GC)가 최소입니다
- ⚠ **단점:** 동시성이 만드는 큐잉·경합은 안 보입니다 → 100만에서 A로 1회 보완

### 🧠 A. 고정 부하(10 VU) — 100만 지점에서 1회만

| 항목 | 내용 |
| --- | --- |
| **목적** | 실사용 근접 조건에서 볼륨에 따른 p95/p99 열화 |
| **알 수 있는 것** | 사용자 체감 지표, **몇 건부터 SLO를 깨는지** |
| **못 알아내는 것** | **왜** 느려졌는지 — 쿼리 지목이 불가합니다(slow log 병행 필수) |
| **한계** | VU 선정이 결과를 좌우합니다. 너무 높으면 CPU가 볼륨 효과를 가립니다(11장) |
| **비용** | 낮음 (1런, 약 5분) |

- ✅ **장점:** VU 1로는 못 보는 커넥션풀 포화·락 경합을 드러냅니다
- ⚠ **단점:** 원인 규명이 안 돼 단독으로는 다음 행동을 못 정합니다

### 🧠 B. 볼륨마다 계단식 램핑 (50→100→200→400 VU)

| 항목 | 내용 |
| --- | --- |
| **목적** | 볼륨별 용량 곡선(knee) 전체 |
| **알 수 있는 것** | 볼륨이 처리량 천장을 얼마나 깎는지 (현재 ≈900 req/s → ?) |
| **못 알아내는 것** | 여전히 원인 지목은 불가합니다 |
| **한계** | 고 VU에서 **k6 자체가 오염원**입니다 — 로컬 단일 호스트라 k6·앱·MySQL이 CPU를 나눠 씁니다 |
| **비용** | 큼 (16런, 약 3시간) |

- ✅ **장점:** 용량 한계를 볼륨별로 비교할 수 있습니다
- ⚠ **단점:** 표가 복잡해져 정작 "볼륨 효과"가 묻힙니다

### 🧠 C. 하이브리드 (A + 100만에서만 B)

## 🚧 3. 전 매트릭스 공통 한계

> 결과 문서에 **반드시 함께 적습니다.** 이 단서 없이 숫자만 남기면 다음 사람이 오독합니다.

### ⚠ 3-1. 로컬 단일 호스트 오염

k6·Spring·MySQL이 같은 맥북 CPU를 나눠 씁니다. 부하가 올라갈수록 **측정 도구가 측정 대상을 방해**합니다.

- 운영은 인스턴스가 분리돼 있어 곡선 모양이 다릅니다
- 절대값을 운영에 그대로 대입하면 안 됩니다. **볼륨 간 상대 비교**만 유효합니다
- 완화: 부하 구간에서 `docker stats`를 함께 기록해 CPU 포화 시점을 표시합니다

### ⚠ 3-2. 버퍼풀이 결과를 지배합니다

운영은 **t3.small(2 vCPU · RAM 2GB · 디스크 20GB)** 한 대에 **도커로 전체 스택**(Spring + MySQL + Redis + Alloy)을 올립니다. MySQL이 쓸 수 있는 메모리가 매우 좁습니다.

| 대략적 배분 (RAM 2GB) | 추정 |
| --- | --- |
| JVM 힙 + 메타스페이스 | ~700MB~1GB |
| MySQL (버퍼풀 128MB + 커넥션·기타) | ~400~500MB |
| Redis (`maxmemory 64mb`) | ~80MB |
| Alloy · OS · 페이지캐시 | 나머지 |

- **기본값 128MB가 오히려 운영 현실입니다.** 올릴 여유가 없습니다 — t3.small에서 버퍼풀을 1GB로 올리면 JVM과 충돌해 OOM입니다
- 100만 건이면 데이터가 버퍼풀을 한참 넘겨 **디스크 IO가 지배**합니다. 이건 회피 대상이 아니라 **재현 대상**입니다
- **결정**: 로컬 MySQL도 **`innodb_buffer_pool_size=128M`으로 고정**해 운영의 IO 압력을 재현합니다. 전 볼륨 동일 값이며 `meta.json`에 기록합니다
- 대조군: 100만 건에서 **1GB로 올린 런 1회**를 추가합니다 — "메모리를 늘리면 해결되는 문제인가"에 답하기 위해서지, 운영 설정 후보가 아닙니다

### ⚠ 3-2b. t3.small은 버스트 인스턴스입니다 (로컬에서 재현 불가)

t3.small은 **CPU 크레딧** 기반입니다. baseline을 넘겨 지속적으로 CPU를 쓰면 크레딧이 소진되고 **성능이 baseline(vCPU당 20%)으로 throttle**됩니다.

- 로컬 맥북은 크레딧 개념이 없어 **이 열화를 재현할 수 없습니다**
- 즉 **로컬 부하 결과는 운영보다 낙관적**입니다. 특히 장시간 부하에서 격차가 벌어집니다
- 완화: 운영 판정이 필요하면 Grafana의 `CPUCreditBalance`를 별도로 봅니다. 이 실험의 결론은 **볼륨 간 상대 비교**로 한정합니다

### ⚠ 3-3. 콜드 / 웜

아웃박스 실험의 원칙을 그대로 씁니다 — **2회 실행, 2회차(웜) 기준**입니다.

- 안 지키면 첫 실행의 디스크 IO가 섞여 볼륨 효과로 오인됩니다
- k6는 별도 **워밍업 스테이지**(측정 제외)를 앞에 둡니다

### ⚠ 3-4. 증폭 데이터의 카디널리티 왜곡

`title`을 `"전시-1" … "전시-1000000"`처럼 만들면 실제 한글 전시명과 **선택도가 달라져** 옵티마이저가 다른 계획을 고릅니다. `like '%키워드%'` 경로가 특히 왜곡됩니다.

- 5장의 증폭 규칙으로 완화하되, **완전히 없앨 수는 없습니다**
- 결과에 "이 수치는 합성 데이터 기준"임을 명시합니다

### ⚠ 3-5. 통계 갱신 누락

대량 적재 후 옵티마이저 통계가 낡으면 `EXPLAIN`의 `rows`가 실제와 자릿수까지 어긋납니다.

- **모든 볼륨 전환 후 `ANALYZE TABLE`을 필수 단계로 넣습니다**

### ⚠ 3-6. 측정하지 않는 것

- 네트워크 지연(로컬이라 ~0) · CDN · 프론트 렌더링
- 쓰기 부하와의 상호작용(별도 실험) — 단, 상세 조회는 그 자체가 쓰기 트랜잭션이라 A에 자연히 포함됩니다

## ✅ 4. 채택 구성과 실행 순서

**D가 본체입니다.** A는 100만 지점에서 1회만 붙이고, B·C는 이번 범위에서 **제외**합니다.

| 순서 | 무엇 | 답하는 질문 | 산출물 |
| --- | --- | --- | --- |
| 1 | 볼륨 시드 (313 / 10만 / 50만 / 100만) | — | `meta.json` |
| 2 | 각 볼륨에서 **EXPLAIN + EXPLAIN ANALYZE** | **왜** 느린가 | `explain-*.txt` |
| 3 | **D: 반복 조회 스윕 (VU 1)** ← **본체** | 볼륨에 따라 p95·p99가 어떻게 변하나 | `single-*.json` |
| 4 | *(개선 후)* 2·3 재실행 | before/after | `compare.md` |
| 5 | **A: 10 VU — 100만에서 1회만** | 동시성이 붙어도 결론이 유지되나 | `k6-1m.json` |
| ~~6~~ | ~~B·C: 계단식~~ | **제외** — 용량 한계는 이번 목적이 아닙니다 | — |

### 🧠 왜 D를 본체로 올렸는가

조회속도 개선은 **쿼리 문제**이지 동시성 문제가 아닙니다. 그리고 p95·p99는 VU를 올려야만 얻는 값이 아닙니다 — **같은 경로를 N회 반복**해도 분포는 나옵니다.

| | D (VU 1 반복) | A (VU 10 부하) |
| --- | --- | --- |
| 분포의 변동 요인 | JIT · GC · **버퍼풀 히트/미스 · 디스크 IO** | 위 전부 + **큐잉 · 커넥션풀 · CPU 경합** |
| 볼륨 효과 | **선명하게 드러남** | 경합에 섞여 희석됨 |
| 표본 수 | **원하는 만큼**(경로당 500회) | 시간에 종속 |
| 재현성 | 높음 | 중간 |

> ✅ 볼륨 효과를 보려면 **변동 요인이 적을수록 좋습니다.** VU가 만드는 큐잉·경합은 이번 실험에서 **신호가 아니라 노이즈**입니다.
>
> 표본 수도 D가 유리합니다. 운영 실측이 n=38이라 p99가 무의미했던 것을 떠올리면, **경로당 500회를 마음대로 찍을 수 있다는 게 D의 큰 장점**입니다.

### ⚠ 그래도 A를 완전히 빼지 않는 이유 (100만에서 1회)

VU 1로는 **원리상 절대 안 보이는 것**이 둘 있습니다.

| 안 보이는 것 | 왜 중요한가 |
| --- | --- |
| **커넥션풀 포화** | HikariCP 기본 10입니다. 볼륨이 커져 쿼리가 500ms가 되면 `10 커넥션 ÷ 0.5초 = 20 req/s`가 천장이 됩니다. VU 1에서는 절대 나타나지 않습니다 |
| **조회수 UPDATE 락 경합** | [SQL 분석](전시_조회_SQL_분석.md)에서 "인기 전시에서 같은 행 경합"을 지적했습니다. **VU 1이면 경합이 0이라 그 지적이 영영 가설로 남습니다** |

그래서 **최악 볼륨(100만)에서 10 VU를 1회만** 돌립니다. 전 볼륨에 돌리지 않습니다 — 목적이 곡선이 아니라 **"동시성이 붙어도 D의 결론이 뒤집히지 않는다"는 확인 1회**이기 때문입니다.

### 🧪 실측: 기간 조건이 언제 붙고 언제 사라지는가

| 요청 | totalCount | `ongoingOn` 적용 |

| (필터 없음) `sort=latest` | **246** | ✅ 오늘 진행 중만 |


> 📉 **필터를 하나라도 걸면 기간 조건이 통째로 사라집니다.** `section=free`가 292건인 이유이고, 그 목록 상위가 전부 **아직 시작도 안 한 전시**인 이유입니다(정렬이 `start_date desc`라 미래가 위로 옵니다).
>
> 실험 설계 관점에서 중요한 것은 **필터 유무에 따라 스캔 대상 자체가 달라진다**는 점입니다. 필터를 건 쿼리가 오히려 **더 많은 행**을 봅니다(free 292 > 무필터 246).

### 🧪 실측: "정렬 안 함" = 최신순

`section=free&size=3`과 `section=free&sort=latest&size=3`의 결과가 **완전히 동일**했습니다. `canonicalSort(null)`이 `"latest"`를 돌려주기 때문입니다.

> ✅ 따라서 **"정렬 안 했을 때"는 별도 측정 대상이 아닙니다** — 최신순과 같은 쿼리입니다. 매트릭스에서 1칸을 아낍니다.

## 🌱 5. 시드 데이터셋 설계

### 🧱 원칙: 상상하지 않고 증폭합니다

운영 스냅샷(0장 분포표)이 이미 레포에 있으므로, **그 분포를 유지한 채 배수로 늘립니다.**

```
313건(로컬 시드 원본 = 운영 스냅샷)
  → ×320  = 10만
  → ×1600 = 50만
  → ×3200 = 100만
```

> ⚠ **로컬 baseline은 313건이고 운영은 402건입니다.** 시드 스냅샷을 뜬 시점 이후 운영에 89건이 더 쌓였습니다.
> 이 차이는 **보정하지 않습니다** — 89건 차이는 볼륨 축(10만~100만)에서 무의미하고, 억지로 맞추면 시드의 분포 충실도만 깨집니다.
> 대신 0장의 운영 실측(402건)과 로컬 baseline(313건)을 **다른 열로 나란히** 적어 혼동을 막습니다.

### 📋 그대로 유지하는 분포

| 항목 | 유지값 | 이유 |
| --- | --- | --- |
| 전시장 비율 | 전시 1.37건당 전시장 1개 | 목록의 장소 `IN` 크기를 좌우 |
| 상세 보유율 | 93.6% | 상세 조인 대상 비율 |
| 장르 보유율 | 100% | 상세 조회 경로 |
| 지역 분포 | SEOUL 37% · GYEONGGI 14% · … | 지역 필터 선택도 |
| 기간 분포 | 진행 중 **61%**(246/402) | `ongoingOn` 통과율 — 최신순 목록의 스캔량을 좌우 |
| 무료·진행 중 | **176건**(전체의 44%) | 정리 후 `section=free` 대상 — 홈 진입마다 count가 도는 조건 |
| 설명 보유율·길이 | 18% · 평균 1,046자 | 행 크기 → 버퍼풀 압력 |
| 좌표 보유율 | 99.6% | 거리순 정렬 대상 |

### 📋 의도적으로 이탈하는 분포 (근거 필수)

0장에서 드러난 **선택도 없는 세 필드**입니다. 그대로 두면 필터·정렬 성능을 측정할 수 없습니다.

| 항목 | 스냅샷 실측 | 시드 값 | 이유 |
| --- | --- | --- | --- |
| `category` | PAINTING 100% | **고른 분포 + PAINTING 우세** (예: PAINTING 40% · 나머지 8종 분할) | 스냅샷의 100%는 **그 시점 아티팩트**입니다. 실제 서비스는 고르되 회화가 많다는 것이 도메인 사실이라, 그쪽을 재현합니다 |
| `our_view_count` | 312/313이 0 | **분산 부여**(로그정규 근사) | 전량 0이면 `popular` 정렬이 `id desc`로 퇴화해 **정렬 자체를 측정 못 합니다** |
| `price` 무료 비율 | 79% | **70% 내외 유지** | 무료가 많은 것은 도메인 사실입니다. 선택도가 나쁜 것 자체가 측정 대상입니다(Stage 2의 "낮은 선택도" 사례) |

> 🧠 `category`는 **스냅샷을 그대로 믿지 않은 유일한 항목**입니다. 스냅샷은 100% PAINTING이지만 도메인 확인 결과 실제 분포는 고르며 회화가 우세합니다. 스냅샷이 곧 진실은 아니라는 예이고, 그래서 이 표에 근거를 남깁니다.

> ⚠ **이탈은 반드시 결과 문서에 명시합니다.** `our_view_count`를 분산시킨 상태의 `popular` 정렬 수치는 "운영에서 조회수가 쌓였을 때"의 예측치이지 현재 운영 재현이 아닙니다.

### 🧱 제목·자연키 생성 규칙

카디널리티 왜곡(3-4)을 줄이기 위한 규칙입니다.

- `title`: **원본 313개 한글 제목을 순환 재사용** + 구분 접미사. 순수 합성 문자열을 쓰지 않습니다 → `like '%키워드%'`의 매칭률을 실제에 가깝게 유지합니다
- `external_id`: `EXT-{n}` (UK 충돌 회피)
- `exhibition_place.place_key`: 원본 전시장명 순환 + 접미사, **1.37:1 비율 유지**
- 날짜: 원본 분포를 유지하되 ±N일 지터를 줘 동일값 뭉침을 방지합니다

### 🧱 적재 방식

아웃박스 실험(`01-setup.sql`)의 **곱집합 SELECT 대량 INSERT**를 그대로 씁니다. 재귀 CTE 없이 순수 SQL 한 방이라 빠르고 재현 가능합니다.

### 🗒 5. 북마크 볼륨 축 — 이번 범위에서 제외합니다

[SQL 분석](전시_조회_SQL_분석.md)에서 확인했듯 **관심 전시 목록은 LIMIT 없이 전량 로드**합니다. 그런데 이 경로가 반응하는 것은 전시 볼륨이 아니라 **사용자 1명당 북마크 수**입니다.

> 📉 전시를 100만 건 넣어도 **북마크가 1개면 그 경로는 안 터집니다.** 지금 설계엔 이 축이 빠져 있습니다.

**결정: 이번 실험에서는 다루지 않습니다.** 전시 볼륨과 직교하는 별개의 축이라 같이 넣으면 실험이 흐려집니다.

> ⚠ **다만 이 사실은 남겨 둡니다.** 이번 결과에 "관심 전시 목록은 안전하다"는 결론을 쓸 수 없습니다 — **측정하지 않았기 때문**입니다. 그 경로는 사용자당 북마크 수가 커질 때 별도 실험이 필요합니다.

### 🗒 6. 100만 건의 성격 — 의도적 극단으로 명시합니다

현재 402건이고 공공데이터 수집 페이스를 감안하면 100만은 **자연 증가로는 도달하지 않는 수치**입니다. 그래도 넣는다면 성격을 명시해야 합니다.

| 볼륨 | 성격 |
| --- | --- |
| 10만 | 전국 확대·다년 누적의 **현실적 상한** |
| 50만 | 여유 마진 |
| 100만 | **의도적 극단** — "언제 무너지는가"의 답을 얻기 위한 지점이지 예측치가 아님 |

**결정: 이 표를 결과 문서에 그대로 싣습니다.** 안 적으면 "100만 건에서 느림"이 임박한 위험처럼 읽힙니다.

## 🧑‍🤝‍🧑 11. VU를 왜 두는가

> 💬 "VU 수는 왜 필요한 거야?"

**VU(Virtual User)** 는 k6가 만드는 가상 사용자 1명입니다. 각 VU는 독립된 워커로 `요청 → 응답 대기 → 다음 요청` 루프를 돕니다. VU 50이면 **항상 50개 요청이 동시에 앱에 물려 있는** 상태입니다.

### 🧱 왜 필요한가 — 혼자 재면 안 보이는 것

단일 요청 지연과 부하 중 지연은 다릅니다.

```
VU 1  : [요청]────[응답 50ms]              → 순수 처리 시간
VU 50 : [요청]──[큐 대기]──[처리]──[응답]   → 대기가 붙는다
                  ↑ 커넥션풀·스레드·CPU를 두고 경합
```

혼자 치면 **커넥션풀 포화, 스레드 경합, 락 대기, CPU 큐잉이 전혀 나타나지 않습니다.** p95·p99는 본래 "동시에 여러 명이 있을 때 꼬리가 얼마나 두꺼운가"를 보는 지표라 VU 없이는 의미가 없습니다.

상세 조회처럼 **조회수 UPDATE가 붙은 경로**는 특히 그렇습니다. 혼자 치면 락 경합이 0이지만, 같은 인기 전시를 여러 명이 동시에 보면 같은 행에 UPDATE가 몰립니다. 이건 VU를 올려야만 보입니다.

### 🎯 그런데 우리는 VU를 **낮게** 씁니다 (10 VU)

목적이 볼륨 축이기 때문입니다. VU를 올리면 CPU 포화가 쿼리 비용을 덮어써서 **볼륨 효과가 오히려 안 보입니다**(1장).

근거 셋:

| 근거 | 내용 |
| --- | --- |
| 실사용 규모 | 가입자 **20명**, API 누적 20,336건. 동시 50명은 현실의 수십 배입니다 |
| 운영 스펙 | **t3.small 2 vCPU**에 전체 스택. 기존 "100 VU 운영점"은 **맥북 기준**이라 운영에 그대로 적용되지 않습니다 |
| 실험 목적 | 볼륨만 변수로 두려면 나머지는 **작고 일정해야** 합니다 |

### ✅ 최종 결정 — VU는 본체에서 빠집니다

**본체는 D(VU 1 반복 조회)이고, p95·p99도 거기서 뽑습니다.** VU 10은 **100만 지점에서 1회만** 붙입니다(4장).

| | 쓰나 | 왜 |
| --- | --- | --- |
| VU 1 반복(D) | ✅ 전 볼륨 | 볼륨 효과가 가장 선명. 표본을 원하는 만큼 확보 |
| VU 10(A) | 100만에서 **1회만** | 커넥션풀 포화·UPDATE 락 경합은 VU 1로 **원리상 못 봅니다** |
| VU 램핑(B·C) | ❌ 제외 | 용량 한계는 이번 목적이 아닙니다 |

> 🧠 이 실험에서 VU는 **재는 대상이 아니라 통제 변수**입니다. "몇 명까지 버티나"가 필요해지면 그때 별도 실험으로 C를 돌립니다.
