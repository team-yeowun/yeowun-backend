### 1-1. 이 문서의 ms는 **서버 사이드 응답시간**입니다 (SQL 쿼리 시간이 아닙니다)

| 계층 | 무엇을 재나 | 어디에 나오나 |
| --- | --- | --- |
| **① API 요청** ⭐ | k6 `http_req_duration` = `sending + waiting(TTFB) + receiving`.<br>컨트롤러·파사드·**그 요청이 날리는 SQL 전부**·JSON 직렬화·응답 전송을 포함하고, **연결 수립(`blocked`·`connecting`·TLS 핸드셰이크)은 제외**합니다(keep-alive라 대부분 0) | **2·3·4장 대부분.** 별도 표기가 없으면 전부 이것 |
| **② 순수 지연(API, VU 1)** | 같은 ①인데 동시 요청이 없어 **큐 대기가 0** | 3-1의 R1 열, 5-3 |
| **③ 순수 SQL** | MySQL 안에서 **쿼리 1개**만 잰 값 | 3-2의 `EXPLAIN ANALYZE`, 1-2 표 |

#### ①이 정말 "서버 처리 시간"인가 — 교차검증 ✅

k6가 잰 값과 **앱이 스스로 잰 값**(Micrometer `http_server_requests`, 서블릿 안쪽)을 같은 런에서 비교했습니다(10만 볼륨, 런 전후 프로메테우스 덤프 차분):

| 엔드포인트 | 서버측 평균 | k6측 평균 | 차이 |
| --- | ---: | ---: | ---: |
| `/api/v1/exhibitions` | 671.0ms | 671.9ms | **+0.9ms** |
| `/api/v1/exhibitions/banners` | 7.4ms | 8.2ms | **+0.8ms** |
| `/api/v1/exhibitions/region-groups` | 0.9ms | 1.8ms | **+0.8ms** |

**차이가 크기와 무관하게 일정한 +0.8~0.9ms**입니다(671ms짜리에도, 8ms짜리에도 같은 값). 지연에 비례해 늘지 않으므로 루프백 전송과 서블릿 바깥 처리에 해당하는 **고정 비용**입니다.

> ✅ 그래서 **① 값은 사실상 서버 처리 시간으로 읽어도 됩니다.**
> ⚠ 다만 **새 클라이언트가 처음 붙을 때의 연결 수립 비용은 이 숫자에 없습니다.** 실제로 `curl`로 한 건씩 치면(프로세스 시작 + TCP 연결 포함) 100만에서 상세가 23~47ms로 나옵니다 — k6 기준 13ms에 그 비용이 얹힌 값입니다. **실사용 체감은 ①보다 조금 더 큽니다.**

### 1-2. 목록 1요청은 **SQL 5개**입니다

```
GET /api/v1/exhibitions?sort=latest&size=20
  ├ count(*)            ← findAll(spec, Pageable)이 만들고 그냥 버리는 count
  ├ slice (LIMIT 21)
  ├ count(*)            ← totalCount용
  ├ 전시장 배치 조회 (IN …)   ← 조립
  └ 가격 배치 조회 (IN …)     ← 조립
```

10만 볼륨에서 쿼리를 하나씩 떼어 재면(③ 계층, warm):

| 쿼리 | ③ 순수 SQL |
| --- | ---: |
| `count(latest)` | 123ms |
| `slice(latest)` | 161ms |
| `slice(ending)` | 159ms |
| **`slice(popular)`** | **≈ 0ms** |
| `count(free)` | 225ms |
| `count(region=SEOUL)` | 184ms |

`count 123 × 2 + slice 161 = 407ms`이고 같은 조건의 **② 값이 457ms**입니다 →
**API 지연의 약 89%가 이 세 쿼리**이고, 나머지 11%가 조립 2회 + 직렬화 + 전송입니다.

> ⚠ `count(*)`에는 `LIMIT`이 없습니다. **`size=2`인 홈 섹션도 2건을 보여주려고 50만 행을 셉니다.**
> 그리고 지금 코드는 count가 **2번** 나갑니다(하나는 만들어놓고 버립니다). 이를 1번으로 줄이는 커밋 `459ae28`은 **이번 측정에 포함되지 않았습니다.**

## 3. 왜 그런가 — 발견 5개

### 3-1. 🥇 범인은 `count(*)`다

> **`totalCount`를 부르지 않는 경로만 평평했습니다. 정렬·필터는 그다음 문제입니다.**

| 경로 | `count` | 313 | 100만 | 배율 |
| --- | :---: | ---: | ---: | ---: |
| 배너 (`limit 3` 전용 쿼리) | ❌ | 6ms | **11ms** | **1.8×** |
| 상세 (PK 조회 묶음) | ❌ | 12ms | **13ms** | **1.0×** |
| 인기순 목록 | ✅ ×2 | 11ms | 5,382ms | 502× |
| 최신순 목록 | ✅ ×2 | 12ms | 8,890ms | 768× |
| 무료 목록 | ✅ ×2 | 12ms | 15,181ms | 1,229× |

**상세는 조회수 `UPDATE`가 붙은 쓰기 트랜잭션인데도 100만에서 112 req/s**입니다. 같은 볼륨의 목록이 0.2 req/s이니 **560배** 차이입니다. 6테이블을 왕복하지만 전부 PK·UK 조회라 볼륨과 무관합니다.

> 🧠 **"조인이 많아서 느리다"가 아닙니다.** 상세는 조인이 가장 많은데 가장 빠릅니다. **읽는 행 수가 고정이냐 아니냐**가 전부입니다.

### 3-2. 정렬 — 인기순만 인덱스 정렬을 탄다

> **인기순이 최신순보다 1.65배 빠르고, 그 비율은 볼륨이 커져도 그대로입니다.**

| 볼륨 | 최신순 | 종료순 | 인기순 | **최신순 ÷ 인기순** |
| --- | ---: | ---: | ---: | ---: |
| 313 | 12 | 11 | 11 | 1.09× |
| 10만 | 590 | 594 | 359 | **1.64×** |
| 50만 | 4,411 | 4,436 | 2,666 | **1.65×** |
| 100만 | 8,890 | 8,730 | 5,382 | **1.65×** |

#### EXPLAIN이 이유를 보여줍니다 (100만)

| 경로 | 잡은 인덱스 | 추정 rows | Extra |
| --- | --- | ---: | --- |
| **최신순** | `idx_exhibitions_type_owner` | 465,384 | **Using filesort** |
| **종료순** | `idx_exhibitions_type_owner` | 465,384 | **Using filesort** |
| **인기순** | `idx_exhibitions_view_count` | **42** | **Backward index scan** |
| **배너** | `idx_exhibitions_view_count` | **6** | **Backward index scan** |

`EXPLAIN ANALYZE` 실측(종료순, 100만):

```
-> Limit: 21 row(s)                                    (actual time=2171..2171 rows=21)
-> Sort: e.end_date, e.id, limit input to 21 row(s)     (actual time=2171..2171 rows=21)
-> Filter: (deleted_at is null) and (start_date <= curdate()) and (end_date >= curdate())
-> Index lookup on e using idx_exhibitions_type_owner (type='CATALOG')
                         (cost=55834 rows=465384) (actual time=0.713..1959 rows=1e+6)
```

**`rows=1e+6` — 21건을 돌려주려고 100만 행을 전부 읽습니다.** `type='CATALOG'`가 전체 행의 **100%** 라 이 인덱스는 사실상 풀스캔이고, 그 위에 filesort가 얹힙니다.

> ⚠ **설계 문서의 가설을 정정합니다.**
> 설계 문서: *"종료순만 `idx_exhibitions_dates`의 2번째 컬럼(선두 불일치)이라 불리하고, 최신순은 선두 일치"*
> **실측: 최신순도 `idx_exhibitions_dates`를 아예 못 씁니다.** `(start_date IS NULL OR start_date <= ?)` 형태의 OR가 range 조건이 되지 못해 옵티마이저가 이 인덱스를 버리고 선택도 0인 type 인덱스를 잡습니다. 그래서 최신순(8,890)과 종료순(8,730)의 실측이 같았습니다.

> 🧠 **계층에 따라 답이 달라지는 지점입니다.**
> ③ 순수 SQL로 보면 최신순 161ms vs **인기순 ≈0ms**로 격차가 비교 불가입니다.
> ① API로 보면 1.65배로 줄어듭니다 — **양쪽에 똑같이 붙는 count 2번(246ms)이 격차를 희석**하기 때문입니다.
> 그래서 **count를 먼저 없애야 인덱스 개선이 체감으로 드러납니다.** ([4장 우선순위의 근거](#4-그래서-뭘-해야-하나))

### 3-3. 커서 페이지네이션은 정상이다 — 손대지 마세요

| --- | ---: | ---: | ---: | ---: | ---: |
| 10만 | 590 | 601 | 594 | 603 | **1.02×** |
| 50만 | 4,411 | 4,329 | 4,393 | 4,483 | **1.02×** |
| 100만 | 8,890 | 9,262 | 8,492 | 8,799 | **0.99×** |

키셋은 이미 O(1)입니다. 2-4의 스크롤 시나리오에서 페이지마다 지연이 균일한 것도 같은 증거입니다.
(313 볼륨은 진행 중이 208건뿐이라 50p·100p가 물리적으로 존재하지 않아 `N/A`입니다.)

### 3-4. 필터 선택도·검색 매칭 수는 성능과 무관하다

> **결과가 10분의 1인 제주가 서울보다 오히려 느립니다.**

| 볼륨 | 서울(23만건) | 제주(2.3만건) | 제주 ÷ 서울 |
| --- | ---: | ---: | ---: |
| 10만 | 774 | 788 | 1.02× |
| 50만 | 5,633 | 5,997 | 1.06× |
| 100만 | 11,746 | **12,828** | **1.09×** |

`exhibition_place.region`에 인덱스가 없어 서브쿼리가 전시장 **73만 행을 통째로** 훑습니다. 몇 건이 걸리든 읽는 양은 같습니다.

검색도 마찬가지입니다:

| 볼륨 | 고빈도 `미술` | 희소 `사진` | 매칭 수 비 |
| --- | ---: | ---: | ---: |
| 10만 | 955 | **1,012** | 28,937 : 320 (**90배**) |
| 50만 | 5,891 | 5,378 | 144,473 : 1,598 |
| 100만 | 12,088 | 9,989 | 288,885 : 3,195 |

매칭이 90배 적은 검색어가 10만에서는 **오히려 더 느렸습니다.** `lower(title) like '%k%'`는 인덱스를 원리상 못 쓰므로 비용이 매칭 수가 아니라 **스캔 대상 전체**에 비례합니다.

#### 섹션 × 정렬 매트릭스 (100만 p50, ms)

| | 최신순 | 종료순 | 인기순 |
| --- | ---: | ---: | ---: |
| 곧 끝남 | 8,903 | 9,399 | **5,779** |
| 이번 달 개막 | 9,259 | 8,791 | **5,639** |
| **무료** | **15,424** | **15,226** | **11,238** |

행 방향(섹션)이 열 방향(정렬)보다 영향이 큽니다. **무료 행이 다른 두 행의 1.7배**입니다 — `exhibition_detail`(100만 행, `price` 인덱스 없음) 서브쿼리가 count 안에서 돌기 때문입니다.
사전 예상은 "무료 × 종료순이 최악"이었지만 실제로는 **무료 × 최신순과 사실상 동률**입니다(15,424 vs 15,226). 다시 한 번, 정렬이 아니라 필터가 지배합니다.

### 3-5. 거리순은 100만에서 무너진다

## 5. 이 숫자를 믿어도 되는가

### 5-1. 오염 판정 — 이 런은 깨끗합니다 ✅

DB를 타지 않는 `region-groups`(대조군)를 전 볼륨에서 함께 쟀습니다. 볼륨이 늘어도 평평해야 하고, 평평하지 않으면 그 런은 CPU 포화·k6 자체 오염이 있었다는 뜻입니다.

| 볼륨 | 대조군 p50 | 대조군 p95 | R2 실패 요청 | 판정 |
| --- | ---: | ---: | ---: | :---: |
| 313 | 1 | 1 | 0 | ✅ |
| 10만 | 1 | 4 | 0 | ✅ |
| 50만 | 2 | 4 | 0 | ✅ |

전 볼륨 1~2ms로 평평하고 실패 요청도 0건입니다(100만 거리순 제외 — 그건 [3-5]의 측정 결과 자체입니다).

### 5-2. 표본 수 — p99는 못 냈습니다

| 티어 | 313 | 10만 | 50만 | 100만 |
| --- | ---: | ---: | ---: | ---: |
| 티어1 8경로 | 200 | 120 | 42~54 | 30 |
| 티어2 18경로 | 80 | 40 | 12~19 | 10 |

- **p99 없음**: 100만에서 티어1 표본이 30이라 p99는 상위 0.3건입니다. 이 하드웨어(MySQL 2 vCPU, 100만에서 0.2 req/s)에서 p99에 필요한 표본(경로당 ≥2,000)을 채우려면 **볼륨당 3시간 이상**이 듭니다.
- **50만 R2는 부분 완주**(목표의 약 82%, 외부 종료). **중앙값은 유효하지만 p95는 참고치**입니다.
- p50은 전 구간 신뢰할 만합니다. 곡선의 형태(배율·비율)를 읽는 데는 충분합니다.

### 5-3. 큐 대기가 차지한 몫

동시 2로 쟀으므로 ① 값에는 큐 대기가 섞여 있습니다. VU 1(②)과 비교하면:

| 볼륨 | ② 순수 지연 | ① 동시 2 | 큐 대기 몫 |
| --- | ---: | ---: | ---: |
| 10만 | 457 | 590 | +29% |
| 50만 | 2,851 | 4,411 | +55% |
| 100만 | 5,802 | 8,890 | +53% |

**순수 쿼리 비용을 보려면 [부록 B](#부록-b-전체-데이터)의 R1 표를 보세요.** 결론(어느 경로가 평평하고 어느 경로가 초선형인가)은 두 계층에서 동일합니다.

### 5-4. 인용할 때 반드시 함께 적을 것

- [x] **모든 수치는 서버 사이드 응답시간**입니다 — 클라이언트 연결 수립·렌더링은 빠져 있으므로 **사용자 체감은 이보다 큽니다**
- [x] **100만은 의도적 극단**입니다. 운영 402건이고 자연 증가로 도달하는 수치가 아닙니다 — "언제 무너지는가"를 보려는 지점입니다

- [x] Docker VM이 **2 vCPU**라 MySQL이 병목입니다. **볼륨 간 상대 비교**로만 읽으세요 — 절대값을 운영에 대입하지 마세요
- [x] 운영 t3.small은 **버스트 인스턴스(CPU 크레딧)** 라 로컬 결과가 오히려 **낙관적**일 수 있습니다
- [x] **합성 데이터**입니다 — 원본 313건의 한글 제목을 순환 재사용했고, `our_view_count`만 인위적으로 분산시켰습니다
- [x] 그래서 **인기순 수치는 "조회수가 쌓였을 때"의 예측치**이지 현재 운영 재현이 아닙니다
- [x] **중복 count 제거 커밋이 미포함**된 코드의 측정입니다 — 반영하면 목록 경로가 개선됩니다
- [x] **관심 전시 목록은 측정하지 않았으므로 "안전하다"고 쓸 수 없습니다**(볼륨 축이 전시 수가 아니라 유저당 북마크 수)
- [x] 홈 4경로는 파라미터가 고정이라 **웜 조건 수치**입니다
- [x] `N/A`·`ABORT`·부분 완주를 표에서 지우지 않았습니다

### 측정 중 밟은 함정 (재실행 시 주의)

- **커서 구분자는 공백이 아니라 NUL(`\0`)입니다**(`Cursor.java:25`). 공백으로 만들면 전 요청이 400 `INVALID_CURSOR`인데 응답이 5ms라 **"커서가 압도적으로 빠르다"로 오독**하게 됩니다. 이 실험도 처음엔 이 상태로 돌아 313·10만을 폐기하고 재측정했습니다.
- **`GROUP_CONCAT` 기본 상한 1024바이트** — 안 올리면 id 풀이 5,000개가 아니라 172개가 됩니다.
- **외부를 부르는 `curl`에 `--max-time` 필수** — 거리순 OOM 뒤 앱 actuator가 응답하지 않아 타임아웃 없는 `curl`이 1시간 26분을 잡아먹었습니다.
- **k6 요청에 `tags: {path: id}` 필수** — 없으면 커서·id가 섞인 URL이 서로 다른 메트릭으로 집계돼 경로별 p95가 산산조각 납니다.
