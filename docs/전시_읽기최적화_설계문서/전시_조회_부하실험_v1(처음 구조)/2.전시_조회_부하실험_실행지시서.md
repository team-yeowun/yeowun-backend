## ⚙️ 2. 측정 조건 — 얼마나 세게, 몇 번 칠 것인가

### 📌 동시성은 **10 VU**입니다 (50이 아닙니다)

| | 값 | 왜 |
| --- | --- | --- |
| **본체 부하** | **10 VU** | 실사용 규모(가입자 20명)의 수 배. 운영은 **t3.small 2 vCPU**에 전체 스택이라 그 이상은 현실이 아닙니다 |
| 보조 측정 | 1 VU | 큐잉·경합이 0인 **순수 쿼리 시간**. `EXPLAIN` 옆에 붙는 열 |
| 거리순만 | 1 VU | 한 요청이 수십 초라 다른 경로의 큐잉을 오염시킵니다 → **격리** |

> 🧠 **VU 1만 쓰면 안 됩니다** — p95/p99의 꼬리에는 큐잉·커넥션풀 대기가 포함되어야 하는데 VU 1에서는 그게 원리상 0입니다.
> 반대로 **너무 올리면 CPU 포화가 쿼리 비용을 덮어써서**, p95가 올라가도 인덱스 탓인지 CPU 경합 탓인지 구분할 수 없게 됩니다. **10은 "경합이 보이되 포화는 아닌" 출발점**입니다.

### 📌 VU를 올려 시간을 줄이려면 — 캘리브레이션 런으로 판정합니다

로컬(M-series 10코어 · 32GB)은 운영(t3.small 2 vCPU · 2GB)보다 여유가 큽니다. **10 VU는 로컬 CPU를 다 쓰지 못할 가능성이 높고**, 그렇다면 VU를 올려 총 시간을 줄일 수 있습니다. 다만 **추측하지 말고 재서 정합니다.**

#### 🧠 풀과 VU는 다른 것입니다

**동시에 도는 쿼리 수를 정하는 건 VU이고, 풀은 그 천장일 뿐입니다.**

| 조합 | 실제 동시 쿼리 | 판정 |
| --- | ---: | --- |
| 풀 50 · VU 30 | **30** | ✅ 안전. 풀은 남는 여유일 뿐 |
| 풀 10 · VU 30 | **10** | ❌ 풀이 천장이라 늘린 VU 20이 전부 큐 대기 |
| 풀 50 · VU 50 | **50** | ⚠ 위험 — 아래 상한 참조 |

> 따라서 **풀은 50으로 넉넉히 고정하고, 실험 전 구간에서 바꾸지 않습니다.** VU만 캘리브레이션으로 정합니다.
> 이러면 앱 재기동이 3번 → **1번**으로 줄고, 풀이 변수에서 완전히 빠져 **VU 하나만 남습니다.**
> 풀 크기는 VU를 넘는 한 성능에 중립입니다 — 안 쓰는 커넥션은 비용이 없습니다.

#### 캘리브레이션 런 (10만 볼륨에서 1회, 약 5분)

```yaml
# compose.yaml · app.environment — 실험 구간 고정값
- 'SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE=${HIKARI_MAX:-50}'
- 'SPRING_DATASOURCE_HIKARI_MINIMUM_IDLE=10'   # 유휴 커넥션 50개 상시 점유 방지
```

풀 50으로 **한 번만** 띄워 두고, VU만 바꿔가며 k6를 3번 돌립니다(앱 재기동 없음).

| 단계 | VU | 풀 | 요청 |
| --- | ---: | ---: | ---: |
| C1 | 10 | 50 | 3,000 |
| C2 | 20 | 50 | 3,000 |
| C3 | 30 | 50 | 3,000 |

```bash
HIKARI_MAX=50 docker compose --profile app up -d --force-recreate app
for v in 10 20 30; do k6 run -e VUS=$v loadtest/k6/calibrate.js; done
```

각 단계 = **워밍업 200 → 측정 3,000**(26경로 균등). 단계 사이에 30초 idle.

| 볼 것 | 판정 |
| --- | --- |
| **처리량(req/s)** | VU 배수의 **70% 이상** 오르면 여유 있음. 그 아래면 이미 포화 — 올려도 시간이 안 준다 |
| **Z1(대조군) p95** | DB를 안 타는 경로다. **10% 이상 오르면 CPU 포화 신호** — 여기가 상한선 |
| `hikaricp_connections_pending` | 0에 가까워야 한다. 쌓이면 풀이 천장(= VU만 올린 셈) |
| `docker stats` CPU | k6·앱·MySQL 합이 코어 수를 넘기 시작하면 측정 도구가 측정 대상을 방해하는 구간 |

> ⛔ **VU 상한은 30입니다**(풀이 아니라 VU). `section=free`의 `IN (서브쿼리)`는 100만 볼륨에서 `exhibition_detail` 93.6만 행을 **임시 테이블로 구체화**할 수 있고, `sort=ending`은 전량 filesort입니다. **동시 쿼리 50개가 디스크 임시 파일을 함께 쓰면 쿼리 비용이 아니라 디스크 스래싱을 재게 됩니다.**
> 연결 수 자체는 문제가 아닙니다 — MySQL 8.4 `max_connections` 기본값이 151이라 풀 50은 여유롭습니다.

> 🧠 **Tomcat 스레드풀(기본 200)은 건드리지 않습니다.** 30 VU에서 여유가 넘칩니다. 병목 후보는 커넥션풀 쪽입니다.

**채택 조건 4가지** — 이걸 다 지키면 VU를 올려도 됩니다.

1. **전 볼륨에 동일한 VU·풀**을 적용한다(하나라도 다르면 볼륨 비교가 깨진다)
2. **풀은 50 고정**이라 어느 단계에서도 천장이 되지 않는다 — 늘린 VU가 큐 대기로 새지 않는다
3. 결과를 **"동시 N 조건의 p95"** 로 라벨한다. 운영 예측치가 아니다
4. **Z1이 볼륨에 따라 평평한지** 매 런 확인한다. 흔들리면 그 런은 오염이다

> ⚠ 캘리브레이션은 10만에서 하지만 **포화는 100만에서 먼저 옵니다**(IO 압력이 다르므로). 100만에서 Z1이 깨지면 조건 1 때문에 **전 볼륨을 다시 돌려야 합니다.** 그러니 경계선에 걸치면 **한 단계 보수적으로** 고르세요.

### 📌 표본 수 — 경로별로 목표치를 정해 놓고 정확히 채웁니다

p99는 상위 1%입니다. n=400이면 **p99가 샘플 4개**라 GC 한 번에 값이 바뀝니다.

| 티어 | 경로 (개수) | 볼륨당 샘플/경로 | 보고 |
| --- | --- | ---: | --- |
| **1** | H2 · H4 · S1 · S2 · S3 · X8 · K1 · D100 (8개) | **2,000** | **p95 + p99** |
| **1** | V1 (상세, 별도 런) | **2,000** | **p95 + p99** |
| **2** | 나머지 18개 | **400** | **p95만** (p99는 "n=400 참고치" 표기) |
| 특수 | S4 (거리순, 격리 런) | **50** | 완주 여부 · 실패 사유 |
| 시나리오 | SC2 (탐색 스크롤) | **300** | 화면 단위 p95 |

### 📌 볼륨 축과 통제 변수

- 볼륨: **313 → 10만 → 50만 → 100만** (오름차순, 증분 적재)
- `innodb_buffer_pool_size = 128M` 고정 — t3.small(RAM 2GB) 재현. **100만에서 1GB 대조군 1회 추가**
- 볼륨 전환마다 `ANALYZE TABLE` 필수
- 워밍업(측정 제외) 후 **측정 1회**. 워밍업과 측정은 **다른 난수 시드**를 씁니다
- 실행 중 다른 작업 금지(빌드·테스트·브라우저) — 단일 호스트라 CPU를 뺏깁니다

### 📌 판정선 (측정 전에 못 박습니다)

```
목록 p95 ≤ 300ms   ·   상세 p95 ≤ 500ms   (로컬 128MB 버퍼풀 기준)
```
> 사후에 정하면 나온 숫자에 맞춰 기준이 움직입니다.

### 📌 측정 지점은 2중

| 어디서 | 무엇 | 왜 |
| --- | --- | --- |
| k6 | `http_req_duration` p95/p99 | 클라이언트 관점(연결·큐잉 포함) |
| `/actuator/prometheus` | `http_server_requests` · `hikaricp_connections_pending` · `hikaricp_connections_acquire_seconds` | 쿼리 지연과 **풀 대기**를 갈라내기 위해 |

런 시작·종료 시점에 프로메테우스를 덤프해 함께 저장합니다.

## 📖 4. 용어 3개 — 정렬 · 필터 · 기간 조건

### 🧱 정렬 4종

| 코드 | 사람 말 | 실제 ORDER BY | 인덱스 |
| --- | --- | --- | --- |
| `latest` | **최신순** (기본값) | `start_date desc, id desc` | `idx_exhibitions_dates` **선두 일치** ✅ |
| `ending` | **종료순** (곧 끝나는 순) | `end_date asc, id asc` | 같은 인덱스의 **2번째 컬럼** → 못 씀 ❌ |
| `popular` | **인기순** | `our_view_count desc, id desc` | `idx_exhibitions_view_count` **선두 일치** ✅ |
| `distance` | **거리순** | **DB가 정렬 안 함** — 전량 로드 후 앱에서 계산 | 없음 ❌ |

> `sort`를 안 보내면 `latest`(최신순)입니다. "정렬 안 함 = 최신순"이라 별도 경로가 아닙니다.

### 🧱 필터 축 3종

| 축 | 값 | 어디에 걸리나 |
| --- | --- | --- |
| **섹션**(`section`) | 곧 끝남 / 이번 달 개막 / 무료 | 날짜 창 또는 `exhibition_detail` 서브쿼리 |
| **지역·분류**(`region`·`category`) | SEOUL·JEJU… / PAINTING… | `exhibition_place` 서브쿼리 / `exhibitions.category IN` |
| **검색**(`keyword`) | 한글 토큰 | `title like '%k%'` **또는** 전시장명 서브쿼리 |

### 🧱 기간 조건 — 요청마다 다르게 붙습니다

`ExhibitionSearchQueryFactory.resolveOngoingOn()`이 결정합니다. **경로마다 스캔 모집단이 달라지는 원인**입니다.

```java
if (date != null)     return date;                                     // 지정일 진행 중
if (section != null)  return section.requiresOngoing() ? today : null;  // 곧끝남·무료만 today
if (keyword != null)  return null;                                     // 대신 notEndedOn=today
return today;                                                           // 지역·분류·무필터는 today 유지
```

| 붙는 조건 | 뜻 | 어느 경로에 |
| --- | --- | --- |
| `ongoingOn = today` | **오늘 진행 중**(시작 ≤ 오늘 ≤ 종료) | 무필터 · 지역 · 분류 · 곧끝남 · 무료 |
| (없음) | 미래·과거 전시 포함 | **이번 달 개막** |
| `notEndedOn = today` | 아직 안 끝남(**미래 전시 포함**, 종료만 제외) | **검색** |

## ✂️ 5. 경로 선정 원칙 — 전수 조합하지 않는 기준

목록 API 파라미터는 `keyword · section · period · region · category · date · sort · lat/lng · cursor · size` + 로그인 여부입니다.
전수 조합은 `4(sort) × 4(section) × 2(keyword) × 19(region) × 9(category) × 4(커서깊이)` = **수만 개**. 불가능하고 불필요합니다.

**기준은 하나 — 이 축이 실행계획의 *모양*을 바꾸는가, *상수*만 바꾸는가.**

| 파라미터 | 계획을 바꾸나 | 처리 |
| --- | --- | --- |
| `sort` | ✅ ORDER BY 컬럼과 인덱스 사용 여부가 통째로 달라짐 | **경로로 분리** (4종) |
| `section` | ✅ free는 서브쿼리, 나머지는 날짜 BETWEEN. 기간 조건 유무까지 달라짐 | **경로로 분리** (3종 + 없음) |
| `keyword` | ✅ `like '%k%'`(인덱스 불가) ×2 + `notEndedOn` 추가 | **경로로 분리**, 값은 매칭률 대역별 고정 |
| `region` | ✅ `exhibition_place` 서브쿼리가 통째로 추가 | **경로로 분리**, 값은 선택도별 고정 |
| `category` | △ 약하게 — `category IN (…)`, 인덱스 없음 | 경로 1개(최신순에만) |
| `cursor` 깊이 | ✅ 키셋 경계가 붙고 읽는 위치가 달라짐 | **깊이별 경로** (10·50·100p) |
| `date` | ❌ 상수만 — `ongoingOn`이 오늘→지정일로 바뀔 뿐 | 제외 |
| `period=week` | ❌ 상수만 — 날짜창 폭만 | 제외 |
| `size` | ❌ 슬라이스 크기만. **count는 size와 무관하게 전체를 센다** | 탐색 20 고정 / 홈은 실제값(2·5) |
| `lat/lng` | ❌ 전량 로드라 좌표값 무관 | 실제 전시장 근방 지터만 |
| 로그인 여부 | ❌ 목록은 항상 `type=CATALOG` 강제라 계획 동일. 북마크 배치 조회 1개만 추가(페이지 크기 비례, **볼륨 무관**) | **비로그인 고정** |

### ⚠ 랜덤화 규칙

랜덤화의 목적은 **버퍼풀이 100% 웜이 되는 걸 막는 것**입니다. **계획이 갈리는 값을 섞으라는 뜻이 아닙니다.**
SEOUL(37%)과 JEJU(희소)를 한 경로에 섞으면 선택도가 자릿수로 달라 **p95가 이중봉이 되어 해석 불가**가 됩니다.

| | 랜덤화 | 고정 분리 |
| --- | :---: | :---: |
| 커서 위치(같은 깊이 대역 안에서) | ✅ | |
| 상세 `exhibitionId` | ✅ | |
| 거리순 좌표 지터 | ✅ | |
| `region` 값 | ❌ | ✅ 고빈도 1종 · 희소 1종을 **다른 경로**로 |
| `keyword` 토큰 | ❌ | ✅ 매칭률 대역별 2종을 **다른 경로**로 |
| `category` 값 | ❌ | ✅ 1종 고정 |

## 🗂 6. 인덱스 현황 — 경로 선정의 근거

```
exhibitions
  PRIMARY (id)
  uk_exhibitions_external_id (external_id)
  idx_exhibitions_type_owner (type, owner_id)
  idx_exhibitions_dates (start_date, end_date)
  idx_exhibitions_exhibition_place_id (exhibition_place_id)
  idx_exhibitions_view_count (our_view_count)

exhibition_place   PRIMARY(id) · uk_exhibition_place_place_key(place_key)   ← region 인덱스 없음
exhibition_detail  PRIMARY(id) · uk_exhibition_detail_exhibition_id         ← price 인덱스 없음
```

| 경로 | 인덱스 상황 | 볼륨 반응 예상 |
| --- | --- | --- |
| **최신순** | `idx_dates` 선두 일치 ✅. 단 인덱스가 `(start_date, end_date, id)`라 **id가 인접하지 않아** 동률 구간 filesort 여지 | 완만 |
| **종료순** | `end_date`는 **2번째 컬럼** → 정렬에 못 씀 → **전량 filesort** | 급격 (**의심 1순위**) |
| **인기순** | `idx_view_count` + InnoDB가 PK를 붙여 사실상 `(our_view_count, id)` → ORDER BY 그대로 사용 ✅ | 완만 (**대조군**) |
| **거리순** | DB 정렬 없음. `searchAll` 전량 로드 + 앱 정렬 | **선형, 100만에서 붕괴** |
| `section=free` | `exhibition_detail.price` 인덱스 없음 → 서브쿼리가 detail **전체 스캔**(1M 볼륨 = 93.6만 행) | 급격 |
| `region=…` | `exhibition_place.region` 인덱스 없음 → place **전체 스캔**(73만 행) | 급격 |
| `keyword=…` | `like '%k%'` 인덱스 원리상 불가 ×2(전시명 + 전시장명 서브쿼리) | 급격 |
| `type=CATALOG` (항상 붙음) | `idx_type_owner` 선두지만 **100% CATALOG라 선택도 0** → 사실상 무용 | — |
| `/banners` | 진행 중 필터(`idx_dates`) vs `order by our_view_count desc`(`idx_view_count`) — **인덱스를 하나만 고를 수 있다** | 급격 가능 |

> 🧠 **인덱스가 없는 축(region · price · keyword)과 정렬 축(종료순 vs 인기순)을 대비시키는 것**이 경로 선정의 전부입니다. 나머지 조합은 같은 이야기를 반복합니다.

## 🌱 9. 호출 전 준비물 (P1~P5) — `pools.json`

**런 중에는 DB를 치지 않습니다.** 파라미터 생성 비용이 측정에 섞이면 안 됩니다.

### P1. 상세 id 풀 (V1)

```sql
select id from exhibitions
 where deleted_at is null and type = 'CATALOG'
 order by rand(:seed) limit 5000;
```

### P2. 커서 토큰 3종 (D10 · D50 · D100)

커서 = `base64url("{sort}\0{key}\0{lastId}")` — **구분자는 공백이 아니라 NUL(`\0`)입니다**(`Cursor.java:25`). 공백으로 만들면 전부 400 `INVALID_CURSOR`가 나고, 응답이 5ms라 "커서가 빠르다"로 오독하게 됩니다. **페이지를 순차로 밟지 말고 SQL로 만듭니다.**

```sql
select start_date, id from exhibitions
 where deleted_at is null and type = 'CATALOG'
   and start_date is not null                       -- NULL은 nulls 블록 경계라 제외
   and start_date <= curdate()
   and (end_date is null or end_date >= curdate())
 order by start_date desc, id desc
 limit 1 offset 199;      --  10페이지 지점 (20 × 10 − 1)
 -- offset  999           --  50페이지
 -- offset 1999           -- 100페이지
```

```bash
# NUL은 명령치환($(...))이 삼키므로 printf에서 base64로 곧장 파이프한다
printf 'latest\000%s\000%s' "$START_DATE" "$ID" | base64 | tr '+/' '-_' | tr -d '='
```

### P3. 검색어 토큰 2종 + 매칭 수 (K1 · K2)

원본 313개 한글 제목에서 2~4글자 토큰을 뽑고, 각 토큰의 실제 매칭 수를 셉니다.

```sql
select count(*) from exhibitions e
 where e.deleted_at is null and e.type = 'CATALOG'
   and (e.end_date is null or e.end_date >= curdate())        -- 검색은 notEndedOn이 붙는다
   and (lower(e.title) like '%전시%'
        or e.exhibition_place_id in
           (select p.id from exhibition_place p where lower(p.name) like '%전시%'));
```

- **토큰은 전 볼륨 고정**, 매칭 수만 볼륨마다 기록합니다. 안 그러면 "토큰 탓인지 볼륨 탓인지"를 못 가릅니다.

### P4. 좌표 풀 (S4)

```sql
select gps_y as lat, gps_x as lng from exhibition_place    -- gps_x=경도, gps_y=위도
 where gps_x is not null and gps_y is not null
 order by rand(:seed) limit 200;
```

### P5. 경로별 `totalCount` 스냅샷

**SQL로 재현하지 말고 앱을 통해 찍습니다.** Specification과 손으로 쓴 SQL이 어긋나면 근거가 무너집니다.

```bash
curl -s "$BASE/api/v1/exhibitions?section=free&size=1" | jq '.data.totalCount'
```
→ `meta.json.totalCounts.{경로ID}`. 워밍업 직후·측정 직전에 28경로를 1회씩.

### 📌 경로별 표본을 정확히 채우는 방법 — 요청 계획(plan) 배열

k6에게 "이 경로를 2,000번"이라고 시키는 가장 확실한 방법은 **미리 만든 배열을 인덱스로 소비**하는 것입니다.

```js
import exec from 'k6/execution';

// 티어별 목표 횟수만큼 경로 ID를 넣고, 고정 시드로 한 번 섞는다
const PLAN = shuffle(seed, [
  ...repeat(['H2','H4','S1','S2','S3','X8','K1','D100'], 2000),   // 티어1  16,000
  ...repeat(['H1','H3','X1','X2','X3','X4','X5','X6','X7','X9',
             'F1','F2','F3','F4','K2','D10','D50','Z1'],   400),   // 티어2   7,200
]);                                                                //        = 23,200

export const options = {
  scenarios: {
    main: {
      executor:    'shared-iterations',   // 10 VU가 PLAN을 나눠 소비
      vus:         10,
      iterations:  PLAN.length,
      maxDuration: '90m',
    },
  },
};

export default function () {
  call(PATHS[PLAN[exec.scenario.iterationInTest]]);   // 전역 반복 인덱스
}
```

> ✅ **`shared-iterations` + 전역 인덱스**라서 경로별 횟수가 **정확히** 채워지고, 고정 시드 셔플이라 볼륨 간 **요청 순서까지 동일**합니다. 순서가 다르면 버퍼풀 상태가 달라져 볼륨 비교가 성립하지 않습니다.

```js

{ executor: 'shared-iterations', vus: 10, iterations: 23200, maxDuration: '90m' }

          startTime: '15m' } }
```

## ⚙️ 11. k6 호출 형태

```js
const POOLS = JSON.parse(open('./pools.json'));   // 런 중 DB 접근 없음
const BASE  = __ENV.BASE || 'http://localhost:8080';
const E     = encodeURIComponent;

const PATHS = {
  H1:   () => `/api/v1/exhibitions?section=ending-soon&size=2`,
  H2:   () => `/api/v1/exhibitions?section=free&size=2`,
  H3:   () => `/api/v1/exhibitions?section=opening-this-month&size=5`,
  H4:   () => `/api/v1/exhibitions/banners`,

  S1:   () => `/api/v1/exhibitions?sort=latest&size=20`,
  S2:   () => `/api/v1/exhibitions?sort=ending&size=20`,
  S3:   () => `/api/v1/exhibitions?sort=popular&size=20`,
  S4:   () => { const c = pick(POOLS.coords);
                return `/api/v1/exhibitions?sort=distance`
                     + `&lat=${c.lat + jitter()}&lng=${c.lng + jitter()}&size=20`; },

  X1:   () => `/api/v1/exhibitions?section=ending-soon&sort=latest&size=20`,
  // … X2~X7, X9 동일 패턴
  X8:   () => `/api/v1/exhibitions?section=free&sort=ending&size=20`,

  F1:   () => `/api/v1/exhibitions?region=SEOUL&size=20`,
  F2:   () => `/api/v1/exhibitions?region=JEJU&size=20`,
  F3:   () => `/api/v1/exhibitions?category=PAINTING&size=20`,
  F4:   () => `/api/v1/exhibitions?region=SEOUL&category=PAINTING&size=20`,

  K1:   () => `/api/v1/exhibitions?keyword=${E(POOLS.keywords.high)}&size=20`,
  K2:   () => `/api/v1/exhibitions?keyword=${E(POOLS.keywords.rare)}&size=20`,

  D10:  () => `/api/v1/exhibitions?sort=latest&size=20&cursor=${POOLS.cursors.p10}`,
  D50:  () => `/api/v1/exhibitions?sort=latest&size=20&cursor=${POOLS.cursors.p50}`,
  D100: () => `/api/v1/exhibitions?sort=latest&size=20&cursor=${POOLS.cursors.p100}`,

  V1:   () => `/api/v1/exhibitions/${pick(POOLS.detailIds)}`,
  Z1:   () => `/api/v1/exhibitions/region-groups`,
};

function call(id) {
  return http.get(BASE + PATHS[id](), {
    tags:    { path: id },        // ★ 없으면 경로별 p95가 산산조각 난다
    timeout: '30s',
  });
}
```

### 📋 반드시 지킬 것 5가지

| | 이유 |
| --- | --- |
| **`tags: {path: id}` 필수** | 커서·id가 섞인 URL을 k6가 서로 다른 메트릭으로 집계합니다. 태그가 없으면 **경로별 p95가 산산조각** 납니다 |
| **측정 루프에서 `JSON.parse` 금지** | 응답 파싱은 k6(=클라이언트) CPU를 먹고, 단일 호스트라 그게 곧 앱의 CPU입니다. `check`는 **status만** 봅니다 |
| **풀은 파일에서 읽는다** | 런 중에 DB·API를 쳐서 파라미터를 만들면 그 비용이 측정에 섞입니다 |
| **시드 고정 PRNG** | `Math.random()` 금지. 볼륨 간 같은 요청 열이 나와야 비교가 성립합니다. 시드는 `meta.json`에 |
| **`sleep()` 금지** | think time이 들어가면 목표 표본을 채우는 데 걸리는 시간만 늘어납니다 |

## 🖥 12. 시나리오 (R3) — 탐색 스크롤

> 🚫 **홈 진입 병렬 시나리오(SC1)는 제외했습니다.**
> `http.batch`로 4요청을 동시에 보내면 10 VU × 4 = 40 동시가 되어 커넥션풀(기본 10)에 큐가 생깁니다.
> **큐잉은 쿼리가 느려진 결과이지 원인이 아닙니다** — 인덱스를 고치면 저절로 사라지는 증상입니다.
> 이번 목적은 쿼리 비용이므로, 큐 대기가 섞인 숫자를 결과 표에 남기지 않습니다.

### SC2. 탐색 스크롤 — 커서 이어받기

```js
let cursor = null;
for (let page = 0; page < 3; page++) {
  const url = `/api/v1/exhibitions?sort=latest&size=20` + (cursor ? `&cursor=${cursor}` : '');
  const r = http.get(BASE + url, {tags: {path: `SC2.p${page}`}});
  cursor = r.json('data.nextCursor');      // 이 시나리오에서만 파싱 허용
  if (!cursor) break;
}
```
> 다음 요청에 필요한 값이라 파싱이 불가피합니다. 절대값을 다른 경로와 직접 비교하지 않습니다.

## 📝 16. 결과 문서에 반드시 적을 것
