전시 조회 부하실험 · 볼륨 313 → 100만

어떤 API의, 어떤 조합이 문제인가

28개 요청 경로를 네 볼륨에서 같은 조건으로 재고, 비용이 어디서 발생하는지를 필터 축과 정렬 축으로 갈라 정리했습니다.

측정 2026-07-29 코드 551794f 동시 2 버퍼풀 128M 모든 ms = 서버 사이드 응답시간 p50
비용은 두 곳에서만 나옵니다 — 필터가 정하는 count(*), 정렬이 정하는 filesort.

totalCount를 부르지 않는 API(배너·상세)는 데이터를 3,196배 늘려도 평평했습니다. 목록 API만 500~1,250배가 됐고, 그 안에서도 무료 필터가 count 비용을 2배로, 최신순·종료순이 filesort로 3~4초를 더합니다.

읽는 법 하나. 붉은 칸(count)이 필터를 바꿔도 5.4~5.8초로 거의 같은데 무료만 11.2초로 2.1배입니다. section=free가 exhibition_detail 100만 행을 서브쿼리로 훑기 때문입니다 — 그 테이블 price에 인덱스가 없습니다.

size는 비용을 안 바꿉니다. 홈은 size=2·size=5로 부르는데 size=20인 탐색과 같은 값이 나옵니다(H1 9,334 ≈ X1 8,903). count(*)에는 LIMIT이 없어서 2건을 보여주려고 50만 행을 셉니다.

선택도도 비용을 안 바꿉니다. 결과가 1/10인 제주가 서울보다 느리고, 매칭이 1/90인 희소 검색어도 고빈도어와 같은 대역입니다. 서브쿼리와 LIKE '%…%'가 대상 테이블을 전량 스캔하기 때문입니다.

04 — count 발생 지도

count는 어디서 몇 번, 얼마나 비싸게 나가나

목록 1요청이 날리는 SQL 5개 중 2개가 count이고, 그중 하나는 만들어놓고 버립니다.

GET /api/v1/exhibitions?sort=latest&size=20
  ├ count(*)              ← findAll(spec, Pageable)이 만들고 그냥 버림  ⚠ 낭비
  ├ slice (LIMIT 21)
  ├ count(*)              ← totalCount 응답용
  ├ 전시장 배치 조회 (IN …)     ← 조립
  └ 가격 배치 조회 (IN …)       ← 조립
어떤 조건의 count인가 순수 SQL 1회 무필터 대비 비싼 이유
필터 없음 sort=latest 123 ms 기준 진행 중 6.6만 행을 전부 셈
지역 region=SEOUL 184 ms 1.5× exhibition_place 서브쿼리 — region 인덱스 없음
무료 section=free 225 ms 1.8× exhibition_detail 서브쿼리 — price 인덱스 없음

10만 볼륨 · warm · 파이프 오버헤드 보정 · 이 값 ×2가 매 요청에 붙습니다

21건을 돌려주려고 100만 행을 전부 읽습니다. type='CATALOG'가 전체 행의 100%라 idx_exhibitions_type_owner는 이름만 인덱스이고 실제로는 풀스캔입니다.

최신순도 마찬가지입니다 — (start_date IS NULL OR start_date <= ?)의 OR가 range 조건을 막아 옵티마이저가 idx_exhibitions_dates를 버립니다. 그래서 "종료순만 불리하다"는 사전 가설과 달리 최신순과 종료순의 실측이 같습니다.
