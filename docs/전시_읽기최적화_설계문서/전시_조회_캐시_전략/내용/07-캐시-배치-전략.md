# 07 캐시 배치 전략
캐시를 어디에 둘 것인가 (로컬 vs 전역)

같은 캐시라도 **어디에 두느냐**에 따라 속도와 정합성이 갈린다. 각 서버의 메모리에 두면(로컬) 빠르지만 서버끼리 어긋나고, 별도 서버에 모으면(전역/공유) 일치하지만 네트워크를 탄다. 서버가 2대가 되는 순간 이 선택이 캐시 설계의 뼈대가 된다.

> **이 인덱스의 경계**: [04]의 "분산 환경 무효화 전파"가 사실 이 문제의 한 단면이다 — 무효화가 어려운 이유가 "캐시가 로컬에 흩어져 있어서"이기 때문. 배치(placement) 선택을 여기서 하고, 그 선택이 무효화 난이도를 결정한다.

---

## 로컬 캐시 vs 전역(공유) 캐시

| 구분 | 로컬 캐시 (예: Caffeine) | 전역 캐시 (예: Redis) |
|---|---|---|
| 위치 | 각 서버의 JVM 메모리 | 별도 캐시 서버 |
| 속도 | 매우 빠름 (네트워크 없음, ~µs) | 빠름 (네트워크 1홉, ~ms) |
| 정합성 | **서버마다 값이 다를 수 있음** | 모든 서버가 같은 값 |
| 무효화 | 전 서버 전파 필요 (pub/sub 등) | 한 번 지우면 끝 |
| 직렬화 | 불필요 (객체 그대로) | 필요 (JSON 등 — 역직렬화 CPU 비용) |
| 재배포 시 | 캐시 소멸 (콜드 스타트) | 생존 |
| 장애 격리 | 캐시 장애 = 그 서버만 | 캐시 서버가 단일 장애점이 될 수 있음 |

### 분산 환경의 함정

- 서버 A가 데이터를 변경하고 자기 로컬 캐시를 지워도, **서버 B의 로컬 캐시는 그대로**다
- 사용자가 어느 서버에 연결되느냐(로드밸런서)에 따라 새 값과 옛 값이 **뒤섞여** 보인다 — 새로고침할 때마다 값이 바뀌는 최악의 UX
- 해결은 두 갈래:
    1. **모두가 공유 캐시를 바라보게** 한다 — 한번 갱신하면 모두에게 반영 (무효화 문제 소멸)
    2. 로컬 캐시를 쓴다면 — **변경 이벤트를 모든 서버에 방송**(pub/sub)해서 각자 자기 로컬 캐시를 무효화 ([04] 이벤트 기반 무효화의 분산 버전) + 방송 유실에 대비해 **로컬 TTL을 보조 안전장치**로

## 사례 연구: 카카오페이 "분산 시스템에서 로컬 캐시 활용하기"

같은 문제를 큰 스케일에서 푼 사례이자, **이 시리즈가 채택하는 구조의 원본**이다. 요지:

- **왜 로컬 캐시를 썼나**: 통신사 정보·상품 같은 **자주 변하지 않는 데이터**를 빈번하게 조회 → 네트워크 왕복 자체를 없애고 외부 의존(Redis)도 줄였다. 서버 간 데이터가 잠시 어긋나도 되는(**Eventual Consistency 허용**) 데이터였기에 가능한 선택
- **불일치는 어떻게 풀었나**: 관리자(Admin)가 데이터를 수정하면 → 변경 이벤트를 **Redis Pub/Sub 채널에 발행** → 모든 API 서버가 구독하고 있다가 **각자 자기 로컬 캐시를 evict** → 다음 조회 때 최신으로 재적재. 로컬 캐시에는 기본 TTL(1시간)을 함께 둬서 이벤트가 새더라도 최대 1시간 안에 수렴
- **왜 Pub/Sub이었나**: ① Redis를 이미 쓰고 있어 추가 인프라 없음 ② 가볍고 단순 ③ **변경 빈도가 낮아** 메시지 유실 가능성이 상대적으로 적음. (Pub/Sub은 전달 보장이 없다 — 유실이 치명적이면 Kafka·Redis Streams 같은 ACK 기반으로)
- **구조 정리**: CacheManager 하나가 LOCAL/REDIS 타입을 통합 관리, 캐시 선언은 sealed class로 — 캐시 추가가 선언만으로 가능
- **더 나아가기로 언급된 것**: 다단계 캐시(1차 로컬 → 2차 Redis → DB), Write-Through, 캐시 크기 관리

핵심 판단 기준: **로컬 캐시는 "빠름"의 대가로 "무효화 전파 인프라"를 요구한다.** 이 비용을 지불할 가치는 (a) 데이터가 전 사용자 공통이고 (b) 변경 빈도가 낮아 방송이 드물며 (c) 잠깐의 불일치가 허용될 때 극대화된다 — 아래에서 보듯 내 상황은 세 조건에 전부 부합한다.

## 내 상황 분석

| 조건 | 내용 | 배치 선택에 주는 의미 |
|---|---|---|
| 캐시 대상 성격 | 목록 6종·상세 — **전 사용자 공통** (개인화 없음, [01]) | 로컬 캐시 히트율이 극대화되는 이상적 조건 — 어떤 사용자가 와도 같은 키를 침 |
| 변경 빈도 | 새벽 1시 배치 1회 + 저빈도 관리자 수정 ([04]) | 무효화 방송이 **하루 몇 건** — Pub/Sub 유실 확률·부하가 사실상 0. 카카오페이가 Pub/Sub을 고른 조건과 정확히 일치 |
| 신선도 요구 | 목록은 지연 허용, 상세도 이벤트성 변경 ([01]) | Eventual Consistency 허용 — 로컬 계층의 잠깐 불일치가 비즈니스 문제를 만들지 않음 |
| 값의 크기 | 목록 = DTO 20건 리스트 (JSON 수십 KB) | Redis 히트여도 **매 조회 역직렬화 CPU 비용** 발생 — 로컬 히트는 이 비용까지 0 |
| Redis 구성 | 같은 EC2의 단일 인스턴스, HA 없음 ([00]·[06]) | 로컬 계층이 있으면 Redis 장애 시에도 로컬에 살아있는 동안 정상 서빙 — **가용성 완충층**이 하나 늘어남 |
| 서버 구성 | Spring 2대 + 공유 Redis (이미 운영) | 방송 인프라(Pub/Sub) 추가 비용 0. 불일치 전파 범위도 2대로 작음 |

핵심: 카카오페이의 판단 기준 세 가지(전원 공통 · 저빈도 변경 · 불일치 허용)에 내 캐시 대상이 전부 부합하고, 방송 인프라(Redis)는 이미 있다. 여기에 내 환경 특유의 이득이 하나 더 있다 — **단일 Redis가 죽어도 로컬 계층이 완충**이 되어, 캐시 시스템 전체가 단일 장애점을 벗어난다. 지불하는 비용은 방송 발행·구독 코드와 "서버별 로컬 상태"라는 디버깅 복잡도인데, 변경 이벤트가 하루 몇 건뿐이라 이 비용이 최소인 지점에 서 있다.

## 내 상황 추천

### 배치 = 2단 캐시: L1 로컬(Caffeine) → L2 공유 Redis → DB + Pub/Sub 무효화 (카카오페이식)

```
읽기 (Cache-Aside 2단, [03]):
  요청 → L1 로컬 Hit? ── Yes → 반환 (~µs, 역직렬화 없음)
           │ No
           ▼
         L2 Redis Hit? ─ Yes → L1에 되채움(backfill) → 반환 (~ms)
           │ No
           ▼
         DB 조회 → L2·L1 채움 → 반환

무효화 (변경은 전부 이 경로, [04]):
  배치 재적재/관리자 수정
     → L2(Redis) 갱신·삭제                        ← 전 서버 공통 진실
     → Pub/Sub 채널에 키 방송                      ← "이 키 로컬에서 지워라"
     → 각 서버 리스너가 자기 L1만 evict             ← 다음 조회가 L2에서 backfill
  + 방송 유실 대비: L1 TTL(목록 1h·상세 10m)이 불일치 상한
```

- **L1 TTL은 L2보다 훨씬 짧게** (목록 1h, 상세 10m — [05]): 방송이 유실된 최악의 경우에도 "그 서버만 최대 L1 TTL 동안 옛 값"으로 피해가 묶인다. 카카오페이가 로컬 1h TTL을 병행한 것과 같은 이유
- **L1은 `maximumSize` 필수** — 1GB 힙([00])에서 상한 없는 로컬 캐시는 OOM 예약. 우리 데이터(수백 KB)에는 여유가 크지만 상한은 규율이다
- **재배포 시**: L1은 사라지지만 L2가 살아 있어 첫 요청들이 L2에서 backfill — DB로 직행하지 않는다 ([08])
- **Redis 장애 시**: L1에 살아있는 동안 정상 서빙, L1까지 만료되면 DB 폴백 ([06]) — 캐시 계층 전체가 죽어도 서비스는 산다
- 구현(선언 enum · CacheManager · 방송 발행/구독 코드)은 → [캐시매니저_설계_및_구현.html]

### 결정 및 근거 (포트폴리오용 메모)
- **결정**: 카카오페이식 2단 배치 — L1 로컬(Caffeine, 짧은 TTL + maximumSize) + L2 공유 Redis(긴 TTL + jitter), 무효화는 "L2 갱신 + Redis Pub/Sub 방송으로 전 서버 L1 evict + L1 TTL 보조"
- **근거**: 캐시 대상이 전 사용자 공통·저빈도 변경·불일치 허용이라는 로컬 캐시의 3조건에 전부 부합하고, 방송 인프라는 기보유 Redis로 비용 0이다. 로컬 히트는 네트워크 왕복뿐 아니라 JSON 역직렬화 비용까지 없애며, 단일 Redis(HA 없음) 장애 시 완충층이 되어 가용성도 올린다. 변경 이벤트가 하루 몇 건이라 Pub/Sub 유실 리스크가 최소이고, 유실돼도 L1 TTL이 불일치를 목록 1h·상세 10m으로 묶는다
- **제약사항**: ① 모든 변경 경로는 반드시 "L2 갱신 + 방송"을 함께 수행([04]의 무효화 경로 일원화) ② 방송은 전달 보장이 없으므로 L1 TTL 없이 운영 금지 ③ L1 `maximumSize` 필수 ④ 서버별 L1 상태가 다를 수 있음을 전제로 디버깅(장애 분석 시 "어느 서버의 캐시인가"를 항상 확인)
- **기각한 선택지**: 공유 Redis 단독(구현은 가장 단순하나 매 조회 네트워크+역직렬화 비용을 지불하고, 단일 Redis 장애 시 완충 없이 전 요청이 DB 직행 — 로컬 3조건이 충족되는 상황에서 이점을 포기할 이유가 없음) / 로컬 단독(배치가 실행된 서버만 갱신되는 불일치, 재배포마다 콜드 스타트) / Kafka·Redis Streams 기반 무효화(전달 보장이 필요할 만큼 변경이 잦지 않음 — 방송 유실은 L1 TTL로 충분히 수습)
