# 06 캐시 장애 패턴
캐시가 오히려 장애를 만드는 상황과 방어법

캐시가 있어서 오히려 DB가 죽는 상황들. 세 패턴(스탬피드·패너트레이션·아발란치)은 이름은 다르지만 **"요청이 캐시를 뚫고 DB로 몰린다"** 는 공통 구조를 가진다. 여기에 "캐시 저장소(Redis) 자체가 죽는" 네 번째 상황까지 더해 방어를 설계한다.

> **이 인덱스의 경계**: 평상시 흐름은 [03], 변경 순간의 정합성은 [04], 여기는 **비정상 순간의 가용성**이다. TTL이 여기서는 "동시 만료를 만드는 장애 요인"으로 등장한다([05]의 만료 정책과 같은 TTL, 다른 얼굴).

---

## 패턴 1: 스탬피드 (Stampede / Thundering Herd)

- **인기 키 하나**가 만료 → 그 순간 대기 중이던 동시 요청 전부가 Miss → 같은 DB 쿼리가 한꺼번에 몰림
- TTL 만료 시점이 위험. 심하면 DB가 느려지고 → 응답 지연으로 더 많은 요청이 쌓이고 → 연쇄 Miss가 커지는 악순환
- DB 과부하 시 빠르게 폴백 응답으로 전환(서킷 브레이커)도 보조 수단

### 해결 1 — 분산 Lock (한 스레드만 DB에 보낸다)

```java
public Product getProductWithLock(Long id) {
    String key = "product:" + id;

    Product cached = cache.opsForValue().get(key);
    if (cached != null) return cached;

    RLock lock = redisson.getLock("lock:" + key);   // 분산 락으로 한 스레드만 DB 조회
    try {
        if (lock.tryLock(3, 10, TimeUnit.SECONDS)) {
            // Double Check — 락 기다리는 사이 다른 스레드가 이미 채웠을 수 있다
            cached = cache.opsForValue().get(key);
            if (cached != null) return cached;

            Product product = repo.findById(id).orElseThrow();
            cache.opsForValue().set(key, product, Duration.ofMinutes(30));
            return product;
        }
    } finally {
        if (lock.isHeldByCurrentThread()) lock.unlock();
    }
    throw new RuntimeException("캐시 갱신 대기 초과");
}
```

- 핵심은 **Double Check** — 락을 얻고도 캐시를 재확인해야 중복 쿼리가 안 나간다
- 비용: 락 인프라(Redisson 등) + 모든 Miss 경로에 락 대기 지연이 낀다

### 해결 2 — PER (Probabilistic Early Recomputation)

```java
long ttl = entry.getExpireAt() - System.currentTimeMillis();
double gap = entry.getComputeTime() * Math.log(Math.random());  // 항상 음수
if (ttl + gap <= 0) {
    return fetchAndCache(id, key);   // TTL이 끝나기 전에 확률적으로 미리 갱신
}
return entry.getValue();
```

- 만료 시점에 가까울수록 갱신 확률이 올라가 자연스럽게 1~2개 요청만 DB로 감 — **락 없이** 스탬피드를 예방
- 값 계산이 비쌀수록(computeTime 클수록) 더 일찍 갱신 시작
- Refresh-Ahead(만료 전 선제 갱신)의 확률적 구현 — [03]의 용어 교정 참조

## 패턴 2: 패너트레이션 (Penetration)

- **존재하지 않는 데이터**를 반복 요청 → 캐시엔 영원히 없으니(없는 건 캐시 안 하니까) 매번 DB까지 관통
- 악의적 스캔(무작위 id 순회)이나 삭제된 리소스로의 잔존 링크에서 발생
- 해결 1: **null(없음)도 캐시**한다 — 짧은 TTL(수십 초~수 분)로. "없음"이라는 사실도 정보다
- 해결 2: **Bloom Filter** — "존재할 가능성이 있는 id" 집합을 메모리에 두고, 확실히 없는 요청은 캐시·DB 전에 차단 (대규모 스캔 방어용)

## 패턴 3: 아발란치 (Avalanche)

- **대량의 키가 동시에 만료** → 전체 트래픽이 한꺼번에 DB로 (스탬피드가 키 하나의 문제라면, 아발란치는 키 전체의 문제)
- 같은 시각에 일괄 적재한 캐시는 TTL도 같은 시각에 끝난다 — 배치 재적재가 전형적인 유발 조건
- 해결: **TTL에 랜덤 jitter**를 더해 만료 시점을 흩뿌린다 (`TTL = 기본값 + random(0~N분)`)

## 패턴 4: 캐시 저장소 자체의 장애 (Redis down)

- 위 세 패턴은 "캐시가 살아 있는데 뚫리는" 문제고, 이건 "캐시가 통째로 사라지는" 문제
- Cache-Aside의 본질적 장점이 여기서 발휘된다: **캐시는 최적화 층일 뿐, 죽어도 DB로 동작해야 한다**
- 방어 3종: **짧은 타임아웃**(캐시 응답을 오래 기다리면 캐시 장애가 곧 API 지연이 된다) + **예외 삼키고 DB 직행** + (대규모라면) 서킷 브레이커로 복구 전까지 캐시 접근 자체를 차단

## 내 상황 분석

| 패턴 | 내 상황에서의 발생 가능성 | 근거 |
|---|---|---|
| 스탬피드 | **낮음** | 목록 6키는 만료로 죽지 않는다 — 새벽 배치가 만료 **전에** 재적재(갱신)하므로 TTL은 사고 시에만 발동([04]·[05]). 상세는 evict 후 Miss가 나지만 관리자 수정이 저빈도 + 단건 PK 조회라 쿼리가 싸다 |
| 패너트레이션 | **낮음** | 없는 전시 id 상세 요청 정도가 표면. 공개 서비스라 0은 아니지만, 트래픽 규모가 작고 없는 id 조회도 PK 인덱스라 저렴 |
| 아발란치 | **조건부** | 6키가 배치에서 같은 순간 적재돼 **TTL이 같은 순간에 끝난다** — 정상 경로에선 다음 배치가 먼저 오지만, 배치가 하루 죽으면 25h 뒤 6키가 동시 만료 |
| Redis down | **대비 필수** | Redis가 같은 EC2의 단일 인스턴스(HA 없음). 이미 선례 있음 — draft 어댑터(`RedisAiDraftStore`)는 예외를 삼켜 degrade, `timeout: 2s` 설정 완료. 단, 2단 배치([07]) 덕에 **L1(로컬)이 1차 완충** — L1에 값이 살아있는 동안은 Redis에 아예 안 가고, L1 만료 후에야 폴백 경로를 탄다 |

핵심: 내 구조의 1차 방어선은 이 인덱스가 아니라 **[04]의 "만료 전 재적재"** 다 — 만료가 안 일어나면 만료발 장애(스탬피드·아발란치)도 없다. 따라서 여기서 설계할 것은 "재적재가 실패한 날"과 "Redis가 죽은 날"의 2차 방어선뿐이다. 분산 Lock·PER·Bloom Filter는 트래픽과 키 규모가 정당화하지 못한다 — 교과서 지식으로 보유하고 도입하지 않는다.

## 내 상황 추천

### 방어 1 — TTL jitter (아발란치 대비, 사실상 공짜)

```
목록 TTL = 25h + random(0 ~ 30분)   ← 키마다 다른 랜덤 값
```

- 배치가 죽은 다음 날 6키가 동시에 만료되는 대신 30분에 걸쳐 흩어져 만료된다. 키 6개라 몰림 자체가 크진 않지만, 코드 한 줄짜리 보험이라 안 할 이유가 없다
- 상세 TTL(6h)에도 동일하게 ±수 분 jitter

### 방어 2 — Redis 장애 시 "L1 완충 → DB 폴백" (실패 삼킴은 CacheManager 한 곳에)

```
Redis down 상태의 조회:
  L1에 값 있음  → 그대로 서빙 (~µs) — Redis에 아예 안 감, 사용자는 장애를 모름
  L1 만료 후    → L2 get 예외 (timeout 2s) → CacheManager가 삼키고 로그
                → loader(DB) 실행 → 정상 응답 → L1에 적재 (L1은 정상이니 이후 요청은 L1 Hit)
  L2 put 실패   → 역시 삼킴. Redis 복구 후 첫 Miss부터 자연 재적재
```

- 읽기·쓰기·방송 실패 모두 **예외를 삼키고 정상 응답** — 캐시 장애가 사용자 장애로 번지지 않게. 이 삼킴은 각 서비스가 아니라 **CacheManager 한 곳**에 있다(한 곳만 빼먹어도 캐시 장애 = API 500이 되는 설계를 구조적으로 차단 → [캐시매니저_설계_및_구현.html] UC-4)
- L1 완충 덕에 Redis가 죽어도 **L1 TTL(목록 1h) 동안은 DB조차 부하를 받지 않는다.** L1까지 만료된 뒤의 DB 직행도, 목록·상세 쿼리 모두 최적화가 끝나 있어([전시_조회_count_제거_v2]) 감당 가능한 규모
- 서킷 브레이커는 도입하지 않음 — 2s 타임아웃 × 낮은 트래픽에서는 "매 요청 2s 대기"가 쌓여 죽을 규모가 아니고, Lettuce는 연결 끊김을 빠르게 감지한다. 트래픽이 늘어 타임아웃 대기 자체가 부하가 되면 그때 도입
- 참고: Redis down 동안은 무효화 방송도 안 나간다 — 이 구간의 변경(관리자 수정)은 L1 TTL이 수습한다. 어차피 L2도 죽어 있어 "옛 값" 자체가 L1에만 잠깐 남는 구조

### 방어 3 — 없는 id의 상세 요청 (패너트레이션, 최소 대응)

- 상세 조회에서 "없음"(404)이 확인되면 **null 마커를 짧은 TTL(1분)로 캐시**하는 것만 적용 — 같은 없는 id의 반복 조회가 DB에 닿지 않게
- Bloom Filter는 기각: 전시 id 공간이 작고 스캔 공격의 실질 위협·비용이 현재로선 없음. `disableCachingNullValues()`를 쓰는 Spring 설정([02])과 충돌하니, 적용한다면 null 마커 객체를 명시적으로 넣는 방식으로

### 결정 및 근거 (포트폴리오용 메모)
- **결정**: L2 TTL jitter(목록 +0~30분, 상세 +수 분) + Redis 장애 시 예외 삼킴·DB 폴백(읽기/쓰기/방송 모두, CacheManager 일원화) 2가지만 도입. L1 완충은 [07]의 2단 배치에서 공짜로 얻는다. 분산 Lock·PER·Bloom Filter·서킷 브레이커는 도입하지 않음
- **근거**: 만료발 장애의 1차 방어는 [04]의 만료 전 재적재가 이미 담당한다. 남는 시나리오는 "배치 실패 다음 날의 동시 만료"(→ jitter로 분산)와 "단일 Redis 장애"(→ 폴백으로 가용성 유지)뿐이며, 두 방어 모두 코드 몇 줄 비용으로 얻는다. 락·PER은 Miss 비용(최적화 끝난 쿼리 1번)과 동시성 규모가 작아 오버엔지니어링이다
- **제약사항**: 폴백이 동작하려면 캐시 계층의 예외가 밖으로 나가지 않아야 한다 — 삼킴을 CacheManager 한 곳에 일원화하고 서비스는 캐시 예외를 다루지 않는다. Redis 타임아웃(2s)이 L1 만료 후 최악의 경우 응답에 더해지는 것은 수용
- **기각한 선택지**: 분산 Lock(Miss가 몰릴 인기 키 만료 이벤트 자체가 없음), PER(동일 이유 + 캐시 엔트리에 메타데이터 추가 필요), Bloom Filter(위협 규모 미달), 서킷 브레이커(트래픽 규모 미달 — 성장 시 재검토)
