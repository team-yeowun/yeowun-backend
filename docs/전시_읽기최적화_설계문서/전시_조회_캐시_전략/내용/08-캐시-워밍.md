# 08 캐시 워밍
비어있는 캐시를 어떻게 채워둘 것인가

캐시가 비어 있으면 모든 요청이 DB로 직행한다 — **Cold Start 문제**. 워밍(warming)은 사용자가 Miss를 맞기 전에 캐시를 미리 채워두는 기법이다. "언제 비는가"를 먼저 알아야 "언제 데울까"를 정할 수 있다.

> **이 인덱스의 경계**: [03]·[04]에서 "배치 완료 후 재적재"를 이미 결정했다 — 그것이 사실 워밍의 한 형태다. 여기서는 그 재적재를 포함해 **캐시가 비는 모든 순간**(기동·장애 복구·배치 실패)을 나열하고 각각의 대응을 정한다.

---

## 캐시는 언제 비는가

| 순간 | 원인 | 비는 범위 |
|---|---|---|
| 최초 배포 | 캐시에 아무것도 넣은 적이 없음 | 전부 |
| 앱 재배포/재시작 | **로컬 캐시만** 소멸 (공유 캐시는 생존) | 로컬 전부 / 공유 0 |
| 캐시 서버 재시작 | 공유 캐시 소멸 (비영속 설정 시) | 공유 전부 |
| 무효화 직후 | evict가 키를 지움 | 지운 키만 |
| TTL 만료 | 시간 경과 | 만료된 키만 |

## 워밍 전략 4가지

| 전략 | 설명 | 적합 시나리오 |
|---|---|---|
| **기동 시 워밍** | 서버 시작 시 인기 데이터를 미리 적재 | 인기 상품, 메인 페이지 (키가 적고 예측 가능할 때) |
| **Lazy Loading** | 최초 요청이 Miss를 맞으며 적재, 이후 Hit | 범용. 데이터가 많아 뭘 데울지 모를 때 (워밍 안 함 = 이것) |
| **스케줄 워밍** | 주기 작업이 정기적으로 캐시를 갱신·적재 | 검색 자동완성, 랭킹, **배치성 데이터** |
| **Shadow 배포** | 신규 서버에 기존 트래픽을 복제해 캐시를 채운 뒤 투입 | 대규모 서비스의 로컬 캐시 웜업 |

### 기동 시 워밍의 구현 포인트

- `@PostConstruct`보다 **`ApplicationReadyEvent`** 가 안전 — PostConstruct는 빈 초기화 중이라 다른 빈·커넥션 풀이 아직 준비 전일 수 있다. ReadyEvent는 애플리케이션이 요청받을 준비가 끝난 시점
- 워밍 완료 전 트래픽 유입을 막고 싶으면 **헬스체크와 연동** — 워밍이 끝난 뒤에 readiness를 정상으로 전환해 LB가 트래픽을 흘리게 함
- 워밍 실패가 기동 실패가 되지 않게 — 워밍은 try-catch로 감싸고, 실패해도 Lazy Loading이 받쳐주므로 앱은 뜬다

## 내 상황 분석

"캐시는 언제 비는가" 표를 내 구조(L1 로컬 + L2 공유 Redis 2단 — [07])에 대입하면, 걱정할 순간이 몇 개 안 남는다.

| 순간 | 내 상황에서는 | 대응 필요? |
|---|---|---|
| 앱 재배포 | **L1(로컬)은 소멸하지만 L2(공유 Redis)가 생존** — 재배포 직후의 L1 Miss는 L2에서 backfill되므로 **DB로 직행하지 않는다** (2단 배치의 이득, [07]) | 불필요 |
| 새벽 배치 후 | 재적재(갱신)가 곧 워밍 — evict가 아니라 새 값 덮어쓰기이므로 **Miss 구간 자체가 없다** ([04]) | **이미 해결** |
| 배치 실패 시 | 재적재가 안 돌아 옛 캐시가 남음 → 옛 값 서빙(빈 것보다 낫다) → 25h 뒤 TTL 만료로 빔 | 재워밍 수단 필요 |
| Redis 재시작 | 비영속이라 L2 전부 소실 → L1에 살아있는 항목은 그대로 Hit, 나머지는 Miss | Lazy로 회복 가능하나 수단 있으면 좋음 |
| 상세 evict 직후 | 관리자 수정 건 1키만 Miss — 다음 조회 1번이 채움 | 불필요 (Lazy로 충분) |
| 최초 배포 | 빈 캐시로 시작 | Lazy 또는 수동 1회 |

핵심: 주 워밍은 **스케줄 워밍(= 새벽 배치의 재적재)** 로 이미 결정돼 있고, 그 외의 순간들은 "**같은 적재 코드를 다시 실행할 수단**"만 있으면 전부 해결된다. 즉 내 워밍 설계의 실체는 전략 선택이 아니라 **적재 로직을 한 곳에 모아 재사용 가능하게 만드는 것**이다.

## 내 상황 추천

### 구조: 워밍 로직을 컴포넌트 하나로 모으고, 세 곳에서 호출

```
CacheWarmer (컴포넌트 — "6개 목록 키를 DB에서 계산해 refresh한다")
  refresh = L2(Redis)에 새 값 덮어쓰기 + 무효화 방송 → 각 서버 L1 evict → 다음 조회가 L2에서 backfill
  ├─ 호출 1: 새벽 배치 완료 직후  ← 주 경로 (스케줄 워밍, [04]의 재적재)
  ├─ 호출 2: 관리자 수동 트리거   ← 운영 복구용 (배치 실패·Redis 재시작 후)
  └─ 호출 3: (선택) 기동 시       ← 최초 배포·특수 상황용
```

```java
@Component
@RequiredArgsConstructor
public class ExhibitionCacheWarmer {

    private final ExhibitionQueryRepository repo;
    private final CacheManager cacheManager;   // L1·L2·방송을 아는 건 CacheManager뿐

    /** 6개 목록 키를 새 값으로 반영한다(refresh — Miss 구간 없음). 실패해도 예외를 던지지 않는다. */
    public void warmLists() {
        for (ExhibitionCache cache : LIST_CACHES) {        // 고정 6키 enum ([02])
            try {
                Object value = load(cache);                // 키별 조회 로직
                cacheManager.refresh(cache, null, value);  // L2 갱신 + 전 서버 L1 무효화 방송
            } catch (Exception e) {
                log.warn("워밍 실패 — Lazy Loading이 받친다: {}", cache, e);   // 다음 키 계속
            }
        }
    }
}
```

- **호출 1 (배치 직후)**: DB 적재 성공 확인 후 `warmLists()` — [04]의 "적재 성공 후에만 재적재" 규칙 그대로. 배치 스케줄러는 2대 중 1대만 실행(분산 락 전제)이지만 워밍 대상이 공유 Redis라 어느 서버가 실행하든 결과 동일
- **호출 2 (관리자 트리거)**: `/api-admin/v1/...` 수동 엔드포인트 하나. 배치가 죽은 날 아침, Redis를 재시작한 날 — 원인을 고친 뒤 이 버튼 하나로 캐시 상태를 정상으로 복구. 운영 사고 대응이 "코드 배포"가 아니라 "버튼"이 된다
- **호출 3 (기동 시)**: `ApplicationReadyEvent`에서 호출하되 **선택 사항**. 공유 Redis 덕에 평상시 재배포에는 필요 없고, 최초 배포·전체 재구축 때만 의미 있다. 붙인다면 "캐시가 비어 있을 때만 채우는" 조건(`setIfAbsent`)으로 — 멀쩡히 살아 있는 캐시를 기동 때마다 다시 계산하는 낭비 방지
- 키별 실패를 삼키고 다음 키로 진행 — 워밍은 best-effort고, 빠진 키는 Lazy Loading(Cache-Aside의 Miss 경로)이 받친다

### 워밍 완료 전 트래픽 — 헬스체크 게이팅은 하지 않는다

- 교과서의 "헬스체크를 워밍 완료 후 정상 전환" 기법은 **Miss 폭주가 DB를 위협하는 규모**에서 쓰는 것
- 내 경우 워밍이 안 된 상태의 최악은 "첫 사용자 몇 명이 최적화된 쿼리를 직접 침" — DB 위협이 아니라 응답 수십 ms 손해다. 게이팅으로 배포 파이프라인을 복잡하게 만들 이유가 없다

### 상세 페이지는 워밍하지 않는다

- 상세는 Lazy Loading으로 충분 — 어떤 전시가 조회될지 예측해 데우는 것보다, 조회되는 것만 채우는 게 낭비가 없다 (교체·만료 정책상 안 읽히는 키를 채워봐야 TTL 6h 뒤 버려짐)
- 예외적으로 "1페이지에 노출되는 전시들의 상세"([01]의 캐시 대상)를 목록 워밍 때 함께 데우는 확장은 가능하나, 상세 Miss 1번의 비용(PK 단건 조회)이 싸서 지금은 이득이 없다

### 결정 및 근거 (포트폴리오용 메모)
- **결정**: 주 워밍 = 새벽 배치 직후 refresh(스케줄 워밍 — L2 갱신 + L1 무효화 방송). 적재 로직을 `ExhibitionCacheWarmer` 컴포넌트 하나로 모으고 관리자 수동 트리거를 추가. 기동 시 워밍은 선택(있어도 setIfAbsent), 헬스체크 게이팅·상세 워밍·Shadow 배포는 하지 않음
- **근거**: 2단 배치([07])에서 재배포는 L1만 비우고 L2가 backfill을 받쳐 DB 직행이 없으므로, 캐시가 실질적으로 비는 시나리오는 "배치 실패"와 "Redis 재시작" 두 가지다. 둘 다 새 전략이 아니라 **기존 refresh 로직의 재실행**으로 해결되므로, 로직을 한 곳에 모아 세 진입점에서 재사용하는 구조가 가장 단순하다. L1은 방송 evict 후 L2에서 자연 재적재되므로 별도로 데울 필요가 없다. Miss 비용이 낮아(쿼리 최적화 완료 + 낮은 트래픽) Lazy Loading이 훌륭한 안전망 역할을 한다
- **제약사항**: 워밍과 배치의 실행 주체가 분산 락으로 단일화되어 있어야 함(2대가 동시에 워밍해도 결과는 같지만 DB 조회가 중복). 수동 트리거는 관리자 인증 뒤에 둘 것
- **기각한 선택지**: 헬스체크 게이팅(Miss 폭주가 위협이 아닌 규모 — 배포 복잡도만 증가) / 상세 워밍(예측 적재보다 Lazy가 낭비 없음) / Shadow 배포(로컬 캐시도 대규모 트래픽도 없음)
