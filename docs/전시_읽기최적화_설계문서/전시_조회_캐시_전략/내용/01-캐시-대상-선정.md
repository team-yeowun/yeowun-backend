# 01 캐시 대상 선정
무엇을 캐시할 것인가

> 대상 서비스: https://yeowun.vercel.app/yeowun (운영 중)
> 매일 새벽 1시에 전시 초기화 파이프라인으로 전시 적재
> → 조회 목록은 하루에 거의 변할 일이 없으며, 어느 정도 지연은 허용함

## 캐시하기 좋은 데이터의 조건
- 읽기 비율이 압도적으로 높다 (조회 : 수정 비율이 큼)
- 계산·조회 비용이 비싸다 (JOIN 많은 목록 쿼리, 집계)
- 약간의 신선도 손해를 허용할 수 있다 → 얼마나 허용하는지가 무효화 설계로 이어짐 → [04 캐시 무효화]

## 캐시하면 안 되거나 신중해야 하는 데이터
- 항상 최신이어야 하는데 **실시간(초 단위)으로 바뀌는** 데이터 (재고 수량, 실시간 조회수)
- 사용자마다 다른 데이터 (개인화 결과 — 키 폭발 위험 → [02 키 설계])

> "항상 최신 필요"라고 해서 무조건 캐시 제외는 아니다. **변경 시점을 애플리케이션이 인지할 수 있으면**(관리자 수정처럼) 그 순간 무효화해서 최신을 지키면서 캐시할 수 있다. 캐시를 정말 빼야 하는 건 "초 단위로 계속 바뀌어 무효화가 따라잡을 수 없는" 경우다.

## 판단 근거로 쓸 수치
- 해당 API의 QPS, 평균 응답시간, DB 부하 비중 → 도입 **전에** 베이스라인 측정 → [10 캐시 지표와 모니터링]

## 캐시 대상 목록

### 홈 화면
- 배너 목록
- 곧 끝나기 전에 봐야 할 전시 목록
- 이번달 새로 열리는 전시 목록

### 전시 탐색 화면
- 최신순 조회 목록 1페이지 (필터=전체, 장르=전체)
- 종료순 조회 목록 1페이지 (필터=전체, 장르=전체)
- 인기순 조회 목록 1페이지 (필터=전체, 장르=전체)

### 상세 조회 페이지
- 각 1페이지에 노출되는 전시들의 상세 조회 페이지 → **캐시함** (아래 결정 참고)

## 내 상황 분석

| 대상 | 변경 경로 | 변경 빈도 | 캐시 판단 |
|---|---|---|---|
| 홈/탐색 목록 (6종) | 새벽 1시 배치만 | 하루 1회 | 캐시 O — 배치 후 재적재 → [04] |
| 상세 페이지 | 관리자 수정(가격·위치 등) | 낮음(저빈도) | 캐시 O — 관리자 수정 시점 무효화 → [04] |

핵심: 캐시 대상이 **임의 조합이 아니라 미리 아는 고정 집합**이다. 목록은 6개로 유한하고(→ [02] 키 폭발 없음), 상세는 단건이라 키가 명확하다. 변경 경로도 목록은 배치, 상세는 관리자 수정으로 각각 **예측·인지 가능**해서 무효화가 어렵지 않다.

## 상세 조회 캐시 결정

> 01번의 미결 항목이자, 원문의 충돌("상세를 캐시 대상"이라면서 "상세는 항상 최신 보장")을 여기서 해소한다.

**결정: 상세를 캐시한다.** 단 목록과 무효화 방식을 다르게 가져간다.

판단에 쓴 사실:

| 질문 | 답 | 의미 |
|---|---|---|
| 상세가 '항상 최신' 필요한 이유 | 가격·위치 등을 **관리자가 수정** | 실시간이 아니라 **가끔 있는 이벤트성 변경** |
| 정적 정보(제목·설명·이미지·기간) | 관리자 수정 때만, 거의 안 바뀜 | 대부분의 시간 동안 목록과 같은 성격(불변) |
| 상세 트래픽 | 목록보다 적음 | 캐시 이득은 목록보다 작지만, 캐시해도 부담이 적음 |

- 상세가 바뀌는 유일한 경로가 **관리자 수정**이고, 빈도가 낮으며, 그 시점을 애플리케이션이 안다(관리자 수정 API가 곧 무효화 트리거)
- 따라서 그 순간에만 해당 상세 키를 무효화하면 **"항상 최신 보장"과 "캐시 이득"이 양립**한다 → 원문의 충돌은 실제 충돌이 아니었음
- 실시간 카운터(조회수·좋아요)였다면 결정이 달랐겠지만(초 단위 변경 → 정적/동적 분리 필요), 그 케이스가 아니다

무효화 방식의 구체(이벤트 기반 evict, AFTER_COMMIT, 짧은 TTL, 우회 경로 제약)는 → [04 캐시 무효화]의 "상세 조회의 무효화" 절.

## 결정 및 근거 (포트폴리오용 메모)
- **결정**: 홈/탐색 목록 6종 + 각 상세 페이지를 캐시 대상으로 확정. 목록은 배치 후 재적재, 상세는 관리자 수정 시점 무효화
- **근거**: 모든 대상이 고정 집합이고 변경 경로가 예측·인지 가능하다. 상세의 "항상 최신"은 실시간 변경이 아니라 저빈도 관리자 수정에서 비롯되므로, 그 시점 무효화로 최신성과 캐시 이득을 동시에 달성한다
- **제약사항**: 상세는 관리자 수정 경로가 반드시 무효화 로직을 거쳐야 함(DB 직접 수정 우회 시 캐시 어긋남)
- **기각한 선택지**: 상세 캐시 제외 — 트래픽이 적어도 무효화가 쉬운 케이스라 캐시 이득을 포기할 이유가 없음 / 상세 정적·동적 분리 — 실시간 카운터가 없어 현재는 과설계
