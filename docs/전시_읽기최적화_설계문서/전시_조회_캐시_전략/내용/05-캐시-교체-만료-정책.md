# 05 교체·만료 정책
캐시가 가득 차거나 오래되면 무엇을 버릴 것인가

캐시는 유한한 메모리다. 공간이 부족하면 **무엇을 버릴지(교체, Eviction)**, 시간이 지나면 **언제 버릴지(만료, Expiration)** 를 정해야 한다. 둘은 기준이 다르다 — 교체는 **공간** 기준, 만료는 **시간** 기준. 이름이 비슷해 섞기 쉽지만 언제나 따로 설계하고 함께 건다.

> **이 인덱스의 경계**: TTL은 세 얼굴이 있다. [04]에서는 "무효화 수단"(원본 변경에 맞추는 도구), 여기서는 "만료 정책"(오래된 값을 시간으로 버리는 규칙), [06]에서는 "장애 유발 요인"(동시 만료 → 아발란치). 이 인덱스는 만료 정책과 공간 교체 정책만 다룬다.

---

## 교체(Eviction) — 공간이 부족할 때 무엇을 버리나

| 정책 | 버리는 것 | 특징 | 적합한 곳 |
|---|---|---|---|
| **LRU** (Least Recently Used) | 가장 **오래 안 쓴** 것 | 가장 널리 쓰임. "최근에 읽힌 건 또 읽힌다"는 지역성 가정 | 범용 기본값 |
| **LFU** (Least Frequently Used) | 가장 **적게 쓰인** 것 | 인기도 기반. 일시적 스파이크에 밀려나지 않음 | 인기 콘텐츠·랭킹처럼 접근 빈도 격차가 클 때 |
| **FIFO** | 먼저 **들어온** 것 | 접근 패턴 무시, 구현 단순 | 단순 구현이 필요한 특수 상황 |

실무 기본값은 **LRU + TTL 조합**이다 — 공간 관리는 LRU가, 신선도는 TTL이 맡는다.

### Redis의 교체: maxmemory-policy

Redis는 `maxmemory` 도달 시의 행동을 `maxmemory-policy`로 정한다. 자주 쓰는 것만:

| 정책 | 동작 |
|---|---|
| `noeviction` | 안 버리고 **쓰기 명령에 에러** (기본값. 캐시 용도엔 부적합) |
| `allkeys-lru` | **모든 키** 중 LRU로 버림 — 순수 캐시 용도의 정석 |
| `volatile-lru` | **TTL 있는 키만** LRU로 버림 — 캐시와 영속 데이터를 한 Redis에 섞을 때 |
| `allkeys-lfu` | 모든 키 중 LFU로 버림 (Redis 4.0+) |

- Redis의 LRU/LFU는 정확한 알고리즘이 아니라 **표본 추출 근사**다(성능을 위해 몇 개만 뽑아 비교). 캐시 용도로는 충분하다
- `volatile-*` 정책인데 TTL 있는 키가 하나도 없으면 `noeviction`처럼 동작해 쓰기 에러가 난다 — "TTL을 항상 걸어둔다"는 규칙([02], [04])이 여기서도 안전장치가 된다

### Caffeine의 교체: W-TinyLFU

Caffeine은 LRU도 LFU도 아닌 **W-TinyLFU**를 쓴다 — 최근성(LRU 계열)과 빈도(LFU 계열)를 결합해 두 정책의 약점을 보완한 알고리즘으로, 대부분의 워크로드에서 LRU보다 히트율이 높다. `maximumSize`(크기 기반)를 걸면 자동 적용된다. 우리는 Caffeine을 **L1 로컬 캐시로 도입**하므로([07]) 이것이 L1의 교체 정책이다 — `maximumSize`는 1GB 힙 보호를 위해 필수.

## 만료(Expiration) — 시간이 지나면 버린다

- **TTL**: 키마다 "이 값은 N시간까지만 유효"를 선언. 신선도가 중요한 데이터의 기본 장치
- Redis의 만료 처리 방식 두 가지가 **함께** 돈다:
    - **Lazy(수동)**: 키에 접근하는 순간 만료 확인 후 삭제
    - **Active(능동)**: 백그라운드에서 주기적으로 TTL 있는 키를 표본 추출해 만료분 삭제
    - → 만료됐지만 접근도 표본 추출도 안 된 키가 **잠시 메모리에 남아 있을 수 있다** (신선도는 지켜짐 — 읽는 순간엔 없다고 판정)
- TTL 값 자체를 어떻게 정하는가: "**얼마나 오래된 값까지 허용 가능한가**"의 답이 곧 TTL ([01]의 신선도 허용, [04]의 무효화 설계와 같은 질문의 다른 얼굴)
- 여러 키의 TTL이 같은 순간에 끝나면 장애가 된다(아발란치) → jitter로 분산 → [06]

## 내 상황 분석

| 조건 | 내용 | 교체·만료 설계에 주는 의미 |
|---|---|---|
| Redis 설정 현황 | **이미 64mb + `allkeys-lru` + 비영속으로 운영 중** (AI 임시저장 draft 용도로 도입, 1GB EC2 보호 목적) | 교체 정책이 이미 캐시 정석으로 설정돼 있음 — 새로 정할 것이 없다 |
| 한 Redis 공유 | 전시 캐시가 draft 키와 **같은 메모리 풀**을 씀 | 메모리가 차면 LRU가 용도 구분 없이 버림 → 전시 캐시가 draft에 밀리거나 그 반대가 가능 |
| 캐시 데이터 크기 | 목록 6키 × 1페이지(20건 내외) ≈ 수십 KB + 상세 수십 건 ≈ 수백 KB | **64mb의 1%도 안 됨** — 교체가 실제로 발동할 일이 거의 없다 |
| 캐시 층 구성 | L1 로컬(Caffeine) + L2 공유 Redis 2단 ([07]) | TTL이 층마다 역할이 다름 — L2는 사고 대비 상한, L1은 방송 유실 시 불일치 상한 |
| TTL 결정(기존) | L2: 목록 25h·상세 6h ([02]·[04]) / L1: 목록 1h·상세 10m ([07]) | 만료 정책은 이미 결정됨 — 여기서는 검증만 |
| 키 개수 | 고정 6개 + 상세 단건들 | LFU가 이득을 낼 만큼의 키 다양성 자체가 없음 |

핵심: 내 상황에서 교체·만료 정책은 **"새로 설계할 것"이 아니라 "이미 있는 설정이 전시 캐시와 충돌하지 않는지 확인하는 것"** 이다. 확인 결과 충돌 없음 — 데이터가 작아 교체는 사실상 발동하지 않고, 발동하더라도 `allkeys-lru`가 "자주 읽히는 키를 남기는" 방향으로 동작하므로 매일 전 사용자가 치는 전시 목록 키는 살아남는 쪽이다.

## 내 상황 추천

### 교체: 기존 `allkeys-lru` 그대로 (변경 없음)

- 전시 캐시와 draft가 한 풀을 쓰지만, 합쳐도 64mb에 한참 못 미친다. 정책을 나누겠다고 Redis를 분리하거나 `volatile-lru`로 바꾸는 건 지금 규모에서 순수 복잡도 비용
- 단 하나 지킬 규칙: **전시 캐시 키에도 TTL을 반드시 건다.** (이미 [04]에서 결정) — 만에 하나 `volatile-*`로 정책을 바꾸게 돼도 안전하고, "죽는 방법이 없는 키"를 만들지 않는 원칙과도 일치

### 만료: 층별 TTL — L2는 사고 대비, L1은 불일치 상한

2단 배치([07])에서는 TTL이 층마다 **다른 일을 한다**. L2 TTL은 "배치·이벤트가 실패했을 때 옛 값이 영원히 남지 않게 하는 최후 방어선"이고, L1 TTL은 "무효화 방송이 유실됐을 때 서버 간 불일치가 지속되는 시간의 상한"이다.

| 키 | L1 TTL (Caffeine) | L2 TTL (Redis) | 이 숫자가 맞는 이유 |
|---|---|---|---|
| 목록 6종 | **1h** | **25h** | L2: 갱신 주기(24h)보다 약간 길게 — 정상 경로에선 배치 refresh가 만료 전에 새 값을 덮어써 발동할 일이 없다 ([04]). L1: 방송 유실 시 그 서버만 최대 1시간 옛 값 — 카카오페이의 로컬 1h와 같은 근거 |
| 상세 | **10m** | **6h** | 관리자 수정 시 이벤트 evict(양층+방송)가 주 수단이고 TTL은 유실 대비. 상세는 신선도 요구가 높아 양층 모두 목록보다 짧다 |

- 상세 L2 TTL을 1h가 아닌 6h로 두는 이유: 이벤트 evict가 있는 한 TTL은 "사고 시 옛 값 노출 상한"일 뿐이다. 관리자 수정 빈도(저빈도)와 수정 내용(가격·위치 — 몇 시간 어긋나도 치명적이지 않음)을 볼 때, 1h로 줄여 얻는 것보다 재적재(Miss) 빈도만 는다
- L1 TTL은 신선도가 아니라 **방송 유실 시 불일치 상한**이 기준이다 — 방송이 정상이면 L1은 TTL 전에 evict된다
- L2 TTL에 jitter(랜덤 수십 분)를 더할지는 [06 아발란치]에서 결정 (L1은 서버별로 채워지는 시각이 달라 동시 만료 문제가 약함)

### 결정 및 근거 (포트폴리오용 메모)
- **결정**: L2 교체는 기존 `allkeys-lru` 유지(변경 없음), L1 교체는 Caffeine W-TinyLFU + `maximumSize`(필수). 만료는 층별 — 목록 L1 1h·L2 25h, 상세 L1 10m·L2 6h. 모든 캐시 키에 TTL 필수
- **근거**: 캐시 데이터 총량(수백 KB)이 maxmemory(64mb)와 1GB 힙 어느 쪽에도 부담이 아니라 교체는 사실상 발동하지 않으며, 발동해도 LRU/W-TinyLFU가 고빈도 접근 키(전시 목록)를 보존하는 방향으로 동작한다. L2 TTL은 무효화([04])의 최후 방어선, L1 TTL은 방송 유실 시 불일치 상한([07])이라는 서로 다른 역할에 맞춰 층별로 설정했다
- **제약사항**: draft와 메모리 풀을 공유하므로, 캐시 대상을 크게 늘리면(예: 여러 페이지·필터 조합 캐시) 사용량 재계산 필요. `INFO memory`·`evicted_keys` 모니터링으로 교체 발동 여부를 감시 → [10 지표와 모니터링]
- **기각한 선택지**: `volatile-lru` 전환(draft·캐시 모두 TTL을 걸므로 실익 없음) / LFU 전환(키 6개+α에 빈도 통계가 무의미) / Redis 인스턴스 분리(1GB EC2에서 메모리 낭비, 지금 규모에 과설계)
