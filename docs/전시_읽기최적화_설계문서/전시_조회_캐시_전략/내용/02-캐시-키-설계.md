# 02 캐시 키 설계
캐시를 어떤 이름으로 저장할 것인가

## 키 네이밍 규칙
- 기본 형태: `도메인:엔티티:식별자` (예: `product:123`, `exhibition:list:page=1`)
- 서비스 prefix를 맨 앞에 붙이면 한 Redis를 여러 용도로 쓸 때 충돌 방지 (예: `yeowun:...`)
- 소문자 + `:` 구분자로 계층을 표현. 계층 순서는 "넓은 것 → 좁은 것" (도메인 → 화면/용도 → 조건)

## 키 설계 시 고려해야 할 것들

### 1. 정규화 (Canonical Key)
- 같은 조회는 반드시 같은 키가 되어야 함. 파라미터 순서나 기본값 표기 차이로 키가 갈라지면 히트율이 떨어지고 같은 데이터가 중복 저장됨
    - 예: `?sort=latest&genre=all` 과 `?genre=all&sort=latest` 와 `?sort=latest`(genre 생략) → 셋 다 같은 키여야 함
- 해결: 키 생성 함수 한 곳에서만 키를 만들고, 그 안에서 (1) 파라미터를 정해진 순서로 정렬, (2) 생략된 파라미터는 기본값으로 채움

### 2. 키 폭발 차단 — 화이트리스트
- 목록 API는 필터 × 정렬 × 페이지 조합만큼 키가 늘어남 (키 폭발)
- 조합 키가 많을수록 무효화가 어려워짐 → [04 캐시 무효화]
- 모든 조합을 캐시하지 말고, **캐시할 조합을 미리 열거(화이트리스트)** 하고 나머지는 캐시를 우회해서 DB로 직행
- 키 설계로 이를 강제할 수 있음: 화이트리스트에 없는 조합은 키 생성 함수가 키를 만들지 않음(= 캐시 안 함)

### 3. 버전 / 네임스페이스
- 키에는 버전을 넣을 수 있음 (`v2:product:123`) — 배포 시 스키마(직렬화 포맷)가 바뀌면 버전만 올려 일괄 무효화
- 버전을 "데이터 세대"로도 쓸 수 있음: 데이터가 통째로 갈릴 때 새 버전 키에 채우고 포인터만 교체 → 아래 [내 상황 추천] 옵션 B
- 옛 버전 키는 지우러 다니지 말고 TTL로 자연 소멸시킴

### 4. TTL과 키의 관계
- 키 스킴을 정할 때 "이 키는 어떻게 죽는가"를 같이 정해야 함 (명시 삭제로 죽는 키인지, TTL로만 죽는 키인지)
- 명시 삭제가 주 수단이어도 TTL은 보조 안전장치로 항상 걸어둠 → [04 캐시 무효화]

### 5. 금지·주의 사항
- 사용자 입력 문자열을 검증 없이 키에 그대로 넣지 않기 (구분자 `:` 포함 문자열이 들어오면 계층이 깨짐)
- `KEYS pattern` 으로 키를 찾는 운영은 금지 (Redis 블로킹). 패턴 삭제가 필요해지는 설계라면 버전 네임스페이스로 바꿀 신호
- 키를 무한정 길게 만들지 않기 — 조건이 많으면 조건부를 해시로 축약 가능하나, 화이트리스트 방식이면 애초에 필요 없음

## 내 상황 분석

| 조건 | 내용 | 키 설계에 주는 의미 |
|---|---|---|
| 갱신 주기 | 매일 새벽 1시 배치로 전시 적재, 그 외 거의 불변 | 무효화 시점이 하루 1번으로 예측 가능 → 키를 "하루 단위 세대"로 볼 수 있음 |
| 캐시 대상 | 홈 3종 + 탐색 정렬 3종의 1페이지 (필터·장르 전체 고정) | 조합이 6~7개로 유한·고정 → 키 폭발 걱정 없음, 화이트리스트가 곧 키 목록 |
| 서버 | Spring 2대 + **L1 로컬(Caffeine) + L2 공유 Redis 2단**([07]) | L2는 무효화 1번에 전 서버 반영. L1은 서버마다 있으므로 **같은 키 문자열을 Pub/Sub으로 방송**해 각 서버가 자기 L1만 지운다 — L1·L2·방송이 한 키 문자열을 공유하는 것이 전제 |
| 상세 조회 | **캐시함**([01]의 결정) — 관리자 수정 시에만 변경, 저빈도 | 전시 id 기반 단건 키 → 임의 조합이 아니라 키 폭발 없음. 무효화도 "그 키 하나"로 명확 → [04] |

핵심: 내 캐시 대상은 "임의 조합"이 아니라 **미리 아는 고정 목록**이다. 따라서 파라미터를 조립하는 범용 키보다, **열거 가능한 고정 키**가 단순하고 안전하다.

## 내 상황 추천

### 추천 키 스킴 (고정 키 열거)

```
yeowun:home:banners                  # 배너 목록
yeowun:home:ending-soon              # 곧 끝나는 전시 목록
yeowun:home:new-this-month           # 이번달 신규 전시 목록
yeowun:explore:latest:p1             # 최신순 1페이지 (전체 필터)
yeowun:explore:ending:p1             # 종료순 1페이지 (전체 필터)
yeowun:explore:popular:p1            # 인기순 1페이지 (전체 필터)
yeowun:exhibition:detail:{id}        # 전시 상세 단건 (id별 — 예: yeowun:exhibition:detail:127)
```

- `page=1`, `filter=전체` 같은 파라미터를 키에 조립하지 않는 이유: 캐시하는 조합이 이것뿐이므로, 조건을 키에 표현하는 대신 "이 키 = 이 조합"을 코드(enum/상수)로 고정하는 게 더 명확함
- 상세 키만 예외적으로 파라미터(`{id}`)가 들어감 — 단일 식별자 하나라 정규화 문제(순서·기본값 차이)가 생길 여지가 없고, id별 키 수는 전시 수만큼으로 유한. 무효화도 관리자 수정 시 "그 id 키 하나"로 명확 → [04]
- 나중에 2페이지나 장르 필터를 캐시하게 되면 그때 `yeowun:explore:latest:genre=media:p2` 식으로 확장 (정규화 규칙 1번 적용)

### 갱신 전략과 키: 두 가지 옵션

**옵션 A — 고정 키 + 배치 후 재적재 (추천, 단순함)**
- 새벽 배치 완료 시점에 6개 키를 삭제하거나 새 값으로 덮어쓰기(갱신)
- TTL 25시간을 보조 안전장치로 설정 (배치가 실패해도 하루 지난 데이터가 영원히 남지 않음, 24h보다 약간 길게 잡아 배치 지연에 여유)
- 장점: 구현 최소, 키 6개라 관리 쉬움 / 한계: 삭제 방식이면 배치 직후 첫 조회가 Miss → 배치에서 삭제 대신 **새 값으로 즉시 채워넣으면(워밍)** Miss도 없음 → [08 캐시 워밍]

**옵션 B — 날짜(세대) 버전 키 + 포인터 교체 (확장 옵션)**
```
yeowun:list:version                      → "20260804"   (현재 세대 포인터)
yeowun:20260804:explore:latest:p1        (세대별 데이터 키, TTL 48h)
```
- 배치가 새 날짜 키들에 데이터를 모두 채운 뒤, 마지막에 포인터 값만 교체
- 장점: 교체가 원자적 — 배치 도중에도 사용자는 어제 세대를 온전히 보고, 전환 순간 모든 목록이 동시에 새 세대로 바뀜 (목록 간 옛값/새값 섞임 없음). 옛 세대는 TTL로 자연 소멸
- 비용: 조회마다 포인터 1회 추가 조회(또는 로컬에 짧게 캐시), 구현 복잡도 증가
- 지금 규모(키 6개, 새벽 트래픽 낮음)에는 과할 수 있으나, "배치 중 목록 간 정합성"이 문제로 확인되면 도입

### 결정 및 근거 (포트폴리오용 메모)
- **결정**: 목록은 옵션 A(고정 키 6개 + 배치 완료 후 갱신 방식 재적재 + TTL 25h)로 시작. 상세는 `yeowun:exhibition:detail:{id}` 단건 키(TTL은 목록보다 짧게 → [05])
- **근거**: 캐시 대상이 고정 6개 키 + id 단건 키로 유한하고, 갱신 시점이 예측·인지 가능(목록=하루 1회 배치, 상세=관리자 수정)하므로 범용 키 조립·버전 네임스페이스는 현 단계에서 복잡도 대비 이득이 없음. 배치 중 목록 간 정합성 요구가 생기면 옵션 B로 확장할 수 있도록 키 생성을 한 함수에 모아둠
- **제약사항**: L2(공유 Redis)는 갱신 1번에 전 서버 반영되지만, L1(각 서버 Caffeine)은 같은 키 문자열의 무효화 방송 + 짧은 TTL로 동기화한다 → [07 배치 전략]. 키 문자열이 세 곳(L1·L2·방송)의 공용 계약이므로 키 생성 함수 밖에서 키를 만들지 말 것

## 라이브러리별 키 설정 규칙과 코드

### 먼저 알아야 할 차이: Caffeine 키 vs Redis 키

| | Caffeine (로컬) | Redis (원격) |
|---|---|---|
| 키의 실체 | JVM 안의 **객체** (`equals`/`hashCode`로 비교) | 직렬화된 **바이트/문자열** |
| 키 정규화 필요성 | 객체가 같으면 자동으로 같은 키 | 문자열이 한 글자만 달라도 다른 키 → 정규화가 더 중요 |
| 무효화 범위 | 그 서버 JVM만 | 모든 서버 공통 |
| 내 상황 적합도 | 단독으론 2대 서버 불일치 발생 → [07] | **주 캐시로 적합** (공유) |

두 방식 모두 Spring Cache 추상화(`@Cacheable`)를 쓰면 **키 생성 코드는 동일**하고, 뒤에 붙는 CacheManager만 갈아끼우면 된다. 아래 A는 공통(키 만드는 법), B/C는 각 저장소 연결이다.

### A. Spring Cache 공통 — 키를 만드는 3가지 방법

```java
// 1) 기본 KeyGenerator (SimpleKeyGenerator)
//    - 파라미터 0개 → SimpleKey.EMPTY
//    - 1개 → 그 값 자체
//    - 2개+ → 모든 파라미터를 담은 SimpleKey
//    주의: cacheName이 다르면 파라미터가 같아도 안 부딪힘. 하지만
//    같은 cacheName에 시그니처가 다른 두 메서드가 있으면 충돌 가능
@Cacheable("exhibitions")
public List<Exhibition> findLatest() { ... }

// 2) SpEL로 키 직접 지정 (가장 많이 씀)
@Cacheable(value = "exhibitions", key = "'latest:p1'")
public List<Exhibition> findLatestFirstPage() { ... }

// 파라미터 조합 — '#파라미터' 로 접근, 문자열은 + 로 연결
@Cacheable(value = "exhibitions",
           key = "#sort + ':genre=' + #genre + ':p' + #page")
public List<Exhibition> findList(String sort, String genre, int page) { ... }

// Pageable을 그대로 키에 쓰면 위험 (아래 '정규화' 주의 참고)
@Cacheable(value = "exhibitions",
           key = "#pageable.pageNumber + '-' + #pageable.pageSize")
public Page<Exhibition> findAll(Pageable pageable) { ... }

// 3) 커스텀 KeyGenerator (여러 메서드에 같은 규칙을 강제할 때)
@Component("exhibitionKeyGen")
public class ExhibitionKeyGenerator implements KeyGenerator {
    @Override
    public Object generate(Object target, Method method, Object... params) {
        // 여기서 정규화(정렬·기본값 채우기)를 한 곳에 몰아넣는다
        return method.getName() + ":" +
               Arrays.stream(params).map(String::valueOf)
                     .collect(Collectors.joining(":"));
    }
}
// 사용: key 와 keyGenerator 는 동시 지정 불가 (예외 발생)
@Cacheable(value = "exhibitions", keyGenerator = "exhibitionKeyGen")
public List<Exhibition> findList(String sort, String genre, int page) { ... }
```

> **정규화 주의 (앞의 고려사항 1번과 연결)**: `key="#pageable..."` 처럼 입력을 그대로 키에 넣으면, `sort` 생략 여부·순서 차이로 같은 조회가 다른 키가 되어 히트율이 떨어진다. SpEL 안에서 즉석 조립하지 말고 (2)의 명시 문자열이나 (3)의 KeyGenerator로 정규화를 강제하는 편이 안전하다. 내 경우엔 조합이 6개로 고정이므로 **(2)의 상수 키가 가장 단순**하다.

### B. Redis 캐시 연결 — 키 규칙의 핵심은 prefix와 직렬화

Spring Data Redis에서 `@Cacheable`의 최종 Redis 키는 기본적으로 **`cacheName::key`** 형태다 (콜론 2개 구분). 이 prefix 규칙과 직렬화를 `RedisCacheConfiguration`에서 정한다.

```java
@Configuration
@EnableCaching
public class RedisCacheConfig {

    private static final String APP_PREFIX = "yeowun:";

    @Bean
    public RedisCacheManagerBuilderCustomizer redisCustomizer() {
        return builder -> {
            RedisCacheConfiguration config = RedisCacheConfiguration.defaultCacheConfig()
                // 기본 TTL — 배치 주기(하루)보다 약간 길게 (보조 안전장치)
                .entryTtl(Duration.ofHours(25))
                // 키 prefix 규칙: yeowun:cacheName::key 형태로 강제
                //  → 여러 서비스가 같은 Redis를 써도 충돌 방지
                .computePrefixWith(cacheName -> APP_PREFIX + cacheName + "::")
                // 키는 사람이 읽을 수 있는 문자열로 (기본이 StringRedisSerializer라 보통 그대로 둠)
                .serializeKeysWith(SerializationPair.fromSerializer(new StringRedisSerializer()))
                // 값은 JSON으로 (기본 JDK 직렬화는 클래스 바뀌면 깨지고 사람이 못 읽음)
                .serializeValuesWith(SerializationPair.fromSerializer(
                        new GenericJackson2JsonRedisSerializer()))
                // null 캐싱 여부 — 패너트레이션 방어와 연결 → [06]
                .disableCachingNullValues();

            builder.cacheDefaults(config);
        };
    }
}
```

Redis 키 규칙에서 특히 기억할 것:
- **기본 prefix는 `cacheName::`** 다. `@Cacheable(value="exhibitions", key="'latest:p1'")` → 실제 Redis 키는 `exhibitions::latest:p1`. 위 설정을 적용하면 `yeowun:exhibitions::latest:p1`
- 여러 서버/서비스가 한 Redis를 공유하면 **앱 전역 prefix 필수** (안 그러면 서로 캐시를 덮어씀). 내 상황: Spring 2대가 같은 Redis → prefix로 네임스페이스 격리
- **`KEYS` 명령 주의** — Spring 캐시의 `@CacheEvict(allEntries=true)`(전체 삭제)는 내부적으로 `KEYS`를 쓸 수 있고, 키가 많으면 Redis를 블로킹시킨다. `RedisCacheWriter`를 `BatchStrategy`(SCAN 기반)로 바꾸면 완화. 내 상황은 키가 6개뿐이라 문제 없지만, 패턴 삭제가 필요해지면 버전 네임스페이스(옵션 B)로 바꿀 신호
- prefix를 아예 끄려면 `.disableKeyPrefix()` (공유 캐시를 여러 앱이 같은 이름으로 볼 때만)

**Spring 추상화를 안 쓰고 직접 다룰 때** (분산 Lock, Double Delete 등 세밀한 제어가 필요하면 → [04], [06]):
```java
private final RedisTemplate<String, Object> redisTemplate;

public List<Exhibition> getLatest() {
    String key = "yeowun:explore:latest:p1";              // 키를 코드로 완전 통제
    Object cached = redisTemplate.opsForValue().get(key);
    if (cached != null) return (List<Exhibition>) cached;

    List<Exhibition> data = repo.findLatestFirstPage();
    redisTemplate.opsForValue().set(key, data, Duration.ofHours(25));
    return data;
}
```

### C. Caffeine 캐시 연결 — 키는 객체, prefix 개념 없음

```java
@Configuration
@EnableCaching
public class CaffeineCacheConfig {

    @Bean
    public CacheManager cacheManager() {
        CaffeineCacheManager manager = new CaffeineCacheManager("exhibitions");
        manager.setCaffeine(Caffeine.newBuilder()
                .maximumSize(500)                 // 크기 기반 축출 (LRU 계열) → [05]
                .expireAfterWrite(Duration.ofHours(25)));
        return manager;
    }
}
```

Caffeine 키 규칙에서 기억할 것:
- prefix·직렬화 개념이 없다. `@Cacheable`의 `key`로 만든 객체가 JVM 안에서 그대로 키가 된다 (`equals`/`hashCode`로 비교)
- 그래서 키로 쓰는 값이 커스텀 객체면 `equals`/`hashCode`가 제대로 구현돼 있어야 함. **문자열/숫자 키를 쓰면 안전**
- 서버마다 독립된 메모리 → **2대 서버가 서로 다른 값을 가질 수 있음**. 그래서 단독으로는 못 쓰고, **L1으로 쓰되 무효화 방송 + 짧은 TTL로 불일치를 관리**한다 → [07]

### 내 상황에 맞는 선택

- **배치 = L1 Caffeine + L2 공유 Redis 2단** ([07]의 결정, 카카오페이식). 키 관점의 핵심: **L1·L2·무효화 방송이 전부 같은 키 문자열 하나를 쓴다** — Redis 키로 쓰는 `yeowun:explore:latest:p1`을 Caffeine의 문자열 키와 Pub/Sub 메시지 본문으로도 그대로 사용한다. 키 조립을 한 곳(선언 enum의 `key()`)에 강제해야 하는 이유가 하나 더 늘어난 것
- Spring `@Cacheable`은 쓰지 않는다 — 2단 조회 + 방송 + 선언별 TTL 조합을 어노테이션으로 표현하기 어려워, 키를 완전히 통제하는 CacheManager 직접 제어를 택했다 (구현 전체 → [캐시매니저_설계_및_구현.html]). 위 A(SpEL)·B(Redis 설정)·C(CaffeineCacheManager)는 Spring 추상화를 쓸 경우의 교과서 지식으로 보존
