# 03 캐시 읽기/쓰기 패턴
캐시와 DB를 어떤 순서로 오갈 것인가

캐시와 DB 사이의 데이터 흐름을 정하는 구조 패턴. 정합성 100%는 불가능하고, **"얼마나 빨리 일치시킬 것인가"** 가 핵심 설계 포인트다. 패턴별 트레이드오프를 이해하고 비즈니스 요구에 맞는 전략을 선택한다.

> **이 인덱스의 경계**: 여기서는 "캐시와 DB를 어떤 순서로 오갈 것인가"라는 *구조*만 다룬다. "원본이 바뀌었을 때 캐시를 어떻게 지울 것인가"라는 *방법론*(제거 vs 갱신, TTL, 이벤트, Double Delete)은 → [04 캐시 무효화]. 두 인덱스가 겹쳐 보이지만, 03은 "평상시 흐름", 04는 "변경 순간의 대응"으로 역할이 다르다.

---

## 읽기 패턴

### Cache-Aside (= Look-Aside)
1. 데이터가 캐시에 있는지 확인 (Look)
2. 있으면 (Hit) → 바로 반환 (Fast!)
3. 없으면 (Miss) → DB에서 조회해서 캐시에 저장 (Aside)

- 다음 읽기 요청 시 자연스럽게 최신 데이터로 캐시가 재생성
- 읽기 요청이 많은 서비스의 표준 패턴
- 애플리케이션이 캐시와 DB를 **직접** 오간다 (캐시는 그냥 저장소일 뿐, 아무것도 모름)
- DB 업데이트 후에는 갱신이 아니라 무효화 — 캐시를 "삭제"하는 게 핵심 → [04 캐시 무효화]

**장점**: 구현이 단순하고 캐시 장애 시에도 DB로 폴백되어 서비스가 죽지 않음 (캐시가 죽어도 읽기는 가능)
**단점**: 첫 요청은 항상 Miss (Cold Start → [08 캐시 워밍]), 무효화를 애플리케이션이 직접 책임져야 함

```java
// Cache-Aside 읽기 (Spring 추상화 없이 직접)
public List<Exhibition> getLatest() {
    String key = "yeowun:explore:latest:p1";
    Object cached = redisTemplate.opsForValue().get(key);
    if (cached != null) {                       // 1~2. Look & Hit
        return (List<Exhibition>) cached;
    }
    List<Exhibition> data = repo.findLatestFirstPage();  // 3. Miss → DB
    redisTemplate.opsForValue().set(key, data, Duration.ofHours(25)); // Aside
    return data;
}

// Spring @Cacheable 도 내부적으로 Cache-Aside 로 동작한다
@Cacheable(value = "exhibitions", key = "'latest:p1'")
public List<Exhibition> getLatest() {
    return repo.findLatestFirstPage();
}
```

### Read-Through
1. 애플리케이션은 **캐시에만** 요청
2. 캐시에 없으면 **캐시 라이브러리가 자동으로** DB 조회 & 저장
3. 앱은 캐시만 바라봄 (로직 단순화)

- Cache-Aside와 결과는 같지만, DB 조회 책임이 앱 → 캐시 계층으로 넘어감
- 캐시 계층(또는 라이브러리)이 DB 로더를 알고 있어야 함
- 순수 Redis + Spring 조합에서는 잘 안 쓰이고, 로더를 등록하는 캐시 라이브러리(예: Caffeine의 `LoadingCache`)에서 자연스럽다

```java
// Caffeine LoadingCache — Read-Through의 대표 형태
LoadingCache<String, List<Exhibition>> cache = Caffeine.newBuilder()
    .expireAfterWrite(Duration.ofHours(25))
    .build(key -> repo.findByKey(key));   // Miss 시 캐시가 알아서 이 로더를 호출

List<Exhibition> data = cache.get("latest:p1");  // 앱은 DB를 모른다
```

> Cache-Aside vs Read-Through의 실질 차이는 "**Miss 시 DB를 누가 부르는가**"뿐이다. 앱이 부르면 Aside, 캐시가 부르면 Through.

## 쓰기 패턴

### Write-Through
- 캐시 + DB에 **동시에** 쓰기 (동기)
- 쓰기 느림 (두 곳을 다 기다림), 일관성 높음 (캐시와 DB가 항상 같음)
- 읽기가 항상 캐시에서 최신을 보장받아야 할 때

### Write-Behind (= Write-Back)
- 캐시에만 **먼저** 쓰고, DB는 **나중에** 비동기로 (배치/큐)
- 쓰기 빠름, 유실 위험
- 쓰기 지연이 0에 가까워 조회수 같은 대량 쓰기가 빈번한 곳에 효과적
- 단, 캐시 서버가 죽으면 아직 DB에 안 넘어간 데이터가 유실됨. 재시도 큐가 필요하고, **유실되어도 괜찮은 데이터에만** 적용

### Write-Around
- DB에만 쓰고, 캐시는 **읽기 시점에** 채움 (Cache-Aside의 쓰기 쪽 짝)
- 쓰기 빠름, 첫 읽기는 Miss
- "쓰고 나서 바로 안 읽는" 데이터에 적합 (자주 안 읽히는데 캐시를 채워봐야 낭비)

> **용어 교정 (사전 정리 시 발견)**: 원문에서 "Refresh-Ahead(Write-Around)"로 묶여 있었으나 둘은 다른 개념이다.
> - **Write-Around** = *쓰기* 패턴 (DB에만 쓴다)
> - **Refresh-Ahead** = 만료 *전에* 미리 캐시를 갱신하는 *읽기 최적화* 기법 → PER과 같은 계열이므로 [06 캐시 장애 패턴]의 사전 갱신 참조

### 패턴 비교

| 패턴 | 쓰기 속도 | 일관성 | 유실 위험 | 적합한 곳 |
|---|---|---|---|---|
| Write-Through | 느림 | 높음 | 없음 | 읽기 최신 보장 필요 |
| Write-Behind | 빠름 | 낮음(지연) | 있음 | 대량 쓰기, 유실 허용 |
| Write-Around | 빠름 | — | 없음 | 쓰고 바로 안 읽음 |

## 내 상황 분석

| 조건 | 내용 | 패턴 선택에 주는 의미 |
|---|---|---|
| 쓰기 주체 | 매일 새벽 1시 **배치**만 씀 (사용자 실시간 쓰기 없음) | 쓰기 성능·유실 걱정이 사실상 없음 → Write-Behind 등 쓰기 최적화 패턴 불필요 |
| 읽기 비율 | 조회가 압도적 (전형적 읽기 위주) | Cache-Aside가 정석 |
| 갱신 시점 | 하루 1번, 예측 가능 | "쓰기 패턴"이라기보다 "배치가 캐시를 다시 채우는 워밍"에 가까움 → [08] |
| 상세 조회 | **캐시함**([01]) — 관리자 수정 시에만 변경 | 조회는 목록과 같은 Cache-Aside, 수정 시점엔 이벤트 기반 evict → [04] |

핵심: 내 서비스는 **사용자 쓰기 경로에 캐시가 끼지 않는다.** 데이터는 새벽 배치로만 바뀌므로, 위 "쓰기 패턴"(Write-Through/Behind/Around)은 교과서 지식으로만 알아두면 되고, 실제로 설계할 것은 **읽기 패턴(Cache-Aside) + 배치 시점 재적재**다.

## 내 상황 추천

### 읽기 = Cache-Aside (확정)
- 이유: 읽기 위주 서비스의 표준이고, 캐시가 죽어도 DB로 폴백되어 서비스가 안 죽는다. 배치는 **L1 로컬(Caffeine) → L2 공유 Redis → DB 2단**([07]) — L1 Miss는 L2가, L2 Miss는 DB가 받고, Hit한 계층 위로는 backfill한다
- 첫 Miss는 배치 직후 워밍으로 없앤다 → [08]

### "쓰기" = 배치의 캐시 재적재 (Write-Through의 배치 버전)
새벽 배치가 DB 적재를 끝낸 **직후**, 6개 목록 캐시를 새 값으로 다시 채운다. 이건 실시간 Write-Through는 아니지만 성격이 비슷하다 — DB를 쓰면서 캐시도 같이 최신으로 맞추기 때문.

```
새벽 1시 배치:
  1) 전시 데이터 DB 적재
  2) (적재 성공 후) 캐시 6개 키를 새 값으로 재적재  ← 여기
     - 삭제(evict)만 하면 배치 직후 첫 사용자가 Miss를 맞음
     - 새 값으로 채우면(warm) Miss 없이 바로 Hit
```

- 이 방식의 무효화 관점 세부(삭제 vs 갱신, 실패 시 롤백)는 → [04 캐시 무효화]
- 재적재를 어디서 트리거하고 완료 전 트래픽을 어떻게 다룰지는 → [08 캐시 워밍]

### 결정 및 근거 (포트폴리오용 메모)
- **결정**: 읽기는 Cache-Aside, "쓰기"는 새벽 배치 완료 후 목록 캐시 재적재(갱신) 방식
- **근거**: 사용자 실시간 쓰기가 없고 데이터 변경이 하루 1회 배치로 한정되므로, 쓰기 최적화 패턴(Write-Behind 등)은 불필요하다. 읽기 위주 트래픽에는 Cache-Aside가 표준이며 캐시 장애 시 DB 폴백으로 가용성이 유지된다. 실시간 Write-Through 대신 배치 시점 재적재를 택해, 하루 1회의 예측 가능한 갱신 창에서 정합성을 확보한다
- **제약사항**: Cache-Aside는 무효화를 애플리케이션이 책임진다 → 배치 재적재 로직과 TTL 보조 장치로 커버 (→ [04])
- **기각한 선택지**: Read-Through(로더 등록 필요, 순수 Redis+Spring엔 부자연), Write-Behind(유실 위험, 쓰기 트래픽이 없어 이득 없음)
