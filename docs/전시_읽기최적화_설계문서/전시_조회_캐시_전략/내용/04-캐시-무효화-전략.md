# 04 캐시 무효화
원본이 바뀌면 캐시를 어떻게 맞출 것인가

원본 데이터가 바뀌었을 때 캐시 정합성을 지키는 법. 정합성이 깨지는 순간은 이렇다: **DB 값 수정 → 캐시는 옛 값 유지 → 사용자는 옛 값 조회.** 무효화 설계의 핵심은 **오래된 값을 얼마나 허용할지** 결정하는 것이다.

> **이 인덱스의 경계**: [03 읽기/쓰기 패턴]이 "평상시 흐름의 구조"라면, 04는 "변경이 일어난 순간의 대응"이다. 캐시를 지우는/바꾸는 방법론만 여기서 다룬다.

---

## 쓰기 시점 처리: 제거 vs 갱신

수정이 일어났을 때 캐시를 어떻게 할지 두 갈래다.

- **제거(Evict)** — 수정할 때 캐시를 그냥 지운다. 다른 누군가가 조회할 때 캐시가 없으니 원본에서 새로 채워온다 (단순, 안전, 다만 다음 조회가 느릴 수 있음, 실무에서 자주 씀)
- **갱신(Update)** — 수정할 때 캐시도 새 값으로 바꾼다. 다음 조회 시 캐시 즉시 적중 (빠르지만 원본과 캐시 값을 정확히 맞춰야 함)

> 대부분의 실무 기본값은 **제거**다. 갱신은 캐시에 넣을 값을 계산하는 로직이 DB 조회와 어긋나면 오히려 틀린 값을 심게 되기 때문. 단, "다음 조회를 느리게 하고 싶지 않다"가 강할 때(내 배치 재적재처럼)는 갱신을 택한다.

## 무효화 수단 3가지

| 수단 | 방식 | 적합한 경우 |
|---|---|---|
| 쓰기 시점 무효화 | 수정 코드에서 직접 삭제/갱신 | 정확성이 중요할 때 |
| TTL | 시간이 지나면 자동 삭제 | 잠깐의 지연이 허용될 때 |
| 이벤트 기반 | 변경 이벤트에 반응해 즉시 제거 | 옛 값 노출 시간을 최소화하고 싶을 때 |

### TTL로 무효화
- 설정한 시간이 지나면 캐시 자동 삭제. 별도 무효화 코드 없이 구현이 단순하다
- 만료 전까지 옛값이 제공될 수 있으므로, **잠깐 늦어도 되는 데이터에 적합**, 항상 최신이어야 하는 데이터에는 부적합
- TTL은 세 인덱스에서 역할이 다르다: 여기선 "무효화 수단", [05]에선 "만료 정책", [06]에선 "장애 유발 요인(동시 만료)". 헷갈리지 말 것

### 이벤트 기반 무효화
- 이벤트 기반으로 즉시 제거하고, 이벤트 누락에 대비해 TTL을 보조 안전장치로 둔다 (TTL과 배타적이지 않다 — 같이 쓴다)
- TTL보다 옛 값 노출 시간을 최소화하는 방법

```java
@TransactionalEventListener(
    phase = TransactionPhase.AFTER_COMMIT)   // 핵심
public void handle(ProductChangedEvent event) {
    cacheManager.getCache("product")
        .evict(event.productId());
}
```

- 핵심은 **AFTER_COMMIT** — 트랜잭션이 확정된 뒤에 캐시를 지운다
- 커밋 전에 지웠다가 트랜잭션이 롤백되면, DB는 옛 값 그대로인데 캐시만 날아가 "멀쩡한 캐시를 헛되이 버리는" 문제가 생긴다

## 대표 문제: 순서 역전 레이스 컨디션

Cache-Aside의 "DB 업데이트 → 캐시 삭제" 패턴에서 발생하는 레이스 컨디션이다.

1. 스레드 A가 DB를 업데이트하고 캐시를 삭제하려는 순간
2. 스레드 B가 캐시 Miss로 DB를 조회하는데, **A의 업데이트 직전(구) 데이터**를 읽음
3. 스레드 A가 캐시를 삭제한 뒤, 스레드 B가 방금 읽은 **구 데이터를 캐시에 저장**
4. 결과적으로 DB는 최신인데 구 데이터가 TTL 만료까지 캐시에 남는다

```java
public void updateProduct(Long id, ProductUpdateDto dto) {
    repo.updateProduct(id, dto);          // 1. DB 업데이트
    cache.delete("product:" + id);        // 2. 캐시 삭제
    // 문제: 1과 2 사이에 다른 스레드가 구 데이터를 캐시에 저장할 수 있음
    // -> 캐시에 구 데이터가 TTL까지 남게 됨
}

// 반대 순서도 위험
public void updateProductV2(Long id, ProductUpdateDto dto) {
    cache.delete("product:" + id);        // 1. 캐시 먼저 삭제
    repo.updateProduct(id, dto);          // 2. DB 업데이트
    // 문제: 1과 2 사이에 다른 스레드가 캐시 Miss -> DB 조회(구 데이터)
    // -> 동일하게 구 데이터가 캐시에 남음
}
```

- 어느 순서로 해도 레이스 컨디션 가능성은 존재한다
- 실무에서는 **"DB 먼저 업데이트 → 캐시 삭제"** 가 상대적으로 안전 (DB가 진실의 원천이므로, 최악의 경우에도 "잠깐 옛 캐시"이지 "영영 어긋난 DB"는 아님)

### 완화책: Double Delete 패턴

```java
public void updateProduct(Long id, ProductUpdateDto dto) {
    cache.delete("product:" + id);        // 1. 캐시 선 삭제 (구 데이터 즉시 제거)
    repo.updateProduct(id, dto);          // 2. DB 업데이트

    // 3. 지연 후 캐시 재삭제 (레이스 컨디션으로 들어온 구 데이터 제거)
    CompletableFuture.delayedExecutor(500, TimeUnit.MILLISECONDS)
            .execute(() -> cache.delete("product:" + id));
}
```

- **1차 삭제** — 구 데이터를 즉시 제거해 대부분의 요청이 최신을 받도록 유도
- **2차 삭제** — 500ms 뒤 한 번 더 삭제해 레이스로 저장된 구 데이터 제거
- **지연 시간** — DB 복제 지연 + 캐시 쓰기 시간을 고려해 결정 (보통 300ms~1000ms)
- **한계** — 지연 시간 사이에는 여전히 구 데이터 노출 가능. 완벽하진 않고, "확률을 크게 낮추는" 완화책이다

## 분산 환경에서의 무효화 전파

서버가 여러 대면 "누가 무효화를 실행하고, 그게 모든 서버에 반영되는가"가 문제가 된다.

- **공유 캐시(Redis)** 를 쓰면: 한 곳에서 지우면 모든 서버에 즉시 반영 → 전파 문제 자체가 없음
- **로컬 캐시(Caffeine)** 를 쓰면: 한 서버에서 지워도 다른 서버의 로컬 캐시는 그대로 → 변경 이벤트를 모든 서버에 전파(pub/sub)해서 각자 무효화해야 함

이 선택(공유 vs 로컬)의 상세는 → [07 캐시 배치 전략]. 우리는 **L1 로컬 + L2 공유 Redis 2단**을 채택했으므로 두 문제를 다 안는다: L2는 한 번 갱신하면 끝이지만, **L1은 변경 시마다 Pub/Sub으로 방송해 각 서버가 자기 것을 지워야 하고, 방송 유실에 대비해 짧은 L1 TTL이 반드시 동행**한다.

## 내 상황 분석

| 조건 | 내용 | 무효화 설계에 주는 의미 |
|---|---|---|
| 변경 시점 | 새벽 1시 배치만 | 무효화 창이 하루 1번으로 예측 가능 → 실시간 무효화 로직 거의 불필요 |
| 변경 주체 | 사용자 실시간 쓰기 없음 | 순서 역전 레이스·Double Delete가 사실상 발생 안 함 |
| 캐시 저장소 | **L1 로컬(Caffeine) + L2 공유 Redis 2단** ([07]) | L2는 전파 문제 없음. L1은 서버마다 있어 **무효화 방송(Pub/Sub) + 짧은 L1 TTL(목록 1h·상세 10m)** 필요 |
| 지연 허용 | 조회 목록은 어느 정도 지연 허용 | TTL을 주 안전장치로 써도 됨 |
| 상세 조회 | 관리자 수정으로만 변경(가격·위치 등), 저빈도 | **캐시함** → 관리자 수정 시점 이벤트 기반 무효화 (아래 별도 전략) |

핵심: 내 무효화는 대상에 따라 두 갈래다. **목록**은 "새벽 배치가 끝나면 6개를 한 번 새로고침"하는 문제이고, **상세**는 "관리자가 고칠 때 그 키만 지우는" 문제다. 둘 다 변경 시점이 예측·인지 가능하다는 공통점 덕에 어렵지 않다. 다만 L1(로컬) 계층이 있으므로 **모든 변경은 "L2 처리 + 방송"이 한 쌍**이어야 한다 — 이 쌍을 CacheManager의 `refresh`/`evict` 두 동사에 내장해 방송을 잊을 방법을 없앤다(→ [캐시매니저_설계_및_구현.html]). 사용자 실시간 쓰기가 없으므로 레이스 컨디션·Double Delete는 **지금 구조에선 필요 없고**, 나중에 실시간 카운터(조회수 등)가 생길 때를 대비한 지식으로 남겨둔다.

## 내 상황 추천

### 주 전략: 배치 완료 후 재적재(L2 갱신 + L1 방송) + TTL 보조(양층)

```
새벽 1시 배치:
  1) 전시 데이터 DB 적재
  2) 적재 성공 확인 후 → 목록 6키를 refresh
       = L2(Redis)에 새 값 덮어쓰기(갱신)
       + Pub/Sub 방송 → 각 서버가 자기 L1 evict → 다음 조회가 L2에서 backfill
     실패 시 → 캐시를 건드리지 않음 (옛 값 유지가 빈 캐시보다 안전)
  + TTL 보조 2겹:
       L2 25시간  — 배치가 아예 안 돌아도 옛 값이 영원히 남지 않게 (최후 방어선)
       L1 1시간   — 방송이 유실돼도 그 서버의 불일치가 1시간을 못 넘게 ([07])
```

- **왜 L2는 제거가 아니라 갱신인가**: 제거만 하면 배치 직후 첫 사용자가 Miss를 맞아 DB로 몰린다(작게나마 스탬피드 → [06]). 값을 미리 채워 넣으면 DB행이 없다. 재적재 값은 배치가 방금 적재한 DB에서 바로 읽으므로 "갱신의 위험(캐시 값과 DB 불일치)"도 낮다
- **왜 L1은 갱신이 아니라 방송 evict인가**: 방송으로 새 값을 밀어 넣으면(갱신) 직렬화된 값 전파·순서 문제가 생긴다. "지워라"만 방송하면 각 서버가 다음 조회 때 L2에서 새 값을 당겨온다 — L2가 이미 새 값이라 Miss 비용도 Redis 1홉뿐. 카카오페이도 같은 방식(수신자는 evict만)이다
- **왜 TTL을 굳이 더 거는가**: L2 TTL은 배치 실패 시, L1 TTL은 방송 유실 시의 각각 최후 방어선. 정상 동작 시엔 발동하지 않고 사고 시에만 작동한다

### 결정 및 근거 (포트폴리오용 메모)
- **결정**: "배치 완료 후 refresh(L2 재적재 + L1 무효화 방송)" + "TTL 보조 2겹(L2 25h·L1 1h)". 상세는 이벤트 기반 evict(아래). Double Delete는 도입하지 않음
- **근거**: 데이터 변경이 하루 1회 배치 + 저빈도 관리자 수정으로 한정되어 무효화 창이 예측 가능하고, 사용자 실시간 쓰기가 없어 순서 역전 레이스가 발생하지 않는다. L1 도입([07])으로 방송이 필요해졌지만, 변경 이벤트가 하루 몇 건이라 방송 비용·유실 위험이 최소인 지점이고, 유실 피해는 L1 TTL이 1시간(상세 10분)으로 묶는다. "L2 처리 + 방송"을 CacheManager 두 동사에 내장해 무효화 경로가 구조적으로 하나뿐이다
- **제약사항**: 재적재와 DB 적재가 같은 순서로 묶여야 함(적재 성공 후에만 refresh). 배치 실패 시 캐시를 건드리지 않는 것이 핵심 규칙. **모든 변경 경로는 refresh/evict 경유** — DB 직접 수정 우회 시 방송이 안 나가 L1이 어긋난다
- **기각한 선택지**: Double Delete(사용자 동시 쓰기가 없어 방어할 레이스가 없음 — 실시간 수정 기능 추가 시 재검토), 방송으로 새 값 push(evict 방송보다 복잡하고 순서 꼬임 위험), Kafka·Streams 기반 무효화(전달 보장이 필요할 만큼 변경이 잦지 않음)

## 상세 조회의 무효화 (목록과 다른 전략)

상세는 목록과 변경 경로가 다르므로 무효화도 다르게 간다. (캐시 여부 자체의 결정 근거는 → [01 캐시 대상 선정])

- **변경 경로**: 관리자 수정만 (가격·위치 등). 실시간 카운터 없음, 저빈도, 변경 시점을 애플리케이션이 인지 가능
- **전략**: 관리자 수정 커밋 후 해당 상세 키만 **이벤트 기반 evict(양층 삭제 + 방송)** + 짧은 TTL 보조. 관리자 수정이 드물어 evict가 캐시 효율을 거의 해치지 않으므로, "항상 최신 보장"과 캐시 이득이 양립한다

```java
// 조회: Cache-Aside 2단 (목록과 동일 — CacheManager 경유)
public ExhibitionResult.Detail getDetail(Long id) {
    return cacheManager.getOrPut(ExhibitionCache.DETAIL, String.valueOf(id),
            () -> repo.findDetailById(id).map(ExhibitionResult.Detail::from).orElseThrow(...));
}

// 관리자 수정: 커밋 확정 후에만 무효화 (롤백이면 멀쩡한 캐시를 지우지 않는다)
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void handle(ExhibitionAdminUpdatedEvent event) {
    cacheManager.evict(ExhibitionCache.DETAIL, String.valueOf(event.exhibitionId()));
    // evict 내부 = L2 삭제 + 자기 L1 삭제 + Pub/Sub 방송 → 다른 서버의 L1까지 삭제
}
```

- 상세 TTL은 목록보다 짧게 — **L2 6h**(이벤트 유실 시 옛 값 노출 상한) + **L1 10m**(방송 유실 시 서버 간 불일치 상한). 상세가 목록보다 신선도 요구가 높으므로 양층 모두 짧다 ([05])
- **제약**: 관리자 수정 경로가 반드시 이 무효화 로직(evict = 양층+방송)을 거쳐야 함. DB를 직접 건드리는 우회 경로가 있으면 L2뿐 아니라 **두 서버의 L1까지** 어긋난다
- **주의(미래)**: 조회수·좋아요 같은 **실시간 카운터**가 추가되면 evict만으로는 부족해진다(초 단위로 무의미해짐). 그때는 정적 부분(캐시)과 동적 카운터(DB/별도 조회) 분리 설계로 전환
