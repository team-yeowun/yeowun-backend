## 분산 환경 스케줄러 중복 실행 제어

---

> 서버 2대의 스케줄러가 같은 아웃박스 행을 읽어 이벤트가 중복 발송되는 문제를 두고, 락 전략 다섯 가지를 같은 부하 실험 무대에서 한 번씩 재어 비교했습니다. 중복 200만 건에서 출발해 비관적 락, SKIP LOCKED, 배치 분할, 읽기 복제 분산을 차례로 검증하고, 최종적으로 중복 판정을 DB 밖(Redis 마커)으로 옮겨 중복 0건과 DB 락 대기 0을 얻었습니다.

## Problem

전시 수집은 수집에서 보강, 점검, 스테이징으로 이어지는 단계를 이벤트로 연결하고, 커밋과 발행 사이의 유실을 막기 위해 트랜잭션 아웃박스로 운영합니다. 아웃박스 행은 발송 스케줄러가 주기적으로 조회해 대기열로 내보내는데, 이 스케줄러는 인스턴스마다 하나씩 돕니다. 서버가 두 대가 되는 순간 같은 시각에 같은 미발행 행을 두 앱이 함께 읽습니다.

이 문제가 실제로 어떤 크기인지, 그리고 어떤 해법이 무엇을 대가로 요구하는지를 말이 아니라 수치로 판단하기 위해 **운영과 같은 구성(앱 2대 · MySQL master/replica · Redis)의 실험 무대**를 만들고, 미발행 100만 행을 적재한 뒤 락 전략만 바꿔 가며 한 번씩 돌렸습니다. 아무 제어가 없을 때 대기열에는 300만 건이 실렸습니다. 100만 건을 확정하는 데 발행이 세 번씩 나간 셈입니다.

요구는 두 가지였습니다. **중복을 차단할 것, 그리고 인스턴스를 늘린 만큼 처리량이 증가할 것.**

## Action

1. **비관적 락(FOR UPDATE)** — 중복은 0이 됐지만, 잠금을 잡은 한 대가 100만 행을 통째로 잠그고 409초 동안 발행하는 사이 다른 한 대는 선점 조회가 네 번 타임아웃(누적 200,315ms)으로 튕기며 한 건도 처리하지 못했습니다. 인스턴스를 늘려도 처리량은 한 대분이었습니다.
2. **SKIP LOCKED** — 읽기 단계의 대기는 사라졌고 두 인스턴스가 618,991건과 381,009건으로 갈라 집었습니다. 그러나 한쪽의 대량 트랜잭션이 커밋에서 잠금 대기로 롤백되면서, 이미 나간 발행은 되돌아가지 않아 중복 381,009건이 남았습니다.
3. **배치 크기 LIMIT 500** — 한 트랜잭션이 잠그는 행을 500개로 줄이자 중복과 롤백과 락 대기가 모두 0이 됐고, 힙 사용량도 1.3GB대에서 258MB로 내려갔습니다. 대신 조회 왕복이 실측 2,002회로 늘었고(10만 건 기준 202회), 그 왕복은 전부 마스터 한 대로 갑니다.
4. **읽기 복제 분산** — 마스터에 몰린 조회를 나누려 검토했으나 철회했습니다. 복제본은 잠금 조회를 거부하지 않고 실행했지만 그 잠금은 마스터를 쓰는 다른 인스턴스에게 보이지 않아 배타성이 없었고(인스턴스 한 대짜리 반증 실험에서도 중복 3,500건), 잠금을 빼자 복제 지연 동안 이미 보낸 행이 다시 읽혀 10만 행이 전부 두 번 나갔습니다.
5. **Redis 분산락(행 단위 SETNX)** — 문제를 다시 정의했습니다. DB에 바라던 것은 "같은 행을 두 번 보내지 마라"는 판정 하나였습니다. 조회에서 잠금을 걷어내고 행마다 `SET outbox:{id} NX PX`로 도장을 찍어, 도장을 잡은 인스턴스만 발행하도록 바꿨습니다. 중복 0건, DB 행 잠금 대기 0으로 마감했습니다.

## Result

- **중복 발송 차단 →** 미발행 100만 행 기준 중복 0건입니다. 실행 중 마커 키를 60초 동안 강제로 지우는 주입 실험에서는 그 구간에서만 중복 238건이 났고, 밖에서는 0건이었습니다. 락 유실 구간이 그만큼 남아 있다는 뜻이며, 확장성을 얻기 위해 이 구간은 의도적으로 수용했습니다.
- **락 대기 병목 제거 →** 비관적 락에서 200,315ms였던 DB 행 잠금 대기가 0이 됐고, 롤백으로 인한 재발행도 사라졌습니다. 인스턴스가 서로를 기다리는 구간이 발송 경로에서 없어졌습니다.
- **중복 판정을 DB 밖으로 이관 →** 발송 경로에서 DB 행 잠금이 사라져 마스터가 판정을 위해 지던 부담을 덜었습니다. **다만 인스턴스를 2대로 늘렸을 때 처리량은 1대의 0.97배였습니다.** 두 인스턴스가 여전히 같은 목록을 각자 가지러 가고, 마커 경쟁에서 진 쪽이 읽은 행을 버리기 때문입니다. 이 단계가 해결한 것은 중복 판정과 락 대기이고, 확장(읽기 낭비 제거)은 인스턴스가 목록을 가지러 가는 대신 받아 가는 구조, 즉 다음 단계인 대기열 푸시의 몫으로 넘겼습니다.
