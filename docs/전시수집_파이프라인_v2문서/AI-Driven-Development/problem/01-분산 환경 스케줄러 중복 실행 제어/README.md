## 분산 환경 스케줄러 중복 실행 제어

---

> 서버 2대의 동일 스케줄러가 같은 아웃박스 행을 읽어 알림이 중복 발송되던 문제를, 비관적 락에서 SKIP LOCKED와 배치 분할을 거쳐 Redis 분산락까지 단계적으로 개선하면서 중복을 차단하는 동시에 락
> 대기 병목까지 제거했습니다.
>

## Problem

전시 수집 도메인은 수집에서 보강, 점검, 스테이징으로 이어지는 각 단계를 이벤트로 연결하고 있으며, 커밋과 이벤트 발행 사이의 장애 지점을 예방하기 위해 트랜잭션 아웃박스 패턴으로 운영하고 있습니다.

그러나 발행 방식에 문제가 있었습니다. 아웃박스에 적재된 이벤트는 스케줄러의 DB 폴링으로 처리되는데, 동일한 스케줄러 코드가 서버 2대에 배포되어 있어 같은 시각에 같은 행을 조회합니다. 그 결과 수집 요청이
인스턴스 수만큼 중복 발송됩니다.

여기에 규모까지 고려하면 부담은 더 커집니다. 10분 동안 100만 건이 적재되는 상황을 가정하면 1분마다 10만 건을 조회해야 하기 때문입니다. 따라서 요구사항을 두 가지로 정리했습니다. **중복을 차단할 것,
그리고 인스턴스를 늘린 만큼 처리량이 증가할 것.**

## Action

1. **비관적 락**으로 한 인스턴스만 처리하도록 제한했으나, 인스턴스를 추가하면 락을 획득하지 못한 인스턴스의 대기가 발생했습니다.
2. **SKIP LOCKED**로 대기를 건너뜀으로 전환하여, 인스턴스가 늘어나도 병렬로 처리하도록 만들었습니다.
3. **배치 크기 LIMIT**으로 조회를 분할하여 단일 쿼리의 DB 부하를 낮췄으나, 분할한 횟수만큼 네트워크 왕복이 증가했습니다. (10만 건 / 배치 500 = 200회의 네트워크 I/O)
4. **읽기 복제 분산**을 검토했으나 잠금 조회의 특성상 효과가 없다고 판단하여 철회했습니다.
5. 문제를 재정의한 뒤 **DB 락을 철회**하고 **Redis 분산락(SETNX)을 채택**하여 중복 판정을 DB 밖으로 이관했습니다.

## Result

- **중복 발송 차단 →** 다만 Redis 마스터 장애와 비동기 복제 지연이 동시에 발생해 락이 유실되는 경우는 남아 있으며, 확장성을 얻기 위해 이 구간은 의도적으로 수용했습니다.
- **락 대기 병목 제거 →**  인스턴스가 서로를 기다리지 않고 병렬로 처리하는 구조를 확립했습니다.
- **쓰기 확장 제약 해소 →**  중복 판정을 DB 밖으로 옮기면서 DB 락 병목과 쓰기 확장 한계를 동시에 해소했습니다.
