# 핵심 수치 — 01 분산 환경 스케줄러 중복 실행 제어

측정 커밋 `14323e7` · 측정일 2026-08-30 · 환경 L3(docker compose: Nginx · 앱 2대 · MySQL 8.4.10 master/replica · Redis 7.4.9)
공통 조건: 미발행 행을 한 번에 적재한 뒤 앱 동시 기동 · 발송 틱 60초 · 한 틱은 배치 소진까지 반복 · 컨슈머 OFF · 힙 `-Xmx2g` · 변형당 1회(N=1)

## 반드시 봐야 하는 수치

1. **중복 2,000,000건 → 0건** — 아무 제어가 없을 때 100만 행이 300만 번 발행됐고(대기열 3,000,000 / 고유 1,000,000), 행마다 Redis 마커로 판정하자 0이 됐습니다. README Problem의 "인스턴스 수만큼 중복 발송"과 Result 1 "중복 발송 차단"을 이 한 쌍이 증명합니다.
2. **락 대기 4회 / 200,315ms → 0회 / 0ms** — 비관적 락에서는 한 대가 100만 행을 잠근 409초 동안 다른 한 대가 발행 0건이었고, 선점 조회가 50초 타임아웃으로 네 번 튕겼습니다. 배치 상한과 `SKIP LOCKED`를 거쳐 마커로 옮기면서 DB 행 잠금 대기가 완전히 사라졌습니다. README Action 1과 Result 2의 근거입니다.
3. **앱 2대 549초 ≈ 앱 1대 535초(0.97배)** — 채택한 방식에서 인스턴스를 늘려도 처리량이 늘지 않았습니다. 두 앱이 같은 머리 500행을 읽고 한쪽이 마커를 전부 가져가기 때문입니다(진 쪽의 건너뜀 4,762건). README Result 3의 "인스턴스를 늘린 만큼 처리량 증가"는 **이 실험에서 성립하지 않습니다.** 확장은 다음 단계(대기열 푸시)의 몫입니다.

분당 SENT는 소진 시간으로 나눈 파생값이고 표에는 소수 첫째 자리를 반올림해 적었습니다(예: S0 55,300 = 원시 55,299.5, S3a 188,679 = 원시 188,679.2). 원시값은 각 `run-summary.json` 의 `sent_per_minute` 입니다.

읽는 법 세 가지.

- **S3b·S4a·S4b는 10만 행 단축 런**입니다. 판정(중복이 났는가, 대기가 어떤 모양인가)만 확인하는 것이 목적이었으므로 100만 행 런들과 배수·비율로 견주지 않습니다.
- **S0의 분당 SENT는 처리 속도가 아닙니다.** 같은 100만 건을 확정하려고 300만 번 발행한 결과입니다. S2의 값에도 재발행 38만 건이 섞여 있습니다.
- **S4a는 SENT 19,000 / PENDING 81,000에서 관측이 끝났습니다.** 소진을 감지하는 스크립트가 복제본 쪽 잠금 대기를 활동으로 세지 못했습니다. 이 런의 처리량은 지표로 쓰지 않고, 중복이 났다는 판정만 씁니다.

## 미측정 / 미해결

| 항목 | 이유 | 대체 근거 |
|---|---|---|
| Redis 마스터 장애와 복제 지연이 겹친 락 유실 | 실험 Redis가 단일 노드라 장애·복제 지연 자체가 일어나지 않습니다 | 마커 키를 60초 동안 강제로 지워 **락이 사라진 상태를 주입**했습니다. 그 구간에서만 중복 238건, 밖에서는 0건 (`s5/attachments/deleted-keys.txt`) |
| 중복 238건과 삭제된 마커 키의 식별자 단위 대조 | 행 id와 `aggregateId` 가 산술로 환산되지 않고(id 1,000,000 = `lab-1-62-637`) 대응표를 원시에 남기지 않았습니다 | 개수 일치(두 번 지워진 키 238개 = 앱2가 획득한 마커 238개 = 중복 238건)와 시각 일치(17:30:30~17:30:33). 재측정 시 행 id를 담은 덤프로 1:1 대조 |
| S4a의 처리량·소진 시간 | 소진 감지가 복제본 쪽 잠금 대기를 활동으로 세지 못해 조기 종료됐습니다 | 같은 런의 중복 3,500건과 복제본 계기판(`Com_select` 79 · 읽은 행 45,000)만 판정에 사용 |
| S2의 커밋 차단 원인 | 런 종료 시점 InnoDB 상태 덤프에 열린 트랜잭션이 없어 대기 그래프가 남지 않았습니다 | 해석 후보 두 가지를 `design-notes.md` 에 병기 |
| S4a의 데드락 상대 트랜잭션 | 같은 이유로 특정하지 못했습니다 | 복제본 행 잠금 대기 36회를 정황으로만 기재 |
| 잡 단위 락(회수·정리·트리밍)의 효과 | 부하 실험 대상이 아니었습니다 | 단위 테스트 `IngestionLockTest`(마커 배타성 · TTL 만료 후 재획득 · 소유자 비교 해제 · 잡 락 단일 실행) |
| 변형 간 차이의 통계적 유의성 | 변형당 1회만 실행했습니다(N=1) | 방향과 자릿수만 근거로 사용 |
| 운영 DB와의 차이 | 없음 — 실험 MySQL 8.4.10 은 운영과 같은 계열입니다. Redis 7.4.9 는 단일 노드라는 점만 다릅니다 | 조건표에 버전 기재 |
