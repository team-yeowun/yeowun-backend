## 분산 환경 스케줄러 중복 실행 제어

---

> 서버 2대의 동일 스케줄러가 같은 아웃박스 행을 읽어 이벤트가 중복 발송되던 문제를, 비관적 락 → SKIP LOCKED → 배치 분할 → 읽기 복제 분산 → Redis 분산락 순으로 같은 부하 실험에서 재며 골라 **100만 행 기준 중복 2,000,000건 → 0건, DB 행 잠금 대기 200,315ms → 0ms**를 달성했습니다.
>

## Problem

전시 수집 파이프라인은 단계 간 이벤트를 트랜잭션 아웃박스로 전달하고, 스케줄러가 DB를 폴링해 미발행 행을 대기열로 발행합니다. 같은 스케줄러가 서버 2대에 배포되어 있어 같은 시각에 같은 행을 조회합니다.

미발행 100만 행을 두고 서버 2대를 띄운 부하 실험에서 **대기열에 300만 건이 실려 중복 200만 건**이 발생했습니다. 인스턴스 수만큼 중복되는 데다, 롤백된 트랜잭션이 이미 내보낸 발행을 되돌리지 못해 한 번 더 나갔습니다. 요구사항은 **중복을 차단할 것, 그리고 인스턴스를 늘려도 서로를 기다리지 않을 것** 두 가지였고, 락 방식만 바꿔 가며 같은 실험 무대에서 다섯 번 쟀습니다.

## Action

1. **비관적 락(`SELECT … FOR UPDATE`)** — 중복은 0이 됐지만, 한 대가 100만 행을 잠근 409초 동안 다른 한 대는 선점 조회가 50초 타임아웃으로 4회 튕기며(누적 200,315ms) 한 건도 발행하지 못했습니다. 중복 차단이라는 절반만 얻고 확장을 잃어 철회.
2. **SKIP LOCKED** — 잠긴 행을 건너뛰게 하자 대기가 사라지고 두 인스턴스가 행을 갈라 집었습니다. 그러나 한쪽의 대량 트랜잭션이 커밋에서 롤백되자 이미 나간 발행이 되돌아가지 않아 중복 381,009건이 남았습니다. 잠금 절은 "누가 읽을지"만 정할 뿐 중복은 발행과 확정 사이에서 생긴다고 보고, 방식은 유지한 채 트랜잭션 크기로 넘어갔습니다.
3. **배치 크기 LIMIT 500** — 한 트랜잭션이 잠그는 행을 500개로 제한하고 틱마다 배치를 소진할 때까지 반복하게 하자 중복·롤백·락 대기가 모두 0이 됐고 힙은 1.3GB → 258MB로 내려갔습니다. 대신 조회 왕복이 2,002회로 늘었고 그 왕복이 전부 마스터 한 대로 갑니다. 채택하되, 확장의 상한이 앱이 아니라 마스터에 있다는 사실이 드러났습니다.
4. **읽기 복제 분산** — 마스터에 몰린 선점 조회를 복제본으로 보냈으나, 복제본이 잡은 잠금은 다른 인스턴스에 보이지 않아 배타성이 없었고 인스턴스 1대에서도 중복 3,500건이 났습니다. 잠금 조회는 복제본을 쓰지 못하는 것이 아니라 써도 의미가 없어 철회.
5. **Redis 분산락(SETNX)** — DB에 바라던 것은 "이 행을 누가 발행하는가"라는 판정 하나였으므로, 조회에서 잠금을 걷어내고 행마다 `SET outbox:{id} NX PX`로 마커를 찍어 마커를 잡은 인스턴스만 발행하게 했습니다. 중복 판정과 락 대기를 DB 밖으로 옮겨 채택.

## Result

- **중복 발송 차단 →** 100만 행 기준 중복 **2,000,000건 → 0건**(앱 1대, 그리고 앱 2대의 주입 구간 밖). 마커 키를 60초간 강제 삭제한 락 유실 주입 구간에서만 중복 238건이 났고 그 외 0건으로, Redis 장애와 복제 지연이 겹치는 이 구간은 확장성을 위해 의도적으로 수용했습니다.
- **락 대기 병목 제거 →** `Innodb_row_lock_waits` **4회 / 200,315ms → 0회 / 0ms**. 인스턴스가 서로를 기다리지 않는 구조가 됐습니다.
- **중복 판정의 DB 밖 이관 →** 마스터가 판정을 위해 지던 행 잠금 부담을 제거했습니다. 다만 인스턴스 2대의 소진 시간이 1대의 0.97배라 "서로 기다리지 않는다"와 "일이 나뉜다"는 다른 문제였고, 처리량 확장은 인스턴스가 목록을 가지러 가는 대신 받아 가는 대기열 푸시 구조로 바꾸는 다음 단계의 몫으로 넘겼습니다.
