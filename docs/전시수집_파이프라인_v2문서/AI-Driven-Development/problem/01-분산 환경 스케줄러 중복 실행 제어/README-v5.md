## 분산 환경 스케줄러 중복 실행 제어

---

> 서버 2대의 동일 스케줄러가 같은 아웃박스 행을 읽어 이벤트가 중복 발송되는 문제를, 락 방식만 바꿔 가며 같은 부하 실험 무대에서 다섯 번 재고 그 수치로 골랐습니다. 중복 200만 건에서 출발해 비관적 락과 SKIP LOCKED, 배치 분할, 읽기 복제 분산을 거쳐 Redis 분산락에 도달했습니다.

## Problem

전시 수집 도메인은 각 단계를 이벤트로 연결하고 있으며, 커밋과 이벤트 발행 사이의 장애 지점을 예방하기 위해 트랜잭션 아웃박스 패턴으로 운영하고 있습니다.

그러나 발행 방식에 문제가 있었습니다. 아웃박스에 적재된 이벤트는 스케줄러의 DB 폴링으로 처리되는데, 동일한 스케줄러 코드가 서버 2대에 배포되어 있어 같은 시각에 같은 행을 조회합니다. 미발행 100만 행을 두고 서버 2대를 띄운 실험에서 대기열에는 300만 건이 실렸습니다. 인스턴스 수만큼 중복되고, 여기에 롤백된 트랜잭션이 이미 내보낸 발행까지 되돌리지 못해 한 번 더 나갔습니다.

요구사항은 두 가지였습니다. **중복을 차단할 것, 그리고 인스턴스를 늘린 만큼 처리량이 증가할 것.**

## Action

1. **비관적 락**
    - 시도: `SELECT … FOR UPDATE`로 한 인스턴스만 처리하도록 제한했습니다.
    - 발견: 중복은 0이 됐지만, 잠금을 놓친 인스턴스는 선점 조회가 50초 타임아웃으로 네 번 튕기며(누적 200,315ms) 한 건도 발행하지 못했습니다.
    - 판단: 중복 차단이라는 절반만 얻고 확장은 잃었습니다. **철회.**
2. **SKIP LOCKED**
    - 시도: 잠긴 행을 기다리지 않고 건너뛰게 바꿨습니다.
    - 발견: 대기가 사라지고 두 인스턴스가 618,991건과 381,009건으로 갈라 집었습니다. 그러나 한쪽의 대량 트랜잭션이 커밋에서 롤백되자 이미 나간 발행은 되돌아가지 않아 중복 381,009건이 남았습니다.
    - 판단: 잠금 절은 "누가 읽을지"만 정할 뿐 중복은 발행과 확정 사이에서 생깁니다. 방식은 **유지**하되 원인이 트랜잭션 크기에 있다고 보고 다음으로 넘어갔습니다.
3. **배치 크기 LIMIT**
    - 시도: 한 트랜잭션이 잠그는 행을 500개로 제한하고, 한 틱이 배치를 소진할 때까지 반복하게 했습니다.
    - 발견: 중복·롤백·락 대기가 모두 0이 됐고 힙은 1.3GB대에서 258MB로 내려갔습니다. 대신 조회 왕복이 2,002회로 늘었고(10만 건 기준 202회) 그 왕복은 전부 마스터 한 대로 갑니다.
    - 판단: **채택.** 다만 확장의 상한이 앱이 아니라 마스터에 있다는 사실이 드러났습니다.
4. **읽기 복제 분산**
    - 시도: 마스터에 몰린 조회를 읽기 전용 복제본으로 보냈습니다.
    - 발견: 복제본은 잠금 조회를 실행해 줬지만 그 잠금은 다른 인스턴스에게 보이지 않아 배타성이 없었고, 인스턴스가 한 대뿐인 실험에서도 중복이 3,500건 났습니다. 잠금을 빼자 복제 지연 동안 이미 보낸 행이 다시 읽혀 10만 행이 전부 두 번 나갔습니다.
    - 판단: 잠금 조회는 복제본을 쓰지 못하는 것이 아니라 **써도 의미가 없습니다. 철회.**
5. **Redis 분산락(SETNX)**
    - 시도: 문제를 재정의했습니다. DB에 바라던 것은 판정 하나였으므로, 조회에서 잠금을 걷어내고 행마다 `SET outbox:{id} NX PX`로 도장을 찍어 도장을 잡은 인스턴스만 발행하게 했습니다.
    - 발견: 중복 0건, DB 행 잠금 대기 0. 반면 인스턴스를 2대로 늘려도 소진 시간은 1대의 0.97배에 머물렀습니다.
    - 판단: **채택.** 중복 판정과 락 대기를 DB 밖으로 옮기는 목적은 달성했고, 남은 읽기 낭비는 다음 단계의 문제로 넘겼습니다.

## Result

- **중복 발송 차단 →** 100만 행 기준 중복 0건입니다. 다만 실행 중 마커 키를 지우는 주입 실험에서 그 60초 구간에만 중복 238건이 났습니다. Redis 마스터 장애와 비동기 복제 지연이 겹쳐 락이 유실되는 경우가 남아 있다는 뜻이며, 확장성을 얻기 위해 이 구간은 의도적으로 수용했습니다.
- **락 대기 병목 제거 →** DB 행 잠금 대기가 200,315ms에서 0으로 사라졌습니다. 다만 "서로 기다리지 않는다"와 "일이 나뉜다"는 다른 이야기여서, 두 인스턴스가 같은 목록을 각자 읽는 낭비는 남았습니다.
- **쓰기 확장 제약 →** 중복 판정을 DB 밖으로 옮겨 마스터가 판정을 위해 지던 잠금 부담을 없앴습니다. 다만 인스턴스 2대의 처리량이 1대의 0.97배였으므로, **이 단계에서 확장까지 얻었다고 말하지 않습니다.** 인스턴스가 목록을 가지러 가는 대신 받아 가는 구조로 바꾸는 다음 단계로 넘겼습니다.
