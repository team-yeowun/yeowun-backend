# DB 폴링에서 Redis Streams 푸시로 전환

---

> 각 인스턴스가 아웃박스 전체를 조회하며 빈 조회를 반복하던 폴링 구조를 Redis Streams Consumer Group 기반 푸시로 전환하여, 중복 조회를 제거하고 인스턴스 추가만으로 처리량이 늘어나는 구조를
> 확보했습니다.
>

## Problem

분산락을 도입하여 중복 발송은 대부분 차단했습니다. 그러나 이는 이미 발생한 중복을 걸러내는 조치였을 뿐, 발행 방식은 여전히 DB 폴링이었습니다. **각 인스턴스가 아웃박스 전체를 배치 단위로 조회하는 구조가
그대로 유지되었고, 오히려 조회 건마다 Redis 중복 체크가 더해지면서 폴링의 비용은 이전보다 커졌습니다.** **앞 단계 실험에서** 미발행 100만 행에 서버 2대를 띄우자 두 앱이 읽은 행은 3,005,354행이었습니다. 같은 조건에서 1대는 2,000,058행이었으니 1.50배를 더 읽은 셈입니다.

이때 조회 횟수는 **(미처리 건수 / 배치 크기) × 인스턴스 수**가 됩니다. 같은 실험에서 인스턴스 수만큼 늘어난 것은 조회 횟수가 아니라 읽은 행이었습니다(호출 2,012회 대 2,001회). 문제는 그중 대부분이 다른 인스턴스가 이미 가져간 데이터를 확인하고 폐기하는 **낭비 조회**라는 점이며, 마커 경쟁에서 진 인스턴스는 읽은 5,000행 중 4,762행을 버렸습니다. 더구나 발송 지연을 줄이기
위해 폴링 주기를 짧게 설정하면 빈 조회 역시 비례해 증가하기 때문에, **지연 개선과 자원 낭비가 서로 상충하는 구조**였습니다.

## Action

- **인스턴스가 처리 대상을 탐색하는 Pull 구조에서, 처리 대상이 배분되는 Push 구조로** 방향을 정했습니다. 앞 단계에서 인스턴스를 2대로 늘렸을 때 소진 시간이 1대의 0.97배였던 것이 근거입니다.
- **Kafka와 Redis Streams를 비교**하여, 현재 규모와 **운영 부담**을 근거로 Redis Streams를 채택했습니다. 하루 이벤트는 상한 기준 3,500건(실측 원천 기준 1,862건)으로 추정됩니다. 이 규모에서 Redis Streams는 새로 운영할 구성 요소가 0종입니다.
- **폴링은 제거하지 않고 복구 경로로 남겨** 큐와 이중으로 운영했습니다. 10만 행 실험에서 발송 틱은 선점 조회를 1,455회 돌았습니다. 실행 중 강제 종료한 인스턴스가 쥐고 있던 18건도 회수 경로가 되살렸습니다.

## Result

- **인스턴스별 중복 조회 제거 →**  각 인스턴스는 Consumer Group으로부터 배분받은 메시지만 처리합니다. 10만 건이 app1 50,007건과 app2 49,993건으로 갈렸습니다. 중복 소비는 0건이었습니다.
- **수평 확장 구조 확보 →** 트래픽이 늘어나면 인스턴스를 추가하는 것만으로 처리량이 증가합니다. 실행 중 세 번째 인스턴스를 붙이자 그 구간 소비의 31.3%를 가져갔습니다(확장이 확인된 곳은 소비 단계이고, 처리율은 기록만 남겼습니다).
- **쓰기 병목을 DB에서 Redis로 이관 →** RDB는 쓰기 수평 확장 수단이 제한적이지만, Redis는 Cluster 샤딩으로 확장할 수 있고 SPOF 방지가 목적이라면 Sentinel도 선택지로 남습니다. 마스터 3대 클러스터에서 대기열 4개가 두 노드에 나뉘어 앉았습니다. 행 마커도 키 이름으로 계산하면 세 노드에 흩어집니다. 그 상태로 10만 건이 그대로 소비됐습니다(성능 비교가 아닌 배치·정상 동작 확인이며, 조회수 누산 키 하나는 해시태그 적용이 선결 과제입니다).
