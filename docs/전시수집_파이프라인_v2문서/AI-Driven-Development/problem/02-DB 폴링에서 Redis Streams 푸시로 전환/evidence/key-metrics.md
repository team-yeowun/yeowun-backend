## 미측정 / 미해결

| 항목 | 이유 | 대체 근거 |
|---|---|---|
| 폴링 주기를 줄였을 때 빈 조회가 얼마나 느는가 | 유휴 구간을 재는 런을 계획에 넣지 않았습니다 | 구조 논증만 씁니다. 발송 틱은 `dispatch-interval-ms`의 `fixedDelay`로 인스턴스마다 따로 돕니다(`OutboxDispatchScheduler` L53) |
| 발송 폴링이 **재발행**에 쓰이는 장면 | 세 런 모두 발행 실패가 0건이라 재시도가 일어나지 않았습니다 | 스트림 쪽 복구 경로는 회수 18건으로 확인했습니다(`push-scale`) |
| 회수 후 구간의 분당 소비가 낮은 이유(8,129.6) | 이 런의 원시로 가려지지 않습니다 | 해석 후보 셋을 `design-notes.md`에 병기했습니다 |
| Kafka와의 대조 실측 | 브로커를 세우지 않았습니다 | 코드 사실(이미 서 있는 Redis 용도 다섯, 컨슈머 수가 프로퍼티, 회수가 이미 코드)과 규모 추정식까지 씁니다 |
| 하루 이벤트 규모의 실사용 값 | 운영 로그가 아니라 코드값 계산입니다 | 상한 기준 1 × 500 × 7 = 3,500건/일, 실측 원천 기준 1 × 266 × 7 = 1,862건/일. **추정**으로 표기합니다 |
| "쓰기 병목을 Redis로 이관"의 성능 근거 | 클러스터 시연의 목적이 배치와 정상 동작 확인입니다 | 키 배치와 소비 정상(중복 0 · XPENDING 0 · CROSSSLOT 0)까지 씁니다 |
| 조회수 누산기 `RENAME`의 클러스터 대응 | 해시태그 적용이 이번 범위 밖입니다(코드 미변경) | 선결 과제로 기록했습니다. 실험 창에서는 그 잡을 재워 런이 깨지지 않았을 뿐입니다 |
| Sentinel 구성의 동작 | 세워 보지 않았습니다 | 선택지 서술까지입니다 |
| 3대를 넘는 규모·실제 핸들러에서의 배분 비율 | 스텁 20ms · N=1 · 앱 3대까지의 값입니다 | 방향(붙이면 곧바로 몫이 갈린다)만 씁니다. 처리 비용이 제각각인 실제 핸들러에서는 비율이 달라집니다 |
| 런 사이 차이의 통계적 유의성 | 런당 1회입니다(N=1) | 방향과 자릿수만 근거로 사용합니다 |
