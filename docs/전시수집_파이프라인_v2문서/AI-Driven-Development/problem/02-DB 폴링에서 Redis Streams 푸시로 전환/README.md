# DB 폴링에서 Redis Streams 푸시로 전환

---

> 각 인스턴스가 아웃박스 전체를 조회하며 빈 조회를 반복하던 폴링 구조를 Redis Streams Consumer Group 기반 푸시로 전환하여, 중복 조회를 제거하고 인스턴스 추가만으로 처리량이 늘어나는 구조를
> 확보했습니다.
>

## Problem

분산락을 도입하여 중복 발송은 대부분 차단했습니다. 그러나 이는 이미 발생한 중복을 걸러내는 조치였을 뿐, 발행 방식은 여전히 DB 폴링이었습니다. **각 인스턴스가 아웃박스 전체를 배치 단위로 조회하는 구조가
그대로 유지되었고, 오히려 조회 건마다 Redis 중복 체크가 더해지면서 폴링의 비용은 이전보다 커졌습니다.**

이때 조회 횟수는 **(미처리 건수 / 배치 크기) × 인스턴스 수**가 됩니다. 문제는 그중 대부분이 다른 인스턴스가 이미 가져간 데이터를 확인하고 폐기하는 **낭비 조회**라는 점이며, 더구나 발송 지연을 줄이기
위해 폴링 주기를 짧게 설정하면 빈 조회 역시 비례해 증가하기 때문에, **지연 개선과 자원 낭비가 서로 상충하는 구조**였습니다.

## Action

- **인스턴스가 처리 대상을 탐색하는 Pull 구조에서, 처리 대상이 배분되는 Push 구조로** 방향을 정했습니다.
- **Kafka와 Redis Streams를 비교**하여, 현재 규모와 **운영 부담**을 근거로 Redis Streams를 채택했습니다.
- **폴링은 제거하지 않고 복구 경로로 남겨** 큐와 이중으로 운영했습니다.

## Result

- **인스턴스별 중복 조회 제거 →**  각 인스턴스는 Consumer Group으로부터 배분받은 메시지만 처리합니다.
- **수평 확장 구조 확보 →** 트래픽이 늘어나면 인스턴스를 추가하는 것만으로 처리량이 증가합니다.
- **쓰기 병목을 DB에서 Redis로 이관 →** RDB는 쓰기 수평 확장 수단이 제한적이지만, Redis는 Cluster 샤딩으로 확장할 수 있고 SPOF 방지가 목적이라면 Sentinel도 선택지로 남습니다.
