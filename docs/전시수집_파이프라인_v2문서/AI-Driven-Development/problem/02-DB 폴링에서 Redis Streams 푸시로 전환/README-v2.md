# DB 폴링에서 Redis Streams 푸시로 전환

---

> 인스턴스마다 아웃박스를 훑어 처리 대상을 찾던 폴링 구조를 Redis Streams Consumer Group 기반 푸시로 바꿨습니다. 소비 단계에서 인스턴스별 중복 조회를 없애고, 인스턴스를 붙이면 몫이 갈리고 죽으면 그 몫이 회수되는 구조를 같은 무대에서 확인했습니다.

## Problem

분산락으로 중복 발송은 차단했지만 바뀐 것은 **누가 발행할지를 정하는 방법**이었지 **처리 대상을 어떻게 찾는지**가 아니었습니다. 발행 방식은 여전히 폴링이라, 인스턴스마다 자기 시계로 깨어나 미발행 행을 배치만큼 읽고 읽어 온 행이 자기 몫인지 하나씩 확인했습니다. 판정을 Redis로 옮긴 대가로 조회해 온 행마다 확인 호출이 하나씩 더 붙었기 때문에, 폴링의 비용은 오히려 이전보다 커졌습니다.

크기는 앞 단계 실험에 그대로 남아 있습니다. 미발행 100만 행에 앱 2대를 띄우자 조회 호출 수는 2,012회로 1대(2,001회)와 거의 같았지만, 두 앱이 언제나 같은 머리 500행을 받아 읽는 탓에 **읽은 행이 2,000,058행에서 3,005,354행으로 1.50배**가 됐습니다. 경쟁에서 진 인스턴스는 읽은 5,000행 중 4,762행을 버렸고 발행은 238건뿐이었습니다. 그런데 소진 시간은 535초에서 549초로 오히려 늘었습니다. **탐색 비용은 인스턴스 수에 비례하는데 처리량은 그렇지 않았습니다.**

원인은 어느 판정 방식을 고르느냐가 아니라 그 위의 구조였습니다. 인스턴스가 스스로 같은 목록을 가지러 가는 한, 판정을 어디서 하든 경쟁은 조회 시점에 이미 일어나 있습니다.

## Action

- **인스턴스가 대상을 탐색하는 Pull에서, 대기열이 대상을 배분하는 Push로** 방향을 정했습니다. 나눠 주는 쪽이 소비자 목록을 알고 있으면 같은 행을 두 번 읽을 이유 자체가 사라집니다.
- **Kafka와 Redis Streams를 비교해 Redis Streams를 채택했습니다.** 기준은 새로 운영할 구성 요소의 수였습니다. Redis는 캐시·무효화 발행·AI 초안 보관·조회수 누산·수집 마커 다섯 용도로 이미 서 있어 늘어나는 것이 0종인 반면 Kafka는 브로커 한 종이 늘어납니다. 이 규모에서 Kafka가 주는 이점인 보존과 되감기는 원본 이벤트가 아웃박스에 그대로 남아 지금 필요하지 않았습니다. 병렬성도 컨슈머 수를 늘리면 되고 파티션 수가 상한이 되지 않습니다.
- **폴링은 제거하지 않고 복구 경로로 남겨** 큐와 이중으로 운영했습니다. 대기열에 넣는 일 자체가 실패하거나 그 사이 앱이 죽어도 행은 미발행으로 남아 다음 틱이 다시 집습니다.

## Result

- **인스턴스별 중복 조회 제거 →** 10만 건을 두 인스턴스가 50,007건과 49,993건으로 나눠 처리했고, 중복 소비 0건·미확인 0건으로 끝났습니다. 소비 단계에는 읽고 버리는 건수 자체가 없습니다. 같은 실행의 발송 단계는 여전히 27,000행을 읽고 버렸는데, 이것이 폴링을 복구 경로로 남긴 대가입니다.
- **수평 확장 구조 확보(소비 단계) →** 실행 중간에 세 번째 인스턴스를 붙이자 그 구간 소비의 31.3%를 곧바로 가져갔습니다. 그 인스턴스를 강제 종료하자 손에 쥐고 있던 18건이 회수되어 남은 두 대가 유실 없이 끝냈습니다. **다만 처리량 배수는 주장하지 않습니다** — 확인한 것은 몫이 갈린다는 것이고, 발송 단계는 여전히 폴링이라 인스턴스가 늘수록 버리는 행도 함께 늡니다.
- **쓰기 병목을 DB에서 Redis로 이관 →** RDB는 쓰기 수평 확장 수단이 제한적이지만 Redis는 Cluster 샤딩으로 나눌 수 있습니다. 마스터 3대 클러스터에서 대기열 4개가 두 노드에 앉은 상태로 10만 건이 그대로 소비됐고(중복 0·미확인 0·슬롯 오류 0) 실험 후 단일 노드로 되돌렸습니다. 행 마커는 표본 다섯 개의 키 이름으로 슬롯을 계산하면 세 노드에 흩어집니다. **다만 이것은 배치와 정상 동작 확인이지 성능 비교가 아니고, 코어의 조회수 누산 키 하나는 두 키의 슬롯이 달라 해시태그 적용이 선결 과제로 남습니다.** SPOF 방지가 목적이라면 Sentinel도 선택지이지만 이번에는 세워 보지 않았습니다.
