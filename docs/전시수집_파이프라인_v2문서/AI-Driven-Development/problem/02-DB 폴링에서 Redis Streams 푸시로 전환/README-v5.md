# DB 폴링에서 Redis Streams 푸시로 전환

---

> 인스턴스마다 아웃박스를 훑어 처리 대상을 찾던 폴링 구조를 Redis Streams Consumer Group 기반 푸시로 바꾸고, 배분·확장·샤딩을 같은 무대에서 한 번씩 확인했습니다. 소비 단계의 중복 조회는 사라졌고, 복구 경로로 남긴 발송 폴링에는 낭비가 그대로 남았습니다.

## Problem

분산락을 도입하여 중복 발송은 대부분 차단했습니다. 그러나 이는 이미 발생한 중복을 걸러내는 조치였을 뿐, 발행 방식은 여전히 DB 폴링이었습니다. 각 인스턴스가 아웃박스 전체를 배치 단위로 조회하는 구조가 그대로 유지되었고, 오히려 조회 건마다 Redis 중복 체크가 더해지면서 폴링의 비용은 이전보다 커졌습니다.

앞 단계 실험이 그 크기를 남겼습니다. 미발행 100만 행에 앱 2대를 띄우자 조회 호출 수는 1대와 거의 같았지만(2,012회 대 2,001회) 두 앱이 언제나 같은 머리 500행을 받는 탓에 읽은 행이 1.50배(2,000,058 → 3,005,354행)가 됐고, 경쟁에서 진 인스턴스는 읽은 5,000행 중 4,762행을 버렸습니다. 그렇게 더 읽고도 소진 시간은 535초에서 549초로 늘었습니다.

요구는 셋이었습니다. **인스턴스가 처리 대상을 배분받을 것, 인스턴스를 늘리면 몫이 갈릴 것, 늘린 것을 되돌릴 수 있을 것.**

## Action

1. **Pull에서 Push로**
    - 시도: 인스턴스가 목록을 가지러 가는 대신 대기열이 나눠 주는 구조로 방향을 정했습니다.
    - 발견: 낭비의 원인이 판정 방식이 아니라 "스스로 같은 목록을 가지러 간다"는 구조에 있었습니다. 도장을 어디에 찍느냐를 바꿔서는 4,762라는 숫자가 사라지지 않습니다.
    - 판단: **채택.** 나눠 주는 쪽이 소비자 목록을 아는 구조로 옮깁니다.
2. **Kafka와 Redis Streams 비교**
    - 시도: 새로 운영할 구성 요소의 수, 지금 규모, 병렬성을 늘리는 방법, 방치 항목 회수 절차를 기준으로 견줬습니다.
    - 발견: Redis는 캐시·무효화 발행·AI 초안 보관·조회수 누산·수집 마커 다섯 용도로 이미 서 있어 늘어나는 구성 요소가 0종인 반면 Kafka는 브로커 한 종이 늘어납니다. 하루 이벤트는 상한 기준 3,500건(실측 원천 기준 1,862건)으로 추정되고, Kafka의 이점인 보존과 되감기는 원본이 아웃박스에 남아 지금 필요하지 않았습니다.
    - 판단: **Redis Streams 채택.** 다만 브로커를 세워 견준 실측은 없고, 코드 사실과 규모 추정까지가 근거입니다.
3. **폴링 존치**
    - 시도: 발송 틱을 제거하지 않고 복구 경로로 남겨 큐와 이중으로 운영했습니다.
    - 발견: 대기열에 넣는 일 자체가 실패하거나 그 사이 앱이 죽어도 행은 미발행으로 남아 다음 틱이 다시 집습니다. 대신 발송 단계에는 앞 단계의 낭비가 그대로 남아, 10만 행 실행에서 27,000행을 읽고 버렸습니다.
    - 판단: **채택하되 비용을 명시.** 인스턴스가 셋이 되자 버린 행은 35,749행으로 늘었습니다.
4. **인스턴스를 붙였다 되돌리기**
    - 시도: 실행 중간에 세 번째 인스턴스를 띄우고, 3분 뒤 강제 종료했습니다.
    - 발견: 붙자마자 그 구간 소비의 31.3%를 가져갔고, 죽인 직후 손에 쥐고 있던 18건은 회수되어 남은 두 대가 처리했습니다. 유실은 없었습니다.
    - 판단: **채택.** 다만 회수 18건은 수십 건 규모라 대량 유실 방지가 아니라 회수 경로가 실제로 돈다는 증명입니다.
5. **Redis Cluster로 나누고 되돌리기**
    - 시도: 마스터 3대 클러스터를 실험용 구성 안에만 세우고 환경변수 하나로 앱이 그것을 보게 했습니다.
    - 발견: 대기열 4개가 두 노드에, 행 마커가 세 노드에 앉았고 그 상태로 10만 건이 그대로 소비됐습니다(중복 0·미확인 0·슬롯 오류 0). 한편 코어의 조회수 누산 경로는 두 키의 슬롯이 달라 현행 코드로는 클러스터에서 실패합니다.
    - 판단: **샤딩 가능은 확인, 전환은 조건부.** 해시태그 적용이 선결이고 이번 범위 밖이라 기록만 남겼습니다. 실험 후 단일 노드로 되돌렸습니다.

## Result

- **인스턴스별 중복 조회 제거 →** 10만 건이 50,007건과 49,993건으로 갈렸고 중복 소비 0건·미확인 0건입니다. 소비 단계에는 읽고 버리는 건수 자체가 없습니다. 다만 같은 실행의 발송 단계는 여전히 27,000행을 버렸고, 이것은 폴링을 복구 경로로 남긴 대가입니다.
- **수평 확장 구조 확보 →** 세 번째 인스턴스가 붙자마자 31.3%를 가져갔고 죽은 뒤에는 그 몫이 회수됐습니다. 다만 **처리량이 인스턴스 수만큼 는다고는 말하지 않습니다.** 구간별 처리율은 기록으로만 남겼고(11,358.7 → 14,726.0건/분, 조건당 1회), 확장이 확인된 곳은 소비 단계입니다.
- **쓰기 병목을 DB에서 Redis로 이관 →** RDB는 쓰기 수평 확장 수단이 제한적이지만 Redis는 Cluster 샤딩으로 나눌 수 있고, 나뉜 상태에서 소비가 정상인 것까지 확인했습니다. 다만 **병목이 실제로 줄었는지는 재지 않았고**(성능 비교의 조건이 아닙니다), 조회수 누산 키 하나는 해시태그가 선결입니다. SPOF 방지가 목적이라면 Sentinel도 선택지이지만 세워 보지 않았습니다.
