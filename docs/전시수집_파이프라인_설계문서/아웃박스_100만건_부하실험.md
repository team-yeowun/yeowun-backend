# 아웃박스 100만 건 부하 실험 — 교과서 장애 사례를 우리 테이블에 재현하다

> [아웃박스PR.md](./아웃박스PR.md) §10(프러덕션 장애 사례)의 실측 검증. 실험 브랜치: `exp/outbox-1m-loadtest`
> 레퍼런스 장애 시나리오: "폴링 쿼리에 인덱스가 없고 + 완료 레코드를 안 지워 수백만 건으로 비대 → 폴링 수 초 → 릴레이 지연 5분+"

## 0. 실험 설계

**질문 3개**
1. 인덱스가 없으면 100만 건에서 우리 선별(폴링) 쿼리는 정말 죽는가? (교과서 장애 재현)
2. 현행 운영 인덱스(V35: UK + `(status, next_attempt_at)`)는 100만 건을 실제로 감당하는가?
3. "완료 레코드 정리"는 성능에 정말 필요한가? — 우리 §9 "안 지운다" 결정의 실측 검증

**환경**
- MySQL 8.4.10 (Docker, 로컬 — 운영과 동일 메이저), innodb_buffer_pool_size 128MB(기본값)
- 별도 스키마 `outbox_loadtest`에 **운영과 동일한 DDL**(V35)로 테이블 생성 — 앱 데이터 무접촉
- 측정: `EXPLAIN`(플랜) + `EXPLAIN ANALYZE`(실행 계획 + 실측 시간). 각 2회 실행, **2회차(웜 버퍼) 기준**

**데이터 분포 — "미정리 1년 누적" 가정 (총 1,000,000행)**

| status | 행 수 | 의미 |
|---|---|---|
| SUCCEEDED | 984,000 | 정리 안 한 완료 누적 (98.4%) |
| FAILED_PERMANENT | 10,000 | 영구 실패 누적 |
| FAILED_RETRYABLE (백오프 대기) | 4,700 | next_attempt_at 미래 |
| FAILED_RETRYABLE (도래) | 300 | 선별 대상 |
| PENDING (도래) | 1,000 | 선별 대상 |

→ **선별 대상(due) = 1,300행 / 1,000,000행 (0.13%)** — 실제 운영에서도 도래분은 항상 전체의 극히 일부라는 점을 반영한 분포다. 적재 소요 8.1초, 데이터 101.6MB.

**측정 쿼리 (실제 운영 쿼리 그대로)**

```sql
-- Q1. 릴레이 선별(폴링) — OutboxMessageJpaRepository.findDue
SELECT * FROM exhibition_outbox
WHERE message_type='DRAFT_STAGED' AND status IN ('PENDING','FAILED_RETRYABLE')
  AND next_attempt_at <= NOW(6)
ORDER BY next_attempt_at ASC LIMIT 50;

-- Q2. 멱등 enqueue 조회 — findByMessageTypeAndTargetKey
SELECT * FROM exhibition_outbox WHERE message_type='PLACE_STAGED' AND target_key='EXT-999990';

-- Q3. 관리자 대시보드 — countByStatus
SELECT COUNT(*) FROM exhibition_outbox WHERE status='FAILED_PERMANENT';
```

## 1. Before — 시나리오 A: 인덱스 없음 (교과서 장애 재현)

보조 인덱스 없이(PK만) 100만 건. **EXPLAIN 원문**:

```
+----+-------------+-------------------+------+---------------+------+---------+------+--------+----------+-----------------------------+
| id | select_type | table             | type | possible_keys | key  | key_len | ref  | rows   | filtered | Extra                       |
+----+-------------+-------------------+------+---------------+------+---------+------+--------+----------+-----------------------------+
|  1 | SIMPLE      | exhibition_outbox | ALL  | NULL          | NULL | NULL    | NULL | 994744 |     0.67 | Using where; Using filesort |
+----+-------------+-------------------+------+---------------+------+---------+------+--------+----------+-----------------------------+
```

`type=ALL`(풀 테이블 스캔) + `Using filesort` — 50건을 꺼내려고 100만 행을 전부 읽고 정렬한다. **EXPLAIN ANALYZE 원문(웜)**:

```
-> Limit: 50 row(s)  (cost=99774 rows=50) (actual time=445..445 rows=50 loops=1)
    -> Sort: exhibition_outbox.next_attempt_at, limit input to 50 row(s) per chunk
       (cost=99774 rows=994744) (actual time=445..445 rows=50 loops=1)
        -> Filter: ((message_type = 'DRAFT_STAGED') and (status in ('PENDING','FAILED_RETRYABLE'))
                    and (next_attempt_at <= <cache>(now(6))))
           (cost=99774 rows=994744) (actual time=442..445 rows=434 loops=1)
            -> Table scan on exhibition_outbox
               (cost=99774 rows=994744) (actual time=0.012..337 rows=1e+6 loops=1)   ← 100만 행 전부 스캔
```

| 쿼리 | 플랜 | 실측(웜) |
|---|---|---|
| Q1 선별(폴링) | 풀스캔 1,000,000행 + filesort | **445~509ms** |
| Q2 멱등 조회 | 풀스캔 1,000,000행 | **413ms** |
| Q3 대시보드 count | 풀스캔 1,000,000행 | **191ms** |

교과서 장애가 그대로 재현된다: 폴링 한 번에 ~0.5초. 여기에 이벤트 4종 × 폴링 주기가 곱해지고, **멱등 enqueue 조회(Q2)는 발행 트랜잭션 안에서 돈다** — 즉 인덱스가 없으면 소비만 느려지는 게 아니라 **스테이징 tx가 행마다 0.4초씩 길어져** 발행측까지 무너진다. 이게 장애 사례의 "릴레이 지연 5분+"의 실체다.

## 2. After — 시나리오 B: 현행 운영 인덱스 (V35 그대로)

```sql
create unique index uk_exhibition_outbox_type_target on exhibition_outbox (message_type, target_key);
create index idx_exhibition_outbox_status_next on exhibition_outbox (status, next_attempt_at);
```

100만 건 위에서 인덱스 2개 생성에 **약 5초**(온라인 DDL — 운영 중이라도 이 규모면 부담 없음). 인덱스 크기 70.2MB. **EXPLAIN ANALYZE 원문(웜)**:

```
-> Limit: 50 row(s)  (cost=928 rows=50) (actual time=1.79..1.79 rows=50 loops=1)
    -> Sort: exhibition_outbox.next_attempt_at, limit input to 50 row(s) per chunk
       (cost=928 rows=1300) (actual time=1.79..1.79 rows=50 loops=1)
        -> Filter: (message_type = 'DRAFT_STAGED')  (actual time=0.0145..1.71 rows=434 loops=1)
            -> Index range scan on exhibition_outbox using idx_exhibition_outbox_status_next
               over (status = 'FAILED_RETRYABLE' AND NULL < next_attempt_at <= '...')
                 OR (status = 'PENDING'          AND NULL < next_attempt_at <= '...'),
               with index condition: ((status in ('PENDING','FAILED_RETRYABLE')) and (next_attempt_at <= <cache>(now(6))))
               (cost=928 rows=1300) (actual time=0.0139..1.57 rows=1300 loops=1)   ← 도래분 1,300행만 스캔
```

읽는 포인트: 100만 행 중 **인덱스가 도래분 1,300행만 짚는다**(0.13%). SUCCEEDED 98.4만 행은 `status IN` 레인지 밖이라 **존재 자체가 비용이 아니다**. 이게 "인덱스가 있으면 비대는 선별 성능에 무해하다"의 실측 근거다.

| 쿼리 | 플랜 | Before | **After** | 개선 |
|---|---|---|---|---|
| Q1 선별(폴링) | 레인지 스캔 1,300행 | 445ms | **1.8~2.4ms** | **~220배** |
| Q2 멱등 조회 | UK const 룩업 | 413ms | **0.0002ms** | ~200만 배 |
| Q3 대시보드 count | 커버링 인덱스 10,000행 | 191ms | **2.9ms** | ~65배 |

```
-- Q2 (UK): -> Zero rows (no matching row in const table) (actual time=208e-6..208e-6 ...)
-- Q3:      -> Covering index lookup using idx_exhibition_outbox_status_next (status='FAILED_PERMANENT')
--             (actual time=0.0382..2.56 rows=10000 loops=1)
```

## 3. 시나리오 C: 대안 복합 인덱스 `(message_type, status, next_attempt_at)`는 더 나은가

우리 선별 쿼리는 `message_type`도 필터하므로, 타입까지 선두에 넣은 복합 인덱스를 실험했다:

```
-> Limit: 50 row(s)  (cost=384 rows=50) (actual time=0.886..0.893 rows=50 loops=1)
    -> Index range scan using idx_c_type_status_next
       over (message_type='DRAFT_STAGED' AND status=... AND NULL < next_attempt_at <= '...') ...
       (cost=384 rows=434) (actual time=0.0848..0.704 rows=434 loops=1)   ← 434행(타입까지 선필터)
```

2.4ms → **0.89ms**. 스캔 행이 1,300 → 434로 줄지만, 절대값이 이미 밀리초 단위라 **실익이 없다**. 대가는 실재한다: 인덱스 1개 추가 = 쓰기(INSERT/전이 UPDATE)마다 유지 비용 + 저장 공간. **판정: 현행 `(status, next_attempt_at)` 유지.** (도래분이 수십만 행 규모가 되는 날 다시 꺼낼 카드로 기록만 해둔다.)

## 4. 반전 — 시나리오 D: "정리(DELETE)하면 빨라진다"는 반만 맞다

교과서 해법대로 SUCCEEDED 984,000행을 삭제해봤다. 결과가 실험의 백미다:

**D-1. 대량 DELETE 직후 — 오히려 30배 느려졌다**

```
-> Limit: 50 row(s)  (cost=0.899 rows=1) (actual time=70.5..70.5 rows=50 loops=1)
    -> Filter: ((status in ('PENDING','FAILED_RETRYABLE')) and (next_attempt_at <= <cache>(now(6))))
       (cost=0.899 rows=1) (actual time=69.3..70.3 rows=434 loops=1)
        -> Index lookup using uk_exhibition_outbox_type_target (message_type='DRAFT_STAGED')
           (cost=0.899 rows=1) (actual time=53.4..69 rows=5334 loops=1)   ← 플랜이 UK로 바뀜 + 53ms 소요
```

| 항목 | 삭제 전(B) | **삭제 직후(D)** |
|---|---|---|
| Q1 선별 | 2.4ms | **70ms (30배 악화)** |
| data_length | 101.6MB | **101.6MB (그대로)** + data_free 47MB |
| 옵티마이저 플랜 | (status,next) 레인지 | **UK 룩업으로 오판** (통계상 rows=1) |

왜 이런 일이 나는가: ① InnoDB의 DELETE는 즉시 공간을 돌려주지 않는다(삭제 마크 → 백그라운드 퍼지) — 인덱스 페이지에 98.4만 개의 유령이 남아 스캔이 그 사이를 헤집는다. ② 대량 삭제 직후 통계가 왜곡돼 옵티마이저가 엉뚱한 인덱스를 고른다. **"지우면 빨라진다"가 아니라, 지우는 그 순간에는 느려진다.**

**D-2. OPTIMIZE TABLE(재구축) 후 — 그제서야 정리가 완성된다**

| 항목 | 삭제 직후 | **OPTIMIZE 후** |
|---|---|---|
| Q1 선별 | 70ms | **6.0ms** |
| data + index | 101.6 + 70.2MB | **2.5 + 3.0MB** |

```
-> Limit: 50 row(s)  (cost=545 rows=50) (actual time=6.02..6.02 rows=50 loops=1)
    -> Index lookup using uk_exhibition_outbox_type_target (message_type='DRAFT_STAGED')
       (actual time=0.0114..4.84 rows=5334 loops=1)
```

(재구축 후에도 B의 2.4ms보다 느린 6.0ms인 이유: 16천 행 테이블에선 due 비율이 38%라 어떤 플랜이든 비슷하고, 옵티마이저가 UK 경로를 골랐다 — 이 규모에선 아무래도 좋다.)

## 5. 성과 요약과 결론

| 시나리오 | 조건 | Q1 선별(웜) | 무엇이 달라졌나 |
|---|---|---|---|
| A | 100만 건 · 인덱스 없음 | **445~509ms** | 풀스캔 100만행 + filesort — 교과서 장애 재현 |
| **B** | **100만 건 · 현행 운영 인덱스** | **1.8~2.4ms** | 레인지 스캔 1,300행 — **비대해도 도래분만 짚는다** |
| C | B + 복합(type,status,next) | 0.89ms | 434행 — 개선은 되나 실익 없음 → 미채택 |
| D | SUCCEEDED 98.4만 삭제 직후 | **70ms** | 삭제 마크 + 통계 왜곡 — 정리가 일시 악화를 부름 |
| D2 | + OPTIMIZE TABLE | 6.0ms | 공간 101.6→2.5MB — 재구축까지 해야 정리 완성 |

**결론 — 아웃박스PR §9·§10에 반영되는 사실들:**

1. **교과서 장애의 몸통은 '비대'가 아니라 '인덱스 부재'다.** 인덱스만 올바르면(도래분을 짚는 `(status, next_attempt_at)`) 100만 건 누적에서도 폴링은 2.4ms다 — 220배 차이의 원인은 행 수가 아니라 접근 경로였다.
2. **현행 스키마(V35)는 100만 건을 검증받았다.** 하루 수십 건 유입 기준 수십 년 치 누적 규모다.
3. **"인덱스가 있으면 비대는 무해하다"가 실측으로 확인됐다.** SUCCEEDED 98.4만 행은 선별 쿼리가 건드리지도 않는다. 반대로 섣부른 대량 DELETE는 일시 악화(70ms)와 공간 미반환을 부르고, OPTIMIZE(재구축·잠금 비용)까지 해야 끝난다 — 정리는 공짜가 아니다.
4. 이 실험이 정리 절차를 설계했고 **그대로 구현됐다**: 주간(일요일 03시) SUCCEEDED 7일 경과분을 **소량 배치(500건/tx) 반복 삭제** — "DELETE 한 방" 금지, 주간 규모에선 OPTIMIZE 불필요(퍼지 자연 소화). 대량 정리가 필요해지는 날의 절차는 **소량 배치 → 저트래픽 OPTIMIZE → ANALYZE**(통계 복구) 순서다.

## 부록 — 재현 방법

```sql
-- 별도 스키마에 V35 DDL로 테이블 생성 후, 숫자 크로스조인으로 100만 행 적재(8초).
-- 분포: SUCCEEDED 984k / PERMANENT 10k / RETRYABLE 4.7k(대기)+0.3k(도래) / PENDING 1k(도래)
INSERT INTO exhibition_outbox (message_type, target_key, status, attempt_count, next_attempt_at, ...)
SELECT ELT(...조건별 타입...), CONCAT('EXT-', n), CASE WHEN n<=984000 THEN 'SUCCEEDED' ... END, ...
FROM (SELECT a.i + b.i*100 + c.i*10000 + 1 AS n FROM t100 a, t100 b, t100 c) seq;  -- 10^6

-- 측정은 전 시나리오에서 EXPLAIN ANALYZE 2회(2회차 웜 채택), 원문은 본문에 그대로 첨부.
```

실험 스크립트 전문과 원시 출력은 실험 세션 산출물(`01-setup.sql` ~ `05-scenario-d2.sql`, `result-*.txt`)로 보존.
